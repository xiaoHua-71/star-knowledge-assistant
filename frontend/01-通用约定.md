# 通用约定

> **这一篇必须读。** 后面所有接口都建立在这里的约定上，尤其是下面的「类型陷阱」一节。

## 一、基础信息

| 项 | 值 |
|---|---|
| 本地地址 | `http://localhost:8102` |
| 上下文路径 | **`/api`**（所有接口都要带这个前缀） |
| 完整示例 | `http://localhost:8102/api/user/login` |
| 数据格式 | 请求体 `application/json`，响应体 `application/json`（流式接口除外） |
| 接口文档 UI | `http://localhost:8102/api/doc.html` |
| 字符编码 | UTF-8 |

**为什么会有 `/api` 前缀**：它是后端的 `server.servlet.context-path` 配置，不在 Controller 上。所以 Swagger 里显示的路径是 `/user/login`，但真实请求路径是 `/api/user/login`。配置反向代理（如 Nginx）或 Vite dev proxy 时也要带上这个前缀。

## 二、响应信封

**除流式接口外，所有接口的响应都是同一个结构：**

```json
{
  "code": 0,
  "data": { },
  "message": "ok"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | number | **0 表示成功**，非 0 表示失败。判断成功与否**只看这个字段** |
| `data` | 任意 | 业务数据。成功时是具体内容；失败时**一定是 `null`** |
| `message` | string | 提示信息。成功时是 `"ok"`；失败时是具体原因，**可以直接展示给用户** |

### ⚠️ HTTP 状态码永远是 200

**这是最容易踩的第二个坑。**

后端的 Controller 把异常都捕获了，转成了 `code` 非 0 的响应体。所以：

- 登录失败 → HTTP 200，但 `{code: 40000, message: "密码错误"}`
- 未登录访问 → HTTP 200，但 `{code: 40100, message: "未登录"}`
- 不存在的数据 → HTTP 200，但 `{code: 40400, ...}`

**所以前端的错误处理不能靠 HTTP 状态码，必须判断 `code`。**

```js
// ✅ 正确
const res = await fetch('/api/user/current', { credentials: 'include' });
const body = await res.json();
if (body.code !== 0) {
  // 处理错误
  if (body.code === 40100) router.push('/login');
  else toast(body.message);
  return;
}
// 用 body.data

// ❌ 错误：res.ok 永远是 true，这个判断没有意义
if (!res.ok) { ... }
```

### 唯一的例外：流式接口

流式接口（SSE）**建立成功之后**，流里推的数据**不走这个信封**，直接就是事件数据。

但流**建立之前**如果失败（未登录、参数错），返回的还是普通 JSON 信封。

**这个区分很重要，见 [02-SSE协议规范](02-SSE协议规范.md) 的「致命陷阱」一节。**

## 三、类型约定

### ⚠️ 陷阱 1：所有 `Long` 类型在 JSON 里是**字符串**

后端注册了一个全局的 Jackson 序列化器，把所有 `Long` 输出成**字符串**。

```json
{ "code": 0, "data": { "id": "1844674407370955161", "username": "zhangsan" } }
```

**为什么这么做**：Java 的 `Long` 是 64 位，JS 的 `Number` 只能安全表示 53 位整数。如果后端用雪花 ID 之类的大数，直接输出数字会导致**精度丢失**（末几位变成 0）。所以后端统一输出字符串。

**前端要做的**：

| 场景 | 做法 |
|---|---|
| TypeScript 类型定义 | 所有 id 字段写成 `string`，**不要写 `number`** |
| 比较 | `a.id === b.id`（都是字符串，可以直接比） |
| 当 Map/对象的 key | 可以直接用，字符串正好适合 |
| 参与计算 | 不需要（id 不参与运算） |
| 传给后端 | 直接传字符串，不要 `Number()` 转换 |

**受影响的字段**：后端所有 **`Long` / `long`（64 位）** 字段都会转成字符串，**不只是 id**：

- 所有 `id` 类字段——`userId`、`conversationId`、`messageId`、`runId`、`stepId`、`kbId`、`docId`、`chunkId`、`categoryId`
- **分页响应的计数字段**——`total`、`size`、`current`、`pages`（MyBatis-Plus 分页对象里它们是 `long`，也被这条规则波及）

**不受影响的字段**：`int` / `Integer` 类型仍是普通 `number`——如 `code`、`tokenCount`、`messageCount`、`docCount`、`chunkCount`、`seq`；金额是 `number`（见下）。

### ⚠️ 陷阱 2：时间格式**待实测确认**

`UserVO.createTime` 是 Java 的 `LocalDateTime`。后端没有配置 `spring.jackson` 的日期格式，所以用的是 Spring Boot 默认——**ISO-8601 字符串，不带时区**：

```json
"createTime": "2026-09-21T10:30:00"
```

**但这一条请在联调时用浏览器 Network 面板实测确认**，不要直接信。因为：

- 后端 `application.yml` 里没有显式的日期格式配置，默认行为由 Spring Boot 版本决定
- 如果后续有人加了 `spring.jackson.date-format`，格式会变
- 有些实体的时间字段是 `java.util.Date` 而不是 `LocalDateTime`，两者的默认格式**不一样**（`Date` 会带时区偏移）

**建议做法**：前端封装一个统一的日期解析函数，兼容 `"2026-09-21T10:30:00"` 和 `"2026-09-21 10:30:00"` 两种格式，别把格式假设散落在各个组件里。

### 金额

如果后续出现金额字段（如调用成本），类型是 `number`（后端用 `DECIMAL`），单位**元**，最多 6 位小数。展示时用 `toFixed(4)`。

### 分页

列表接口用统一的请求参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `current` | number | 1 | 第几页，从 1 开始 |
| `pageSize` | number | 10 | 每页条数，最大 50 |
| `sortField` | string | 各接口定 | 排序字段 |
| `sortOrder` | string | 各接口定 | **`ascend`** 升序 / **`descend`** 降序 |

**⚠️ 注意 `sortOrder` 的值是 `ascend` / `descend`，不是 `asc` / `desc`**，也不是 `ascending`。写错会静默不排序（不报错）。

**⚠️ 已知后端缺陷**：`CommonConstant.SORT_ORDER_DESC` 的值被写成了 `" descend"`（**前面多了一个空格**）。这意味着如果后端用 `equals` 去比对降序值，前端传 `descend` 会**匹配不上，降序静默失效**。

前端**仍然传 `descend`**（这是本约定的正确值），后端会修掉这个常量。在修掉之前，降序排序可能不生效——如果你发现排序参数传了没反应，先怀疑这个。

响应里的分页数据（**注意是 `size` 且都是字符串**）：

```json
{
  "code": 0,
  "data": {
    "records": [],
    "total": "42",
    "size": "10",
    "current": "1",
    "pages": "5"
  }
}
```

**说明**（⚠️ 这一节字段名和类型最容易记错，逐条看清）：

- **响应里每页条数的字段名是 `size`，不是 `pageSize`。** 请求参数叫 `pageSize`，响应回显叫 `size`（MyBatis-Plus 分页对象的字段名），**两者名字不一致**，别混用。
- `total`（总条数）、`size`（每页条数）、`current`（当前页）、`pages`（总页数）**全是字符串**——它们在后端是 Java `long`，被上一条「Long → 字符串」的规则波及，**不要**以为「只有 id 才是字符串」。
- 需要当数字用时（算总页数、做循环）自行 `Number(data.total)` 转换。
- `records` 里每一项的结构看具体接口。

## 四、鉴权

**用 Session + Cookie，没有 Token，没有 `Authorization` 头。**

- 登录成功后，后端通过 `Set-Cookie` 下发会话 cookie
- 之后每个请求浏览器自动带上这个 cookie
- 后端从 session 里取当前用户

### ⚠️ 前端必须做的两件事

**1. 每个请求都要带 cookie。**

浏览器**同源**请求会自动带 cookie，但**跨域**（比如前端跑在 `localhost:5173`，后端在 `localhost:8102`）**不会自动带**，必须显式开启：

```js
// 原生 fetch
fetch('/api/user/current', { credentials: 'include' })

// axios
axios.create({ withCredentials: true })
```

不设置的话，表现是「登录接口返回成功，但下一个请求说未登录」。**这是跨域联调时最常卡住的地方。**

**2. 后端已经配好了跨域支持**（`CorsConfig`）：允许凭证（`allowCredentials: true`）+ 允许任意来源（`allowedOriginPatterns: "*"`）。所以跨域带 cookie 是可以工作的，不需要额外要求后端改配置。

### Cookie 的名字

后端用的是 Spring Session，cookie 名**默认是 `SESSION`**，不是 `JSESSIONID`。用浏览器开发者工具的 Application → Cookies 面板能看到实际名字。

### ⚠️ 待确认：关掉浏览器后登录还在吗

`application.yml` 里配了 `server.servlet.session.cookie.max-age: 159200`，但 Spring Session 的 cookie 参数是由 `spring.session.servlet.cookie.*` 控制的，**这个配置可能不生效**。

**联调时请实测一次**：登录 → 完全关闭浏览器 → 重新打开 → 访问「获取当前用户」。

- 如果还是登录状态 → 没问题
- 如果变成未登录 → 需要后端加 `spring.session.servlet.cookie.max-age`（提一下就行，是后端一处配置的事）

服务端 session 本身配的是 **30 天过期**（`spring.session.timeout: 2592000`），所以问题只可能出在浏览器这侧的 cookie 上。

## 五、错误码

| `code` | `message`（默认） | 含义 | 前端建议处理 |
|---|---|---|---|
| `0` | `ok` | 成功 | 正常走业务逻辑 |
| `40000` | 请求参数错误 | 参数不合法。**具体原因看 `message`**，它是后端拼的具体提示 | 用 toast 或表单错误提示展示 `message` |
| `40100` | 未登录 | 没登录，或会话过期 | **跳登录页**，并记住当前页面以便登录后跳回 |
| `40101` | 无权限 | 登录了，但没权限操作这个资源（比如访问别人的会话） | 提示「无权操作」，不要跳登录页 |
| `40300` | 禁止访问 | 被封号等 | 提示并引导联系管理员 |
| `40400` | 请求数据不存在 | 记录被删了，或 id 传错了 | 提示并刷新列表 |
| `50000` | 系统内部异常 | 后端未捕获的异常 | 提示「系统繁忙，请稍后重试」 |
| `50001` | 操作失败 | 业务操作失败（如更新失败、模型调用失败） | 展示 `message`，视情况给「重试」按钮 |

**关于 `40000` 的一个细节**：后端很多接口把所有异常都收敛成了 `40000`，所以 **`message` 里才有真正的原因**（比如「用户名已存在」「两次输入的密码不一致」）。失败时**一定要把 `message` 展示出来**，否则用户不知道哪里错了。`message` 可能是空字符串（后端有个构造函数不传 message），所以要有兜底文案。

## 六、开发环境建议

### 推荐：用代理而不是直连

Vite 配置示例（避免跨域 cookie 的一堆问题）：

```js
// vite.config.js
export default {
  server: {
    proxy: {
      // 把 /api 开头的请求代理到后端
      '/api': {
        target: 'http://localhost:8102',
        changeOrigin: true,
      },
    },
  },
}
```

**注意**：这里**不要**写 `rewrite: path => path.replace(/^\/api/, '')`。因为后端的 `/api` 是上下文路径，是要保留的。去掉的话所有请求都会 404。

配了代理之后，前端代码里写 `fetch('/api/user/current')` 就是同源请求，cookie 自动带，`credentials: 'include'` 也可以不写（写了也无害）。

### 直连后端（不配代理）

必须：`credentials: 'include'` + 确认 `localhost:5173` → `localhost:8102` 这种跨域是允许的（后端已放行任意来源，所以是可以的）。

### 拿验证码

注册用的邮箱验证码，在**开发环境不会真的发邮件**（后端没配 SMTP 时会降级）。验证码会被打到**后端控制台日志**里：

```
邮件发送失败(可能是未配置SMTP)，验证码已写入Redis: email=xxx@qq.com, code=123456
```

联调注册流程时，去后端日志里捞这串数字。
