# 前端整体架构

> ⬜ **状态：架构已定稿，代码尚未开始。**
>
> 这篇文档回答的是「**代码怎么组织**」，不是「接口怎么调」——接口在 [01-通用约定](01-通用约定.md) 和各模块篇（`10`~`60`）里。
>
> 读者有两个：**实现前端的人/工具**（含 AI 生成），和**三个月后的自己**。所以本文记录的是**决策和理由**，不是代码。

## 一、这个架构要防的是哪几类失败

前端的职责只有一句话：**把后端的流式事件，稳定地变成一个不会骗人的界面。** 它不参与检索、不参与工具执行、不参与记忆裁剪——那些前端看不到。

围绕这句话，前端有三类特有的失败模式。整个架构就是为防它们而分层：

| 失败模式 | 具体表现 | 防它的机制 |
|---|---|---|
| **① 流式状态错乱** | 「生成中」和「已停止」同时为真；点了停止卡住；重连后文本重复一大段 | 一个显式状态机（§5.3）+ 事件语义集中在一处（§5.2） |
| **② 响应式信息泄漏** | id 当数字比较永远不等；cookie 没带上所以「登录成功但立刻未登录」；把 `code` 当 HTTP 状态码 | 契约层收敛（§5.1）+ TypeScript 类型（§三） |
| **③ 高频更新拖垮渲染** | 一次回答 500 个 token，每个 token 触发整列重渲染，界面越来越卡 | 渲染分层：数据写入与视图刷新解耦（§5.4） |

**边界（明确不归前端管）**：

- 检索过程（走不走 RAG、召回了什么）——协议里不推事件，前端不展示
- 工具的执行细节与幂等——前端只负责展示和确认
- 消息的截断与记忆窗口——前端只调接口

## 二、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | **Vue 3**（Composition API + `<script setup>`） | 见下方「为什么不选 React」 |
| 构建 | **Vite** | 见下方「为什么不上 Next.js」 |
| 语言 | **TypeScript** | 契约里三处类型陷阱（id 是 string、`sortOrder` 是 `ascend`/`descend`、时间格式不定）靠类型挡住，比靠人记可靠 |
| 状态 | **Pinia** | 官方方案，够用 |
| 路由 | **Vue Router 4** | 需要把 `runId` 放进 URL（见 §5.3） |
| 样式 | **Tailwind CSS + 自写组件** | 见下方「为什么不用组件库」 |
| Markdown | `markdown-it` + 代码高亮 + `DOMPurify` | 见 §5.5，含 XSS 处理 |

> **待验证**：Vue / Vite / Tailwind 的**具体版本组合**在搭脚手架时钉死并记到这里。上面只定方向，不写没实测过的版本号。

### 为什么不选 React

1. **验收能力**。这个前端主要由 AI 生成，人负责评审。而这个项目前端的全部难点，恰好都是「**看起来能跑、但行为是错的**」的 bug（重连后文本重复、点停止卡在生成中、中文乱码）——在评审者不熟的框架里定位这类 bug，成本高到不可接受。
2. **DeepSeek 的视觉风格与框架无关**。它的观感来自留白、克制的配色和折叠信息，不是来自 React 的任何特性。
3. **React 的真实优势在这里不成立**。React 侧有现成的 AI 聊天组件生态（Vercel AI SDK、assistant-ui），但它们预设自己的传输协议（OpenAI 风格的 delta 流），与本项目的自定义事件协议（`run_start` / `interrupt` / `approve`）不兼容，最终仍要手写客户端。

**这个结论的前提**：评审者只熟悉 Vue。前提变了结论就变——如果哪天前端交给一个只会 React 的人，上面第 1 条立刻反转。

### 为什么不上 Next.js / Nuxt

后端是**独立的 Java 服务**（`localhost:8102`），前端是纯 SPA。SSR、SEO、服务端路由这些都不需要，引入只会让「本地起服务 + 代理 + cookie」这条链路多一层复杂度（详见 [01-通用约定](01-通用约定.md) 的代理配置）。

### 为什么不用组件库（Element Plus / AntD）

- **外观**：组件库的默认观感是「后台管理系统」——重边框、小圆角、密集控件。而目标风格是 DeepSeek 那种大留白、几乎无边框的克制感。**要把它改成目标风格，比从零写更费劲。**
- **聊天界面本来就没有可抄的组件**：流式文本、折叠的思考过程、工具调用卡片、审批弹窗——这些在任何组件库里都不存在。
- **代价与补偿**：表格、分类树、文件上传这些「表单密集」的页面要自己写。**如果知识库管理页的工程量失控，允许局部引入 `Reka UI`（headless）补这几个控件**——headless 只给行为和可访问性、不带样式，不会污染视觉。**不要**引入带样式的完整组件库。

### 与 `salary-leap-frontend` 的复用关系

那边是 **JS + Element Plus**，本项目是 **TS + Tailwind**，**不能直接复制组件**。可复用的是**逻辑**，需要改写：

| 可搬 | 要改 |
|---|---|
| axios 实例与响应拦截器的思路 | 加上 TS 类型；错误改成抛 `ApiError` |
| 登录 / 注册 / 改密码页的表单校验规则 | 换成 Tailwind 样式 |
| Pinia 组织方式 | 只保留 userStore 的结构，其余重写 |

## 三、目录结构

```
src/
├─ api/            契约层：一个后端模块一个文件
│   ├─ client.ts       axios 实例 + 拦截器（唯一的出口）
│   ├─ user.ts  conversation.ts  chat.ts  agent.ts  knowledge.ts  tools.ts
├─ types/          与后端契约一一对应的类型（id 一律 string）
├─ stream/         ★ 流式层，本架构的核心
│   ├─ sseClient.ts    fetch + 字节流 → 事件对象（零 Vue 依赖）
│   ├─ dispatch.ts     事件 → store 动作（零 Vue 依赖，可单测）
│   └─ mockSource.ts   本地事件回放器（见 §六）
├─ stores/         Pinia：user / conversation / chat / kb / tools
├─ components/
│   ├─ chat/         聊天区组件（本项目的门面）
│   └─ common/       通用小件（图标、折叠、空态）
├─ views/          页面，与路由一一对应
├─ router/
├─ styles/         tokens.css（设计令牌）+ tailwind 入口
└─ utils/          日期解析、格式化、分页参数
```

**依赖方向是单向的，不能反向、不能跨层跳**：

```
views → components → stores → api / stream
```

两条硬性纪律：

1. **`components/` 里不允许出现 `axios` 或 `fetch`**。所有网络请求必须走 store。否则同一个接口会在多个组件里各写一遍错误处理。
2. **`stream/` 里不允许出现 Vue 响应式 API**（`ref` / `reactive`）。理由见 §5.4——它要能脱离 Vue 单测。

## 四、数据流总览

```
ChatInput ─发送─► chatStore.send()
                    │
                    ├─ 无当前会话 → POST /conversation/create 拿 id
                    ├─ POST /chat/stream   （用 fetch，不走 axios，原因见 §5.1）
                    └─ uiState → running；runId 写入 URL

        ◄─── text/event-stream ─── 后端
                  │
        stream/sseClient.ts      只做一件事：字节 → 事件对象
                  │
        stream/dispatch.ts       只做一件事：事件 → store 动作（纯逻辑）
                  │
              chatStore          持有：messages / steps / plan / uiState
                  │
        components（订阅）        MessageBubble / ProcessPanel / RunControls
```

**关键读法**：`sseClient` 和 `dispatch` 是**两个不同的关注点**，分开的理由是它们各自的失败模式不同——前者怕「切错块」（乱码、丢事件），后者怕「理解错事件语义」（把 `snapshot` 当 `delta`）。混在一起写，两类 bug 会长在同一个函数里。

## 五、三条主链路

### 5.1 契约层（`api/`）

**一个 axios 实例，一个出口。** 所有非流式请求都走它：

```
client = axios.create({
  baseURL: '/api',              // 前缀保留，不要 rewrite 掉
  withCredentials: true,        // 跨域带 cookie 的唯一开关
  timeout: 30000,
})
```

响应拦截器做三件事，顺序不能乱：

1. `code !== 0` → 抛 `ApiError{ code, message }`（**不是**按 HTTP 状态码判断，后端永远返回 200）
2. `code === 40100` → 清 `userStore`，跳登录页并**记住当前地址**（登录后跳回）
3. `message` 为空时给兜底文案（后端有不传 message 的构造路径）

调用方只需要 `try / catch (ApiError)`，`message` 直接可展示。

**接口层要顺手收敛的三处契约细节**（细节见 [01-通用约定](01-通用约定.md)，这里只说收敛方式）：

| 项 | 做法 |
|---|---|
| `sortOrder` | 类型定成 `'ascend' \| 'descend'` 字面量联合，写错编译期就报错 |
| 分页参数 | 统一 `PageQuery` 类型与默认值（`current=1`、`pageSize` 分档），别在每个调用点手写 |
| 日期 | 只有一个 `parseDate()`，同时容忍 `T` 分隔与空格分隔两种格式；组件里**不允许**出现 `new Date(str)` |

**SSE 为什么绕开 axios**：`POST /chat/stream` 的响应体是 `text/event-stream` 流。axios 的响应处理会尝试把响应体整体读出来，拿不到增量；而且**建流失败时响应体是普通 JSON**（[02-SSE协议规范](02-SSE协议规范.md) 的「致命陷阱」），需要先看 `Content-Type` 再决定怎么读。这个分支必须自己写，用 `fetch`。

### 5.2 流式层（`stream/`）

**`sseClient.ts`** 的接口形状（实现照 [02-SSE协议规范](02-SSE协议规范.md) 第七节的参考实现，此处不重复代码）：

```
chatStream({ conversationId, content, kbIds }, handlers) → close()
reconnect({ runId, lastEventId }, handlers)               → close()
```

它必须满足四条（每条对应一个已知的坑）：

| 要求 | 不满足会怎样 |
|---|---|
| 先看 `Content-Type` 再决定解析方式 | 建流失败时把 JSON 当真流解析，界面「连接上了但什么都没发生」 |
| `TextDecoder({ stream: true })` | 中文在多字节边界被切坏，偶发乱码 |
| 缓冲跨 chunk 的不完整事件块 | 偶发丢事件 |
| `AbortController` 关闭 | 组件卸载/离开页面后连接泄漏 |

**`dispatch.ts`** 是本文档最该被逐条核对的部分——**一张表覆盖全部 11 种事件**：

| `event` | store 动作 | 幂等性要求 |
|---|---|---|
| `run_start` | 记 `runId` / `messageId`；`uiState → running`；`runId` 写入 URL | 覆盖写，天然幂等 |
| `todo_update` | **全量替换**计划；`planVersion` 比当前小则丢弃 | 重连会重放，必须允许重复 |
| `tool_call` | 按 `stepId` **新增或更新**一个步骤（RUNNING） | 按 `stepId` 归并，不追加两条 |
| `tool_result` | 按 `stepId` **就地更新**状态与结果 | ★ 重连会重放**已持久化**的旧 `tool_result`，必须靠 `stepId` 覆盖 |
| `message_delta` | 追加到**非响应式缓冲**，按帧合批 flush | 重复追加会造成文本翻倍，靠 `lastEventId` 去重 |
| `message_snapshot` | **替换**缓冲全文 | 覆盖写 |
| `interrupt` | 状态机迁移（`USER_STOP`→stopped；`APPROVAL_REQUIRED`→awaitingApproval）；**关闭流** | 覆盖写 |
| `run_end` | 收尾：定稿文本、刷新会话列表、清 URL 的 `runId` | 覆盖写 |
| `error` | `uiState → error`；**保留已生成文本**；`retryable` 决定是否给重试 | 覆盖写 |
| `ping` | 只用于心跳超时检测 | — |

**★ 整张表最重要的约束：事件处理必须幂等。** 原因在 [40-agent](40-agent-中断与恢复.md) 里说过——重连接口会把 `id > lastEventId` 的**已持久化事件**重新推一遍。如果 `tool_result` 的处理是「往列表里 append」，重连一次界面上就多一条重复的工具记录。

**重连策略**（属于 `stream/`，不属于组件）：

```
断线（没收到 run_end 也没收到 interrupt）
  → 等 1s 重连 → 失败 → 等 2s → 失败 → 等 4s
  → 三次仍失败 → uiState = error('连接已断开')，给手动重连按钮
```

**不要在流刚断开时就报错**——网络抖动时后端往往还在正常生成答案，重连能接上。

### 5.3 状态层（`stores/`）

| store | 持有 | 生命周期 |
|---|---|---|
| `userStore` | 当前用户、登录态 | 全局 |
| `conversationStore` | 会话列表（分页）、当前会话元信息 | 路由级 |
| **`chatStore`** | 消息列表、计划、步骤、**uiState** | 会话级 |
| `kbStore` / `toolsStore` | 知识库、文档、工具清单与调用记录 | 页面级 |

**`chatStore` 里的状态机直接沿用 [40-agent](40-agent-中断与恢复.md) 的定义，不另起一套**：

```ts
type ChatUiState =
  | { kind: 'idle' }
  | { kind: 'running'; runId: string }
  | { kind: 'stopping'; runId: string }        // 已请求停止，等 interrupt 事件
  | { kind: 'stopped'; runId: string }
  | { kind: 'awaitingApproval'; runId: string; tool: PendingTool }
  | { kind: 'reconnecting'; runId: string; attempts: number }
  | { kind: 'error'; message: string; retryable: boolean }
```

**两条不能商量的规则：**

1. **`runId` 必须写进 URL**（`/chat/:conversationId?run=xxx`）。刷新页面后前端靠它判断「上次有一次运行」——查状态决定是重连流还是显示继续按钮。不写进 URL，刷新就丢。
2. **`stopping → stopped` 的唯一触发是 `interrupt` 事件**，不是停止接口的返回值，也不是连接关闭。前者太早（停止请求只是登记），后者可能是网络问题。

### 5.4 渲染分层（防失败模式 ③）

一次回答可能有几百个 `message_delta`。如果每个 delta 都直接改 Pinia 的响应式数组，会触发整列消息重渲染 + 全文 Markdown 重解析，随着回答变长越来越卡。

**做法：数据与视图分离。**

```
message_delta ──► 非响应式缓冲（普通字符串变量）
                        │  按帧合批（rAF）或固定间隔
                        ▼
                  响应式 state（触发渲染）
```

三条配套要求：

1. **只对「最后一条正在生成的消息」走这个高频通道**，历史消息是静态的，走普通渲染。
2. **Markdown 渲染节流**：生成中不必每帧都全量解析。生成中可以用轻量渲染（只处理换行与代码块），`run_end` 后再做一次完整渲染。
3. **不要用 `v-html` 直接塞模型输出**——见 §5.5。

> **待验证**：合批的时间间隔（rAF 还是 100ms 固定间隔）需要实测。文字在 60fps 下逐个蹦出是否可读、是否加剧抖动，得看真实手感，不能凭推断定。

### 5.5 Markdown 与安全

助手回答是 Markdown（含代码块、表格、公式），而且内容来自**模型 + 用户上传的文档**——**这是不可信输入**。

| 项 | 要求 |
|---|---|
| 渲染 | `markdown-it`，**关闭 `html` 选项**（不允许原始 HTML 通过） |
| 消毒 | 输出再过一遍 `DOMPurify`，双保险 |
| 代码高亮 | `shiki` 或 `highlight.js`（**待验证**：包体积与首屏影响，可能需要按需加载） |
| 公式 | KaTeX，**按需**，没有公式就不加载 |
| 链接 | 外部链接强制 `target="_blank"` + `rel="noopener noreferrer"` |

**只关掉 `html` 选项还不够**：`markdown-it` 的链接协议白名单也要收紧（`javascript:` 伪协议是经典 XSS 入口），并且必须过 DOMPurify。这一条不是过度设计——模型完全可能因为知识库里有恶意网页（[50-knowledge](50-knowledge-知识库管理.md) 支持「添加网页」）而输出危险内容。

## 六、界面架构

### 6.1 设计令牌（`styles/tokens.css`）

所有颜色、圆角、间距、字号定义一次，组件里只用令牌，不写字面量。**这样调整视觉风格时只改一个文件。**

目标风格取自 DeepSeek，核心特征是：**大留白、极弱边框、信息分层靠折叠而不是靠分隔线。**

> **待验证**：下列取值是照 DeepSeek 界面**目测/取色**得到的起点，**不是实测结论**——实现时对着截图取色校准，校准后把最终值写回这里。
>
> | 令牌 | 参考值 | 用途 |
> |---|---|---|
> | `--color-bg` | `#FFFFFF` | 主区背景 |
> | `--color-bg-subtle` | `#F9FAFB` | 侧栏、代码块、过程面板 |
> | `--color-text` | `#1A1A1A` | 正文 |
> | `--color-text-muted` | `#6B7280` | 时间、次要说明 |
> | `--color-primary` | `#4D6BFE` | 主色（发送按钮、链接、用户气泡） |
> | `--color-border` | `#E5E7EB` | 输入框边框（其余地方尽量不用） |
> | `--radius-bubble` | `12px` | 用户消息气泡 |
> | `--radius-input` | `24px` | 输入框（大圆角是辨识度的一部分） |

### 6.2 布局骨架

```
┌──────────┬──────────────────────────────────────┐
│ 侧栏      │           主区（居中单列）             │
│ (可折叠)  │  ┌────────────────────────────────┐  │
│          │  │  消息流（≈46rem 宽，居中）        │  │
│ [+ 新会话]│  │   ┌─ ProcessPanel（可折叠）       │  │
│          │  │   └─ 回答正文                   │  │
│ 会话 1    │  │                                 │  │
│ 会话 2    │  │                                 │  │
│ ...      │  └────────────────────────────────┘  │
│          │  ┌────────────────────────────────┐  │
│ [用户]    │  │  输入框（大圆角，左侧内容右侧发送） │  │
└──────────┴──────────────────────────────────────┘
```

主区宽度上限定成 `max-w`，**不要拉满屏**——这是 DeepSeek 观感的关键，长行文本也更好读。

| 组合 | `ToolCallCard` | 单个步骤：名称、参数、结果、耗时、`replayed` 标记 |
| 组合 | `ApprovalDialog` | 人工确认框 |
| 组合 | `RunControls` | 停止 / 继续 / 重连按钮，**完全由 uiState 驱动** |
| 页面 | 见 §6.5 | |

**`RunControls` 必须是「状态的投影」，不能自己存状态**。按钮该显示停止还是继续，完全从 `uiState` 推导。自己存一份「是否正在停止」的本地变量，就是失败模式 ① 的起点。

### 6.4 ★ DeepSeek 的哪些抄、哪些不抄

**抄的是视觉骨架和信息收束方式：**

| DeepSeek | 本项目对应 | 说明 |
|---|---|---|
| 「深度思考（用时 N 秒）」折叠块 | `ProcessPanel` | 把 `todo_update` 的计划 + `tool_call`/`tool_result` 收进去。默认折叠，标题显示「已完成 N 步 · 用时 x 秒」 |
| 居中单列 + 底部大圆角输入框 | 布局骨架 | 见 §6.2 |
| 助手消息下方的操作条 | 复制 / 编辑 / 删除 | 编辑 = 截断重发（[20-conversation](20-conversation-会话与消息.md) 的 `message/delete`） |
| 生成中的停止按钮 | `RunControls` 的停止态 | 但**完成判定必须等 `interrupt` 事件** |

**明确不抄的：**

| DeepSeek | 为什么不抄 |
|---|---|
| 输入框里的「深度思考」开关 | 我们的工具由**模型自己决定**调用，不是用户的开关。给一个无法真正控制的开关是骗用户 |
| 「重新生成」按钮 | **语义完全不同。** DeepSeek 的重生成是重跑一遍；本项目的 `resume` 是**从断点续跑**，已执行过的工具会重放结果而**不会重复执行**。按钮文案必须是「继续」，不能叫「重新生成」——否则用户会以为副作用会被重做一遍 |
| 输入框旁的附件上传 | 知识库是独立实体，上传走知识库页面，不挂在某次对话上 |
| 引用来源卡片 | **本项目协议里没有这个事件**，见下方「必须补的一块」 |

**必须自创的三处**（DeepSeek 没有对应交互）：

1. **审批确认框**（`APPROVAL_REQUIRED`）——必须原样展示 `pendingTool.arguments`，用中文 `displayName`，拒绝按钮不能藏。设计细节见 [60-tools](60-tools-工具.md)。
2. **执行详情面板** —— 让用户看到调了什么、传了什么、花了多久，并**标注 `replayed: true` 的步骤**（「已恢复」）。这既是解释性能，也是在向用户证明「你的操作没有被重复执行」。
3. **已停止 / 继续态** —— 挂起是正常状态，界面要平静地展示它，不要做成错误。

> **必须补的一块（建议提给后端）**：`references` 事件——回答引用了哪几篇文档。
>
> 这是 RAG 产品的**核心信任点**：用户凭什么相信这个答案？凭他能点开看依据。目前 [30-chat](30-chat-对话与流式.md) 把它列为待定项，但**界面上一旦缺了它，产品看起来就和「套壳聊天」没有区别**——而这恰恰是本项目要证明自己不是的东西。建议优先级排在知识库管理页之前。

## 七、边界、风险与已知限制

### 7.1 明确不做

- 检索过程可视化（协议不推事件，前端无从展示）
- 切片内容查看（[50-knowledge](50-knowledge-知识库管理.md) 中该接口仍待定）
- 消息撤回（只能靠截断重发）
- 多标签页状态同步、离线缓存、消息搜索

### 7.2 已知风险

| 风险 | 应对 |
|---|---|
| **后端未实现，无法联调** | ★ 见 §7.3，这是本项目前端最大的一条风险 |
| 流式渲染性能 | §5.4 的合批 + 节流；阈值待实测 |
| 超长会话的消息列表卡顿 | 暂用「分页加载更早」；如果真的长了，再考虑虚拟滚动。**不要一开始就上虚拟滚动**——它和「动态高度的流式消息」组合起来很容易出问题 |
| 引用来源缺失 | 见 §6.4 的建议 |
| 前后端字段名在实现期微调 | 类型集中在 `types/`，改动只影响一处 |

### 7.3 ★ 先做本地事件回放器

**这是前端开工后的第一件事，不是最后一件。**

后端 `M4`~`M10` 都还没开始（见 [knowledge/01-总体架构与路线图](../knowledge/01-总体架构与路线图.md)），前端如果等接口，会空等很久；而如果照着文档「猜」着写，猜错的地方要等联调才暴露。

做法：把 [02-SSE协议规范](02-SSE协议规范.md) 第五节的**完整事件序列**（含正常流、中断、审批、`message_snapshot` 重连）做成 `stream/mockSource.ts`，提供一个开关切到假数据源。

它一次解决四件事：

1. 界面和状态机可以**立刻**开工并验证，不依赖后端进度
2. §5.2 那张事件表的**每个分支都能被手工触发一遍**（尤其是最难的「重连后收到 snapshot」）
3. 后端实现完后，同一段事件序列可以直接拿来**对照真实流**，快速定位协议实现的偏差
4. 单元测试的固定输入

**成本很低**——回放器只是把一串写死的字符串按事件块吐给 `dispatch`，不需要任何服务端。
