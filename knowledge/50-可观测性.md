# 可观测性

> 状态：**M12 已实现（2026-10-20）**。`ai_call_log` / `ai_tool_log` 两张表、模型与工具调用的真实落库、
> 首 token 延迟、token/成本汇总、`GET /tools/logs`、`GET /tools/logs/summary` 均已可用。
> 数据结构见 [10-数据模型总览](10-数据模型总览.md) 3.4；前端契约见 [frontend/60-tools](../frontend/60-tools-工具.md)。

## ① 这个模块治的是哪类病（通用问题定义）

一个 Agent 回答错了，你事后想问：

- **它为什么答成那样？** 它调了哪个工具、传了什么参数、拿回了什么？
- **它花了多少钱？** 这次运行、这个会话、今天，各消耗多少 token、折合多少人民币？
- **用户到底等了多久？** 总耗时 20 秒不代表体验差——用户可能 500ms 就看到了第一个字。
- **中断续跑有没有重复执行副作用？** 哪个工具结果是重放的、哪个是真正又跑了一次？

这四类问题有一个共同点：**答案不在「当前状态」里，而在「发生过什么」里**。状态表（`agent_run` / `agent_step`）
能告诉你「现在走到哪」，但它会被更新覆盖；日志表只追加，才能回答「当时发生了什么」。

所以这个模块要解决的本质问题是：

> **把系统里每一次花钱的调用（LLM）和每一次改变世界的调用（工具）记录下来，形成可查询、可汇总、
> 可和运行关联的证据链；并且记录本身绝不能反过来影响主流程。**

### 它和「日志 / 指标 / 链路追踪」的关系

| 概念 | 本项目做了什么 | 没做什么 |
|---|---|---|
| 日志（Logging） | 结构化行落 MySQL（不是文本日志） | 没有 ELK/Loki 那一套采集 |
| 指标（Metrics） | 按用户/运行做 SQL 聚合 | 没有 Prometheus / Grafana |
| 链路追踪（Tracing） | `runId` / `stepId` 作为关联键 | 没有 OpenTelemetry span、没有跨服务 traceId |

这不是「做不起」，而是**当前规模下不值得**：单实例、MySQL 就是权威源，一条 SQL 能回答的问题不需要引入三套基础设施。
边界要写清楚，免得后来者以为这里已经有完整的 tracing。

### 它的边界

| 归它管 | 不归它管 |
|---|---|
| 每次 LLM 调用的入参摘要/出参、token、耗时、首 token、成本 | 模型为什么答错（那是评测/人工分析） |
| 每次工具真实执行/重放的参数、结果、耗时、幂等键 | 工具内部怎么实现（[30](30-工具调用.md)） |
| 按用户/运行查询与汇总 | 运行状态流转（[12](12-中断与恢复的状态机.md)） |
| 记录失败不影响主流程 | 日志的长期归档、分区、脱敏（见 ⑤） |

### 四类典型失败模式

| # | 失败模式 | 后果 | 本模块的对策 |
|---|---|---|---|
| 1 | **只记录成功** | 出错时最需要日志，却恰好没有 | `streamOnce` 的成功/失败两条路径都写 |
| 2 | **把完整 prompt 塞进库** | MEDIUMTEXT 迅速膨胀，查询变慢 | 请求快照只存摘要（消息数、工具名、最后一条用户消息）并截断 |
| 3 | **日志写入失败拖垮对话** | 数据库抖动导致本来成功的回答失败 | `ObservabilityService` 内部吞异常，只打 warn |
| 4 | **成本写成 0** | 被误读为「免费」，掩盖价格未配置 | 价格未配置时写 `NULL`，并显式提供价格配置项 |

## ② LangChain4j 官方怎么做

官方在 1.20.0 提供的是**回调式监听**，不是「日志表」：

| 设施 | 作用 | 本项目是否使用 |
|---|---|---|
| `ChatModelListener`（core） | `onRequest` / `onResponse` / `onError`，能拿到请求、响应、token 用量 | **未直接使用**，但设计上参考了它的三个切面 |
| `langchain4j-agentic` 的 `AgentListener` / `AgentMonitor`（1.20.0-beta30） | 监听 Agent 的工具调用、推理步骤 | **未使用**（agentic 本身也未采用，见 [12](12-中断与恢复的状态机.md) ②） |
| Micrometer 适配 | 把耗时/token 变成指标 | **未使用**（当前没有指标系统） |

**为什么不用 `ChatModelListener` 直接落库**：它只知道「这次模型调用」，不知道这次调用属于
**哪个 run、哪个 step、第几轮、对应的工具幂等键是什么**。这些业务关联是本项目日志最有价值的部分；
而这些东西只有自研的 `AgentRunner` 知道。用监听器最终还要把 runId/stepId 塞进上下文再回调，
并没有比在循环里显式写一行更简单。

**结论**：**在状态机的边界显式记日志**。循环知道「刚刚发生了什么」，就把结构化事实交给
`ObservabilityService`；传输、存储、查询都封装在服务里。

## ③ 本项目怎么落地

### 3.1 两张表，各记什么

| 表 | 一行代表 | 关键字段 | 索引要点 |
|---|---|---|---|
| `ai_call_log` | 一次 LLM 调用 | `scene`、`provider`、`modelName`、token 三件套、`costYuan`、`firstTokenMs`、`elapsedMs`、`success` | `runId`、`(conversationId, createTime)`、`(scene, createTime)`、`(userId, createTime)` |
| `ai_tool_log` | **一次真实执行**或**一次结果重放** | `toolName`、`source`、`sideEffect`、`argumentsJson`、`resultJson`、`elapsedMs`、`replayed`、`idempotencyKey` | `runId`、`(toolName, createTime)`、`idempotencyKey` **普通索引**、`(userId, createTime)` |

DDL 在 `sql/observability_tables.sql`（与 knowledge/10 3.4 一致）。

**为什么 `ai_tool_log.idempotencyKey` 是普通索引**：`agent_step` 上它是唯一索引，负责**拦截**重复执行；
日志表要在「发生重放」时再写一行 `replayed=1`，所以不能唯一。两边职责不同，索引类型也不同。

### 3.2 写在哪几个点

```
AgentRunner.drive
  ├─ streamOnce 成功 → ai_call_log(success=1, tokens, firstTokenMs, elapsedMs)
  ├─ streamOnce 失败 → ai_call_log(success=0, errorMsg)（然后继续走原有的失败处理）
  └─ 工具：
       ├─ 真实执行 → ai_tool_log(replayed=0, elapsedMs, idempotencyKey)
       ├─ 撞键重放 → ai_tool_log(replayed=1, elapsedMs=0)
       └─ 续跑重放 → AgentRunServiceImpl.logReplayedSteps → ai_tool_log(replayed=1, elapsedMs=0)
```

**注意 LLM 日志在安全点 2 之前写**：即使这一轮随后被中断，token 也已经真实消耗，必须计入成本。
同一 run 出现两次 `CHAT` 是正常现象（中断续跑会重新生成被中断的一轮，见 [12](12-中断与恢复的状态机.md) 坑 7）。

### 3.3 请求/响应快照：记摘要，不记全文

完整 prompt 动辄上万 token，直接落库会让表迅速膨胀，而且序列化 LC4j 消息对象有版本兼容风险
（[12](12-中断与恢复的状态机.md) M8 已知边界）。所以：

- `requestJson` 存 `{messageCount, toolNames, lastUserMessage}`；`lastUserMessage` 最多 2000 字符；
- `responseJson` 存 `{text, toolCalls}`（`llmResponseSnapshot`）；
- 落库前统一按 `ai.observability.max-snapshot-chars`（默认 8000）截断，尾部加「…（已截断）」。

**取舍**：排查「用户到底问了什么、模型最后说了什么」够了；但**不能**用它做完整的 prompt 回归。
需要完整 prompt 时，应单独加一个调试开关，而不是把它变成常态日志。

### 3.4 token、首 token 延迟与成本

- **token**：取 `ChatResponse.metadata().tokenUsage()` 的 input/output/total；provider 没给时写 `NULL`
  （0 表示「没给」会误导）。
- **首 token 延迟**：`streamOnce` 里记录第一个非空 `onPartialResponse` 距调用开始的毫秒数。
  **只有流式且模型真的输出了文本才有值**——一轮只返回 tool_call 的响应没有 delta，`firstTokenMs` 为 `NULL`。
- **成本**：
  ```
  costYuan = promptTokens/1000 × inputPricePer1kYuan + completionTokens/1000 × outputPricePer1kYuan
  ```
  用 `BigDecimal`，保留 6 位小数。**两个单价都为 0 时写 `NULL`**，不写 0。
  ⚠️ 单价默认未配置；不同模型、缓存命中、思考 token 的计费方式不同，这个值**只能看趋势，不能当账单**。

配置（`application.yml`）：

```yaml
ai:
  chat:
    provider: deepseek        # 仅写日志，不参与调用
  observability:
    enabled: true
    input-price-per-1k-yuan: 0
    output-price-per-1k-yuan: 0
    max-snapshot-chars: 8000
```

### 3.5 查询接口

#### `GET /api/tools/logs`

| 参数 | 说明 |
|---|---|
| `runId` | 可选，只看某次运行 |
| `toolName` | 可选，按工具筛选 |
| `success` | 可选，`true`/`false` |
| `current` / `pageSize` | 分页，`pageSize` 上限 100 |

返回 `IPage<ToolLogVO>`（`records` / `total` / `size` / `current` / `pages`）。
`arguments` / `result` 是解析后的对象；非 JSON 文本包成 `{"text": ...}`；`replayed=true` 标注「结果来自重放」。

#### `GET /api/tools/logs/summary`

| 参数 | 说明 |
|---|---|
| `runId` | 可选；不传则汇总当前用户全部调用 |

返回 `CallSummaryVO`：调用次数、输入/输出/总 token、平均耗时、平均首 token、成本、工具调用数、
工具失败数、重放次数。**计数字段是字符串**（全局 Long→String 约定），`avg*` 是数字，`costYuan` 是字符串或 `null`。

### 3.6 失败隔离

`ObservabilityServiceImpl` 的两个写方法**不在事务里**，并包住所有异常：

```java
try {
    aiCallLogMapper.insert(row);
} catch (Exception e) {
    log.warn("写 ai_call_log 失败（不影响运行）: runId={}", c.runId(), e.getMessage());
}
```

理由：可观测性是**旁路**。数据库抖动、表被锁、字段超长，都不应该让用户的那次回答失败。
代价是「日志可能悄悄丢一条」——所以 warn 日志里保留 runId，必要时能发现。

## ④ 数据结构与示例

### 4.1 一次「调工具再回答」的日志链（实测 run 8）

```
ai_call_log:
  #1  CHAT deepseek/deepseek-flash  prompt=572  completion=35   total=607   firstToken=NULL  elapsed=1200ms
  #2  CHAT deepseek/deepseek-flash  prompt=643  completion=28   total=671   firstToken=506ms elapsed=600ms

ai_tool_log:
  #1  getCurrentTime source=LOCAL sideEffect=0 success=1 elapsed=3ms replayed=0
```

第 1 次调用只返回了 tool_call，没有文本 delta，所以 `firstTokenMs=NULL`；第 2 次生成最终回答，
首 token 506ms。**总耗时 600ms 和首 token 506ms 是两回事**，后者才接近用户感受。

### 4.2 中断拒绝后续跑（实测 run 9）

```
ai_tool_log:
  #1  createTicket INTERNAL sideEffect=1 success=0 replayed=1 elapsed=0
      resultJson="用户拒绝执行该操作，操作未执行。原因：..."
  #2  searchKnowledge LOCAL_QUERY sideEffect=0 success=1 replayed=0 elapsed=3ms

summary(runId=9):
  callCount=3, promptTokens=2283, completionTokens=705, totalTokens=2988,
  toolCallCount=2, toolFailures=1, replayedCount=1
```

`replayed=1` 就是「这个结果是从断点直接读出来的，没有重新执行」的直接证据；
`toolFailures=1` 来自被拒绝的工单步骤。

### 4.3 常用 SQL

```sql
-- 某个运行的成本与耗时
SELECT scene, COUNT(*) calls, SUM(totalTokens) tokens, SUM(costYuan) cost,
       AVG(firstTokenMs) avg_ttft, AVG(elapsedMs) avg_elapsed
FROM ai_call_log WHERE runId = 9 GROUP BY scene;

-- 某用户最近的工具调用（含重放）
SELECT id, runId, toolName, success, replayed, elapsedMs, createTime
FROM ai_tool_log WHERE userId = 1 ORDER BY id DESC LIMIT 50;

-- 找出被重放过的副作用操作（检查「没有重复执行」）
SELECT * FROM ai_tool_log WHERE replayed = 1 AND sideEffect = 1;
```

## ⑤ 边界、已知限制、坑

### 没做什么

| 没做 | 影响 | 备注 |
|---|---|---|
| **异步写日志** | 写库耗时计入运行（通常 1~2ms） | 当前同步写、失败隔离；量级上来后可改队列/批量 |
| **日志归档与分区** | 两张表会持续增长 | 生产需要按日期分区或 TTL |
| **敏感信息脱敏** | `lastUserMessage`、工具参数/结果可能含手机号/身份证 | 如果知识库会装用户资料，**必须先做脱敏**（模块清单已列为后置项） |
| **完整 prompt 快照** | 无法用日志直接复现一次完整请求 | 需要时加独立调试开关 |
| **OpenTelemetry / traceId** | 跨服务追踪缺失 | `runId` 是当前唯一的关联键 |
| **`messageId`** | `ai_call_log.messageId` 恒为 NULL | 一次 LLM 调用与最终助手消息不是一一对应，暂不填 |
| **LLM 调用列表接口** | 只能通过 SQL 或 summary 看明细 | 前端目前只需要工具日志；需要时再加 `GET /observability/calls` |

### 坑 1：日志写入不能进主事务

如果把 `ai_call_log` 的 INSERT 和 `agent_step` 的更新放进同一个事务，日志失败会让状态回滚；
更糟的是，事务里还夹着模型/工具调用（[12](12-中断与恢复的状态机.md) 坑 1）。所以写日志**永远是独立语句**，
并且异常必须吞掉。

### 坑 2：`firstTokenMs` 不是「模型开始响应」的时间

它是**第一个非空文本 delta** 的时间。模型先思考、再决定调工具时，可能整整一轮都没有 delta——
这时 `firstTokenMs` 为 NULL 是**正确**的，不要为了「有值」去伪造 0。

### 坑 3：续跑的 token 会重复计入（符合预期）

被中断的那次 LLM 调用确实生成了文本、确实花了钱；续跑会重新生成一轮，也会再花一次钱。
同一个 run 出现多条 `CHAT` 日志是预期行为，不是重复计数 bug（[12](12-中断与恢复的状态机.md) 坑 7）。

### 坑 4：成本默认是 NULL，不是 0

价格未配置时写 `NULL`。前端如果直接 `Number(costYuan ?? 0)` 会把「未知」显示成「免费」——
正确做法是显示「未配置单价」。

### 坑 5：日志表也会被大字段撑大

即使截断到 8000 字符，检索上下文类工具的结果仍然很大。`max-snapshot-chars` 要结合
`ai.agent.max-tool-result-chars` 一起看；长期运行前先定好归档策略。

## ⑥ M12 落地记录（2026-10-20）

**做了什么**

- 建表：`sql/observability_tables.sql`（`ai_call_log` / `ai_tool_log`）。
- 实体/Mapper：`AiCallLog`、`AiToolLog`、`AiCallLogMapper`、`AiToolLogMapper`。
- 服务：`ObservabilityService` + `ObservabilityServiceImpl`（写日志、成本、查询、汇总；异常隔离）。
- 接入：
  - `AgentRunner.drive` 每次 LLM 调用写 `ai_call_log`（成功/失败两条路径），并记录首 token 延迟；
  - `AgentRunner.executeAndRecord` 写工具真实执行日志；撞键重放写 `replayed=1`；
  - `AgentRunServiceImpl.logReplayedSteps` 在续跑/审批时写 `ResumePlanner` 重放的日志。
- 配置：`ai.observability.*`、`ai.chat.provider`；新增 `CostCalculator`。
- 接口：`GET /tools/logs`、`GET /tools/logs/summary`。
- 前端契约：`frontend/60` 补齐两个接口；`frontend/00` 状态更新。

**验证**

- 单测 129 个全过（新增 `CostCalculatorTest` 4 个、`ObservabilityServiceImplTest` 6 个、
  `AgentRunnerTest` 1 个可观测性接线用例）。
- 真服务（8102 + DeepSeek + MySQL）：
  - run 8：2 条 `ai_call_log`（607 / 671 token，第二条首 token 506ms），1 条 `ai_tool_log`
    （`getCurrentTime`，`source=LOCAL`，`replayed=0`）；`/tools/logs` 与 `/summary` 返回正确。
  - run 9：拒绝后续跑，`ai_tool_log` 出现 `createTicket replayed=1 success=0`，
    summary 的 `toolFailures=1`、`replayedCount=1`。
  - 价格未配置时 `costYuan=NULL`；按用户/运行过滤、`success=false` 过滤均正常。

**仍未做**：日志归档/分区、脱敏、异步写入、完整 prompt 快照、LLM 调用明细接口（见 ⑤）。
