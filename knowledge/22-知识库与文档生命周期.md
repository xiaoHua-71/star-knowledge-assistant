# 知识库与文档生命周期

> 本篇讲「一份文件从上传到变成可检索的向量，中间经历什么、状态怎么流转、失败怎么办」。
> 模型层面的向量化/重排见 [21](21-本地Embedding与Rerank.md)；检索怎么用这些向量见 [23](23-混合检索与融合.md)。
> 表结构 DDL 在 [10-数据模型总览](10-数据模型总览.md)，本篇只列字段含义。

## ① 这个模块治的是哪类病（通用问题定义）

### 问题定义

一份文档要能被检索，必须先经过一条**多步骤、跨两个存储、可能失败**的流水线：

```
原始文件 → 解析成文本 → 切成片段 → 向量化 → 写向量库
```

这条流水线的本质难点**不是算法**（每一步都有现成工具），而是**状态管理**：

- 它是**多步**的，可能在第 3 步失败，这时前 2 步的产物怎么办？
- 它**跨两个存储**（业务库 + 向量库），一边成功一边失败时，系统处在什么状态？
- 它**耗时长**（一篇 PDF 可能几秒到几十秒），不能阻塞调用方，也不能让用户干等。
- 它**可重入**：同一份文档可能被重传、被重建、被删除重来。

所以这个模块要解决的本质问题是：**给一条跨存储的多步流水线定义一套可重入、可重试、可观测的状态机**。

### 边界

| 归它管 | 不归它管 |
|---|---|
| 文档/切片/知识库的**状态流转** | 文本 ↔ 向量怎么算（那是 [21](21-本地Embedding与Rerank.md)） |
| 双写的**顺序与一致性** | 召回多少条、怎么融合（那是 [23](23-混合检索与融合.md)） |
| 解析、切片的**编排** | 改了之后怎么最小代价重建（那是 [24](24-增量索引.md)） |
| 上传落盘、删除清理 | 权限/配额（后置） |

### 五类典型失败模式

1. **半途失败留下悬空状态。** 切片写了、向量没写；或反过来。删文档时更危险：向量还在、切片行没了 → 检索召回一段「查不到出处的文本」。
2. **双写顺序反了。** 「先删 MySQL 再删向量」会导致中间失败窗口里向量指向已删内容。
3. **重复上传同一份内容。** 存两遍浪费空间，还可能让检索结果里同一段出现两次。
4. **切片参数漂移。** 改了 `chunkSize` 只对新文档生效，库里新旧两种粒度混在一起，检索质量无从判断。
5. **中文切片把语义切碎。** 分层切片器在中文上会因为「没有空格」而整段当一个词，甚至直接抛异常（坑 1）。

## ② LangChain4j 官方怎么做

官方提供入库链路的**组件**，文档：<https://docs.langchain4j.dev/tutorials/rag>（本项目 1.20.0 / 1.20.0-beta30）。

| 职责 | 官方类 | 提供的 | 不提供的 |
|---|---|---|---|
| 加载 | `DocumentLoader` / `FileSystemDocumentLoader` | 来源 → 字节流 | 落盘策略、原始文件管理 |
| 解析 | `DocumentParser` / `ApachePdfBoxDocumentParser` / `ApachePoiDocumentParser` | 字节流 → `Document`（纯文本） | TXT/MD/HTML 解析（**没有对应模块**） |
| 切片 | `DocumentSplitter` / `DocumentSplitters.recursive` 及 `DocumentBy{...}Splitter` | `Document` → `List<TextSegment>` | 中文适配（见坑 1、坑 2） |
| 向量化 | `EmbeddingModel` | 文本 → `Embedding` | — |
| 入库 | `EmbeddingStore.addAll/add/removeAll` | 写/删向量 | 与业务库的事务/一致性 |
| 编排 | `EmbeddingStoreIngestor` | 把「切片+向量化+入库」串成一个 `ingest()` | **任何状态管理** |

**官方明确不做生命周期管理**：没有「文档状态」概念，没有失败重试，没有「删文档时清向量」的编排。`ingest()` 是「给一个 Document、我尽力入库」，失败就抛异常，调用方自己收拾。所以这一层必须自研。

> 注意：`langchain4j-document-parser-apache-pdfbox` / `-apache-poi` 的 core 依赖在 **1.20.0 才对齐**（1.4.0 时不对齐，salary-leap 因此放弃了 parser 退回 jsoup）。这也是本项目升级 LC4j 的收益之一。

## ③ 本项目为什么这么落地

### 用哪些官方的，自研哪些

| 环节 | 用官方 | 自研 |
|---|---|---|
| PDF / Office 解析 | `ApachePdfBoxDocumentParser` / `ApachePoiDocumentParser` | |
| TXT / MD / HTML | | 直读 UTF-8 / jsoup 去标签（`ai/DocumentParserFactory`） |
| 分层切片 | 官方的 `DocumentBy{Paragraph,Line,Word,Character,Regex}Splitter` | **拼链与末级选择**（`ai/ChunkSplitterFactory`，见坑 1、2） |
| 向量化 | `BgeSmallZhV15QuantizedEmbeddingModel`（经 `ai/EmbeddingEngine`） | query 前缀、模型/维度校验 |
| 向量写入 | `MilvusEmbeddingStore.addAll/removeAll`（经 `ai/MilvusStoreFactory`） | |
| **状态机** | | ✅ 全部（`KbIndexServiceImpl`） |
| **双写顺序** | | ✅ |
| **异步执行** | | ✅ 专用线程池 |

### 为什么自研状态机，而不用 `EmbeddingStoreIngestor`

三个理由，按重要性：

1. **要落状态**。每步之间要写 `knowledge_document.status`，`EmbeddingStoreIngestor` 没有插入点。
2. **要写两个库**。切片行进 MySQL、向量进 Milvus，顺序不能乱；ingestor 只认一个 `EmbeddingStore`。
3. **要能停在中途重试**。失败要停在「可重试」的状态（如 `PENDING`），而不是抛个异常了事。

### 为什么异步

上传/重建是**秒级**操作。同步做会让 HTTP 请求挂住、前端转圈、超时重试还可能触发重复索引。

所以接口**立刻返回**（文档 `status=PENDING`），真正的解析/向量化交给 `config/KbExecutorConfig` 里的专用线程池（`kbIndexExecutor`）。前端轮询 `GET /kb/{id}/status` 看进度。

> 用**手动提交**（`executor.execute(...)`）而不是 `@Async`：`@Async` 要求调用穿过 Spring 代理，
> 类内部自调用会静默失效。手动提交没有这个坑，也更容易在测试里同步执行。

### 为什么进度「从数据库派生」而不是单独记

`KbBuildStatusVO` 的 `total / processed / failedCount / currentDocName` 全部是**按文档状态现算的**（`refreshKbStatus` / `buildStatus`）：

- `total` = 库内文档数
- `processed` = `INDEXED` 的文档数
- `failedCount` = `FAILED` 的文档数
- `currentDocName` = 正在进行的那一篇

好处：**无状态、不会漂移**（不存就不存在「进度记错了」）。代价：每次轮询查一次库——轮询间隔 2 秒，可接受。

## ④ 数据结构与流程时序

### 四张表（字段含义，DDL 见 [10](10-数据模型总览.md)）

| 表 | 关键字段 | 作用 |
|---|---|---|
| `knowledge_base` | `embeddingModel` / `dimension` / `collectionName` / `chunkSize` / `chunkOverlap` / `status` / `docCount` / `chunkCount` | 检索的独立单元；记模型与维度防错配；记切片参数判「是否需要重建」 |
| `knowledge_category` | `parentId` / `level` / `sortOrder` | 分类树（≤3 层） |
| `knowledge_document` | `filePath` / `sourceUrl` / `contentHash` / `charCount` / `chunkCount` / `status` / `errorMsg` | 状态机主体；`contentHash` 是增量索引的支点 |
| `knowledge_chunk` | `docId` / `chunkIndex` / `vectorId` / `content` / `charCount` | 检索最小单位；`vectorId` 同时是 Milvus 主键 |

**`knowledge_base.collectionName` 规则**：`star_kb_{id}`，每个知识库一个 Milvus 集合。为什么每库一集合而不是共用一个：删库/重建时可以直接 drop 整个集合，不用按 `vectorId` 逐条删；也天然隔离了不同库的向量。

### 状态流转

```
                    ┌─────────┐
   上传/重建 ──────► │ PENDING │
                    └────┬────┘
                         ▼
                    ┌─────────┐
                    │ PARSING │  解析成文本
                    └────┬────┘
                         ▼
                    ┌─────────┐
                    │ PARSED  │  拿到正文、算 contentHash/charCount
                    └────┬────┘
                         ▼
                    ┌─────────┐
                    │INDEXING │  切片 + 写 MySQL 切片行 + 写 Milvus 向量
                    └────┬────┘
                         ▼
                    ┌─────────┐        ┌────────┐
                    │ INDEXED │        │ FAILED │◄── 任一步异常（写 errorMsg）
                    └─────────┘        └────────┘

   删除：任意状态 ──► DELETING ──► （删向量 → 删切片行 → 删文档行）
```

- `DELETING` 是**可重试的中间态**，不是终态。卡在它说明「减操作」没做完。
- 知识库的 `status`（`EMPTY/BUILDING/READY/FAILED`）是**文档状态的汇总**：无文档→EMPTY；有文档在 `PENDING/PARSING/PARSED/INDEXING`→BUILDING；全部终态且至少一篇 INDEXED→READY；其余→FAILED。

### 上传流程（编号）

```
1. 校验知识库属于当前用户
2. 校验文件（非空、≤10MB、后缀在 PDF/DOCX/TXT/MD/HTML 内）
3. 落盘到 {storage-dir}/{kbId}/{uuid}.{ext}   ← 不用原始文件名（路径穿越/编码坑）
4. 插 knowledge_document (status=PENDING, filePath=…, userId=…)
5. 提交异步任务 → 立刻返回 VO(status=PENDING)
   ── 异步里 ──
6. status=PARSING → 按 fileType 选解析器 → 拿到正文
   正文为空 → FAILED（可能是扫描件 PDF）
7. 算 contentHash=MD5(正文)、charCount；status=PARSED
8. 用 knowledge_base 的 chunkSize/chunkOverlap 切片
9. 清掉这篇文档可能存在的旧切片/旧向量（重复索引时）
   status=INDEXING
10. 写 knowledge_chunk 行（MySQL 先）
11. 向量化 → store.addAll(ids, embeddings, segments)（Milvus 后）
12. status=INDEXED, chunkCount=N
13. refreshKbStatus(kbId)
```

### 删除流程（顺序不能反）

```
1. status=DELETING
2. 删 Milvus 向量      ← 先删「会被召回的东西」
3. 删 knowledge_chunk 行
4. 逻辑删 knowledge_document 行
5. 删原始文件
```

**为什么先删向量**：检索是从 Milvus 出发的。如果先删了 MySQL 切片行、向量还在，检索会召回一段「MySQL 里查不到的文本」——轻则答非所问，重则把已删的敏感内容答出来。反过来（向量没了、切片行还在）只是少召回几条，安全。所以：

> **新增时「先写 MySQL 再写 Milvus」；删除时「先删 Milvus 再删 MySQL」。**
> 一句话：**让失败窗口停在「多了」而不是「少了」。**

第 2 步失败会**直接抛异常**，不往下走——文档停在 `DELETING`，可重试；这正是 `DELETING` 这个中间态存在的意义。

### 确定性 vectorId

```java
vectorId = UUID.nameUUIDFromBytes((docId + "#" + chunkIndex + "#" + MD5(content)).getBytes()).toString()
```

- 同一「文档 + 位置 + 内容」永远得到**同一个 36 位 id**，于是 Milvus 里是**幂等覆盖**而不是「删旧插新」。
- 36 字符正好放进 Milvus 那个 `VarChar(36)` 的主键字段（`CollectionOperationsExecutor.createCollection` 里写死的）。
- 内容变了 id 就变（内容进了种子）。这是增量判断的基础，详见 [24](24-增量索引.md)。

## ⑤ 边界、已知限制、踩过的坑

### 坑 1：官方的分段链遇到「无标点长中文」会抛异常

**现象**：`DocumentSplitters.recursive(400, 80)` 切一段没有标点的中文（比如一整段 3000 字的连续文字）时抛：

```
RuntimeException: The text "……" (3000 characters long) doesn't fit into the maximum segment size
(400 characters), and there is no subSplitter defined to split it further.
```

**原因**：官方那条链的末级是 `DocumentByWordSplitter`——「词」是**按空白切**的。中文没有空格，整段被当成**一个词**；这个词超过 400 字时，word 拆分器发现自己的 `subSplitter == null`（`HierarchicalDocumentSplitter.split` 里显式抛的），于是报错。

**规避**：不用 `DocumentSplitters.recursive`，手动拼链，在 word 之后接一个 `DocumentByCharacterSplitter` 兜底（`ai/ChunkSplitterFactory`）：中文长串最终按字符切，再离谱的输入也不抛异常。
守住它的测试：`ChunkSplitterTest.无标点无空格的中文长串不会抛异常且不超上限`。

### 坑 2：中文场景 `chunkOverlap` 实际不生效（框架限制）

**现象**：设了 `chunkOverlap=80`，但中文文档切出来的各片直接首尾相接，**没有任何重叠**。

**原因**：重叠区由 `HierarchicalDocumentSplitter.overlapFrom()` 计算，而它**写死了用 OpenNLP 的英文断句模型**：

```java
private HierarchicalDocumentSplitter getOverlapSentenceSplitter() {
    // 注意：这里是硬编码，子类改不了
    return new DocumentBySentenceSplitter(1, 0, null, null);
}
```

`DocumentBySentenceSplitter` 内部是 `SentenceDetectorME`（英文模型），对中文「。」基本不切 → 取不到整句 → 重叠为空。**换任何 splitter 子类都绕不过**，因为是基类里写死的。

**当前处理**：接受它，并**把句子级换成了中文标点正则**（`DocumentByRegexSplitter`，见下），让切片至少在句末标点处切开（而不是把句子从中间劈断）——这是能改善召回质量的部分；重叠那部分留待 M3 用评测集量化后再决定是否自研。

**守住它的测试**：`ChunkSplitterTest.中文下重叠暂不生效_总长度等于原文`——如果哪天这条断言失败（总长 > 原文），说明重叠生效了，回来更新本节。

> **顺带：中文句子边界为什么要单独处理。** 官方句级用英文断句模型，中文不切，等于中文文档「没有句子」，会被一路降级到按字符硬切。所以本项目把句级换成 `DocumentByRegexSplitter("(?<=[。！？!?；;])", "", ...)`，在中文句末标点后切开。<br>
> 完整的链是：**段落 → 行 → 句（中文正则）→ 词 → 字符（兜底）**。

### 坑 3：`collectionName` 要两次写入

**现象**：`knowledge_base.collectionName` 规则是 `star_kb_{id}`，但 `id` 是自增的，**插入前拿不到**；而 `collectionName` 是 `NOT NULL`。

**处理**：同一事务里先插入（用一个临时唯一串占位，如 `tmp_{uuid}`），拿到 `id` 后 `updateById` 改成 `star_kb_{id}`（`KnowledgeBaseServiceImpl.create`）。事务保证中途崩溃不会留下占位串。

**为什么不在建库时就建 Milvus 集合**：建库是轻量操作（前端体验要求「点一下就建好」），而连接 Milvus/建集合是重操作。集合**延迟到第一个文档入库时才建**（`MilvusEmbeddingStore` 构造时会自动建）。

### 坑 4：`tokenCount` 目前是空的（待验证）

`knowledge_chunk.tokenCount` 现在**留空**。原因是 bge 的 tokenizer 没有向上层暴露（`OnnxBertBiEncoder` 内部算了 token 数，但 `EmbeddingModel` 接口不返回），拿不到「实测」值。

按文档纪律，这里**不编数字**：留空，标 `待验证`。验证方法：后续接入一个能复用 bge tokenizer 的实现，对 `knowledge_chunk` 全表回填并统计分布。当前只保证 `charCount` 准确。

### 坑 5：`chunkSize = 400` 与模型 512 token 上限的关系（待验证）

`knowledge_base.chunkSize` 默认 **400 字符**。但 bge-small-zh 建议单段 **≤ 512 token**，而中文里「字符」和「token」不是一回事（一个汉字 1~2 个 token）。400 汉字**有可能超过 512 token**。

这是个**猜测值**，不是结论（与 [21](21-本地Embedding与Rerank.md) 坑 5 同源）。验证同样依赖坑 4 的实测 `tokenCount`：统计真实分布，确认没有大量切片超 512。

### 没做的

| 没做 | 影响 | 备注 |
|---|---|---|
| **增量索引** | `full=false` 当前也按全量重切 | M3，见 [24](24-增量索引.md) |
| **对账任务** | 双写漂移只能靠检索时的 warn 发现 | 表字段已备好（`vectorId` 唯一键、`contentHash`），M11 |
| **解析后清洗** | PDF 的页眉页脚、页码噪声原样进切片 | 影响召回质量，待评测确认是否值得做 |
| **文档预览 / 查看切片列表** | 前端看不到「它把文档切成了什么」 | 接口待定，见 [frontend/50](../frontend/50-knowledge-知识库管理.md) |
| **同库内容去重** | 同一份内容传两遍会存两遍（`contentHash` 已存，但没做拦截） | 后置 |
| **单文件多文档 / 容量上限** | 一次一个文件；文档数、切片数无上限 | 后置 |
| **`docCount`/`chunkCount` 漂移自愈** | 是冗余计数，靠每次操作同步维护 | 对账可修 |
