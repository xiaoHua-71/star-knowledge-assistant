# 中断与恢复的状态机

> 这是本项目**最难、也最危险**的一个模块。难在状态设计，危险在「恢复时重复执行副作用」——那是会真实造成业务损失的事故，不是体验问题。
>
> 建议先读 [10-数据模型总览](10-数据模型总览.md) 里 `agent_run` / `agent_step` / `agent_todo` 三张表，再回来看本文。

## ① 这个模块治的是哪类病（通用问题定义）

**一个执行时间以「秒」甚至「分钟」计的 AI 任务，怎么才能停得下来、并且之后接着跑？**

拆开看，这里其实混着三个**互相独立**的问题，很多实现把它们搅在一起，于是一团乱：

| # | 子问题 | 两种极端选择 |
|---|---|---|
| 1 | **在哪个粒度上停** | 停在「安全点」（回合之间，状态干净）↔ 停在任意点（连半个 token 生成到一半都要能续） |
| 2 | **恢复时怎么对待已经执行过的动作** | 全部重放（要求动作幂等，或者能重放结果）↔ 全部跳过（要求能精确知道执行到哪） |
| 3 | **谁来决定恢复** | 用户显式点「继续」↔ 系统自动恢复（用户无感） |

本项目的选择在第三节，但先讲清楚**为什么这三个问题必须分开想**：

> 「我要能随时中断」——如果理解成「任意点都能停」，那就必须处理「半个 token 怎么办」「HTTP 请求发出去一半怎么办」，复杂度暴涨。但如果理解成「停在安全点，但用户点停止时立刻停止输出」，用户感受到的体验完全一样（字立刻不蹦了），复杂度却低一个数量级。

**这个取舍是本模块最重要的一步**：把「用户感知的即时性」和「状态的一致性」解耦——**停止输出是即时的，状态收敛发生在下一个安全点**。

### 它的边界

| 归它管 | 不归它管 |
|---|---|
| 运行状态的持久化与流转 | 事件怎么推给前端（那是 [31-流式输出SSE](31-流式输出SSE.md)） |
| 中断检测、安全点、挂起 | 连接断开后的补发（那是「重连」，见第五节坑 4） |
| 恢复时决定哪些步骤重放、哪些重跑 | 单步内部的执行细节（那是 [30-工具调用](30-工具调用.md)） |
| 幂等键的生成与唯一性约束 | 后端接口本身是否幂等（那是接口提供方的责任） |

### 四类典型失败模式

按危害从大到小：

| # | 失败模式 | 后果 |
|---|---|---|
| 1 | **恢复时重复执行了副作用动作** | 重复下单、重复发消息、重复扣款。**这是唯一会造成真实损失的一类** |
| 2 | **状态丢失** | 运行卡在「进行中」永远不结束，或者从头重跑（浪费成本，且可能重复副作用） |
| 3 | **僵尸运行** | 进程崩溃后运行记录永远是 `RUNNING`，前端永远转圈 |
| 4 | **恢复后行为与未中断的不一致** | 同样的输入，中断再续跑得到的回答和一次跑完的不一样。这类问题最难发现，因为它**不报错** |

**第 4 类值得特别说明**：它是「正确性」问题而不是「稳定性」问题。一个恢复功能哪怕 100% 不丢状态、不重复执行，只要恢复后的推理路径变了，用户就会觉得「这 Agent 怎么忽好忽坏」。所以验证方式不是「跑通就行」，而是**对比**：同一组输入，跑两遍（一遍不中断、一遍中途中断再续跑），断言两次的结果一致。

## ② LangChain4j 官方怎么做

### 本项目用的版本：**没有 Agent 这个概念**

`langchain4j-core:1.4.0` 里**没有**任何 agent / agentic / 挂起 / 恢复 / checkpoint 相关的类。（可以在本地 sources jar 里搜 `Agentic`、`Suspend`、`Resume`、`HumanInTheLoop`，一个都没有。）

1.4.0 能提供的**最接近**的东西是：

- `AiServices` + `@Tool`：让模型能调用工具，但**循环是内存里的**（`DefaultAiServices` 内部跑完就返回），没有中间状态，进程一挂全丢
- `maxToolCallingRoundTrips` / `maxSequentialToolsInvocations`：限制循环轮次（这是我们需要的「轮次护栏」，可以直接参考它的思路）

所以：**在 1.4.0 上做中断恢复，循环必须自己写，状态必须自己存。这不是我们「选择自研」，是框架在这个版本上确实没有。**

### 官方后来的做法（供参考，本项目不用）

LangChain4j 后来出了独立的 **`dev.langchain4j:langchain4j-agentic`** 模块（**beta**，且**不在 `langchain4j-bom` 里**，必须单独指定版本）。它确实支持挂起/恢复：

| 类 / 机制 | 作用 |
|---|---|
| `@Agent` + `outputKey` | 声明一个 Agent 及其输出写入共享作用域的哪个键 |
| `AgenticServices` | `agentBuilder()` / `sequenceBuilder()` / `loopBuilder()` / `supervisorBuilder()` / `plannerBuilder()` 等 |
| `AgenticScope` | 共享状态（相当于我们说的「运行上下文」），带 `writeState(...)` |
| `HumanInTheLoop` | 包一个 `responseProvider`，返回 `PendingResponse` 时运行**停住** |
| `AgenticScopeStore` | checkpoint 的 SPI，把 `AgenticScope` 存起来 |
| `AgenticSystemSuspendedException` | 挂起时抛出，**释放线程** |
| `AgenticScope.completePendingResponse(...)` | 恢复时补上那个待定的响应 |
| `ResultWithAgenticScope.suspended()` | 带状态的返回值包装 |

官方文档还说了一句很重要的话：**必须把 `AgenticScope` 的 checkpoint 和业务写入放在同一个存储/事务里，否则崩溃会导致副作用被重复执行。** —— 这正是本模块的核心难点，官方解决方案是「用同一个 store」，而我们的「业务写入」是 MySQL，所以答案很自然就是**把状态也存 MySQL**（见第三节）。

**不用的理由**（三条，按权重）：

1. **版本锁定风险**：它是 beta，且不在 BOM 里；要升级就得把整条 LangChain4j 版本线一起动。而本项目已经因为离线仓库的限制，把版本对齐在 `core 1.4.0 + 集成 1.4.0-beta10` 这个组合上。
2. **核心机制我们本来就要自己做**：官方的 `AgenticScopeStore` 解决的是「把状态存哪」，而我们的状态里有业务语义（待确认的工具、幂等键、计划版本），必须落自己的表，不可能塞进框架的通用作用域。**最终还是要写这些表**，那用框架只省了一层壳。
3. **可调试性**：状态机是排查 Agent 行为的主要依据。自己写的状态机能直接在 SQL 里查、能画状态图、能被测试覆盖；框架内部的作用域出问题时，能拿到的东西少得多。

**结论：用官方的 `AiServices` + `@Tool` 作为「单步执行器」，把编排和状态管理全部自研。**

## ③ 本项目怎么落地

### 三个子问题的答案

| # | 子问题 | 本项目的选择 | 理由 |
|---|---|---|---|
| 1 | 停在哪个粒度 | **安全点**（每轮 LLM 调用前、每个工具执行前），但**用户点停止时立刻停输出** | 把「即时性」给体验，「一致性」给状态机。见下面的安全点说明 |
| 2 | 恢复时怎么对待已执行的动作 | **优先重放结果，其次重跑，最危险的情况转人工确认** | 见第五节的幂等键与三分支处理 |
| 3 | 谁决定恢复 | **用户显式点「继续」**（暂不做自动恢复） | 自动恢复需要判断「什么时候该恢复」，而这个判断很容易做错（比如用户其实已经不想继续了） |

### 状态枚举与流转

```
                     ┌─────────┐
        创建run ────► │ PENDING │
                     └────┬────┘
                          │ 开始执行
                          ▼
                     ┌─────────┐  用户点停止 / 用户发新消息 / 进程重启
                     │ RUNNING │──────────────────────────────┐
                     └──┬───┬──┘                              │
        需人工确认的      │   │ 正常结束                        │
        副作用工具        │   ▼                                ▼
             │      ┌─────────┐                        ┌───────────┐
             └─────►│ WAITING_│                         │ SUSPENDED │
                    │ APPROVAL│                         └──┬─────┬──┘
                    └──┬───┬──┘                            │     │
              同意 ────┘   └──── 拒绝                     │     │ 用户放弃
                 │              │                         │     ▼
                 │              └──────────┐              │  ┌───────────┐
                 │                         ▼              │  │ CANCELLED │
                 │                    ┌───────────┐       │  └───────────┘
                 │                    │ SUSPENDED │       │
                 │                    └───────────┘       │
                 └────────────────► RUNNING ◄─────────────┘ 用户点继续
                                       │
                          不可恢复错误  │
                                       ▼
                                  ┌────────┐
                                  │ FAILED │
                                  └────────┘
```

状态与事件对照表：

| 当前状态 | 事件 | 新状态 | `interruptType` |
|---|---|---|---|
| `PENDING` | 开始执行 | `RUNNING` | — |
| `RUNNING` | 正常产出最终回答 | `COMPLETED` | — |
| `RUNNING` | 用户点「停止」 | `SUSPENDED` | `USER_STOP` |
| `RUNNING` | 本轮运行中用户又发了新消息 | `SUSPENDED` | `NEW_MESSAGE` |
| `RUNNING` | 进程重启（由启动扫描设置） | `SUSPENDED` | `SERVER_RESTART` |
| `RUNNING` | 撞到需确认的副作用工具 | `WAITING_APPROVAL` | `APPROVAL_REQUIRED` |
| `RUNNING` | 不可恢复的错误（参数错、权限错） | `FAILED` | — |
| `SUSPENDED` | 用户点「继续」 | `RUNNING` | 清空 |
| `SUSPENDED` | 用户放弃 | `CANCELLED` | — |
| `WAITING_APPROVAL` | 用户同意 | `RUNNING` | 清空 |
| `WAITING_APPROVAL` | 用户拒绝 | `SUSPENDED` | 由用户决定后续 |
| 任意非终态 | 超过保留期（如 24h） | `CANCELLED` | 定时任务 |

**终态**：`COMPLETED` / `FAILED` / `CANCELLED`。进入终态后不再改变。

### 中断来源与检测方式

| 来源 | 怎么触发 | 检测方式 |
|---|---|---|
| 用户点停止 | `POST /agent/run/{id}/interrupt` | 写 Redis 标志 |
| 用户在运行中又发消息 | 发消息的接口里顺手置标志 | 写 Redis 标志 |
| 服务重启 | 无法提前通知 | 启动时扫描非终态运行 |
| 副作用工具需确认 | 工具契约里的 `requireApproval` | 不写标志，直接转 `WAITING_APPROVAL` |

**中断标志存 Redis**：key 形如 `agent:interrupt:{runId}`，**必须显式删除**（不设 TTL，避免「用户点了停止，标志却过期了」）。

*为什么不用 MySQL 字段*：中断标志在每个安全点都要读一次（频率高），而且它**不需要持久性**——丢了最坏的结果是多跑一轮，用户再点一次就行。用 Redis 读，比每轮查一次数据库便宜得多。

*为什么不用内存 Map*：当前是单实例，内存 Map 也能工作。但 SSE 重连、将来多实例部署、以及「点了停止的请求和跑着的运行不在同一个实例」这三种情况都会让它失效。Redis 顺手就解决了，成本几乎为零。

**中断是「协作式」的**：不打断正在执行的线程，而是由状态机在每个安全点**主动检查**标志。

```
为什么不用 Thread.interrupt()？
    1. LLM 调用是阻塞 IO，interrupt 不一定能让 HTTP 客户端干净退出
    2. 挂起的动作本身要写数据库（把 run 置 SUSPENDED），
       如果线程被 interrupt 打断，这次写库可能失败 → 运行状态不一致
    3. 协作式的中断点位置明确，出问题时容易推断「它停在哪了」
```

### 安全点：只有两处

```
┌────────────────────────────────────────────────────┐
│  while (stepNo < maxRounds) {                       │
│      ← 安全点 1：检查中断标志                        │
│      ├─ 命中 → 置 SUSPENDED，退出循环（正常 return）   │
│                                                     │
│      LLM 调用（可能流式，几十秒）                     │
│      ├─ 用户此时点停止 → 立刻停止推流（但代码继续往下走）│
│                                                     │
│      模型要求调工具？                                 │
│        ├─ 有： ← 安全点 2：检查中断标志                │
│        │        命中 → 在「工具执行前」挂起            │
│        │        未命中 → 落库意图行 → 执行工具 → 回填   │
│        └─ 无： 生成最终回答，退出循环 → COMPLETED      │
│  }                                                  │
└────────────────────────────────────────────────────┘
```

**为什么工具执行中间没有安全点？** 因为工具是一个 HTTP 调用，**要么没发出去，要么已经发出去了**，中间没有一个「可以干净停下」的时刻。硬要在中间停，就会产生「请求发出去了但不知道结果」的模糊状态——那是最难处理的情况。

所以安全点 2 放在**工具执行之前**：要么整组不执行，要么整组执行完。这个不变量让状态格外干净。

### 挂起 ≠ 挂住线程

一个很容易搞错的点：**挂起时不能让线程原地等着用户来恢复。**

```
❌ 错误做法：线程 park / sleep，等用户点继续 → 线程池很快被耗尽
✅ 正确做法：把状态写进数据库，然后正常 return，线程释放；
            用户点「继续」时，从线程池取一个新线程，从数据库读状态接着跑
```

这就是为什么状态**必须**落库：它是「跨请求的执行上下文」，是唯一能让不同线程（甚至不同实例）接着跑下去的东西。这也是官方 `AgenticSystemSuspendedException` 的设计意图——**抛出异常来释放线程**，而不是把线程挂住。

### 幂等键

```
idempotencyKey = sha256( runId | stepNo | toolName | canonical(argumentsJson) )  取前 32 位
```

四个组成部分各自的作用：

| 成分 | 作用 | 去掉会怎样 |
|---|---|---|
| `runId` | 区分不同的运行 | 两次运行做同样的操作会被误判为重复 |
| `stepNo` | 同一步重复插入会撞唯一键（**这是防线**） | 防线消失 |
| `toolName` | 不同工具同参数不该互相干扰 | 两个不同工具恰好同参数时冲突 |
| `canonical(argumentsJson)` | **规范化后的**入参 | 见下面的坑 |

**为什么需要 `canonical`（规范化）？** 这是最隐蔽的一个坑：

```java
// 模型给的原始 JSON（键顺序可能是任意的）
{"query":"年假政策","topK":5}
{"topK":5,"query":"年假政策"}

// 直接对原始字符串 hash → 两个不同的值 → 同一个调用被当成两次 → 防线失效
// 规范化：键排序 + 去掉多余空白 + 数值统一格式，再 hash
```

**如果模型每次输出同一组参数时键顺序不稳定**（很可能，因为 JSON 对象在模型输出来说本来无序），那么直接 hash 原始字符串会得到**不稳定的幂等键**，防线形同虚设。必须先把 JSON 解析成对象、按键排序重新序列化，再做 hash。

**为什么不能用「参数的 hash」单独做键？** 因为存在**合法的重复调用**：用户可能明确要求「再建一个一模一样的工单」。那时是**不同的运行**或**不同的 stepNo**，键自然不同，不会误拦。只用参数做键就会把合法的第二次调用拦掉。

**只读工具不需要幂等键**（`idempotencyKey = NULL`）。依赖 MySQL 唯一索引允许多个 NULL 的特性，只读工具天然不参与唯一性约束，不需要额外过滤条件。（见 [10-数据模型总览](10-数据模型总览.md) 里 `agent_step` 的说明。）

### 工具契约：把配置错误暴露在启动时

每个工具注册时必须声明：

| 声明项 | 含义 |
|---|---|
| `name` / `description` | 给模型看的 |
| `sideEffect` | 是否改变系统状态（会写库、会发请求、会下单） |
| `idempotentBackend` | 该接口是否支持我们传幂等键 |
| `requireApproval` | 执行前是否需要用户确认 |

**启动时的强校验**（`ApplicationReadyEvent` 里跑）：

```
若 sideEffect = true 且 idempotentBackend = false 且 requireApproval = false
    → 启动失败，报出是哪个工具配错了
```

**为什么要在启动时失败？** 因为这三者都不满足的副作用工具，是**中断恢复功能的定时炸弹**：它一旦被执行就无法安全重放，而恢复逻辑在没有幂等键时只能重跑。与其等到某次用户中断后才发现，不如启动时就拒绝。

**注意一个取舍**：`requireApproval = true` 也不是万能的。它把「重复执行的风险」换成了「每次都要人点确认的成本」。所以更优的顺序是：**优先让后端接口支持幂等键**，实在不支持才用人工确认兜底。

### 恢复流程（决策树）

```
用户点「继续」
    │
    ├─ 1. run: SUSPENDED → RUNNING
    ├─ 2. 找到最后一个未完成的步骤（agent_step 里 status IN (PENDING, RUNNING, INTERRUPTED) 的最大 seq）
    ├─ 3. 重建 prompt：
    │       ├─ 已完成的工具调用（SUCCEEDED）→ 从 toolResultJson **重放**，标 replayed=1
    │       └─ 中断的 LLM 调用（INTERRUPTED）→ **重新调用**（半截输出无法续写）
    ├─ 4. 回到主循环，从该步骤继续
    └─ 5. 直到正常结束 → COMPLETED
```

**为什么中断的 LLM 调用必须重新调用，不能「接着写」？** 因为大模型的 API 不支持「从中断处继续生成」——你没法告诉它「你上次说到第 37 个字，接着写」。所以只能重新生成整段。**代价是重复的一次 token 消耗**，这是这个功能固有的成本，要计到账上（`ai_call_log` 里会看到同一个 run 两次 `CHAT` 场景的调用）。

**为什么已完成的工具要重放而不是重跑？** 两个理由：
1. 重跑可能得到**不同的结果**（数据已经变了），导致恢复后的推理路径和不中断时不一致——正是失败模式 4
2. 重跑多花时间和钱，而且如果那个工具其实有副作用（只是被错标为只读），就会出事故

**重放的实现**：从 `agent_step.toolResultJson` 反序列化出工具结果对象，塞进 prompt，**完全不发起新的调用**。

## ④ 完整示例：三步任务在第 2 步被中断

### 设定

> 用户："帮我查一下年假政策，然后给 HR 建个工单"
> `conversationId = 7`，本次 `runId = 100`，用户消息 `conversation_message.id = 55`

模型规划出的计划（3 项）：

| itemIndex | title | 副作用 |
|---|---|---|
| 1 | 查年假政策 | 无（只读检索） |
| 2 | 给 HR 建工单 | **有**（会创建工单） |
| 3 | 汇总回复用户 | 无 |

### 场景 B：幂等键真的被用上了

接着上面的状态，假设**用户在 T11 之前就点了一次「同意」，然后因为网络抖动，前端没收到响应，又点了一次「同意」**。

第二次请求走到生成幂等键那一步，算出**同一个键** `a3f7c9e1...`，然后执行：

```sql
INSERT INTO agent_step (runId, seq, idempotencyKey, ...) VALUES (100, 4, 'a3f7c9e1...', ...);
-- ERROR 1062 (23000): Duplicate entry 'a3f7c9e1...' for key 'agent_step.uk_idempotencyKey'
```

撞键之后的**三分支处理**（这是整个模块最需要小心的地方）：

| 已存在那行的 `status` / `toolResultJson` | 含义 | 处理 |
|---|---|---|
| `SUCCEEDED` 且有 `toolResultJson` | 上次真的执行成功了 | **重放**：直接用 `toolResultJson` 作为结果，标 `replayed=1`，**不发起新调用** |
| `PENDING` / `RUNNING` 且**无** `toolResultJson` | 上次执行到一半，结果**未知**（可能已经发出去了！） | **既不能重放也不能重跑** → 转 `WAITING_APPROVAL`，提示用户「上次的工单可能已经创建，请先确认」。这是唯一安全的做法 |
| `FAILED` | 上次执行失败了 | 可以重试（但要考虑失败是否幂等——如果失败发生在「已下单但响应超时」，重试就会重复下单，所以**失败的副作用工具也应转人工确认**） |

**第二行是重点**：很多人会想「没结果就重跑一次嘛」——但如果是「请求已经发到对方系统、对方已处理、只是响应没回来」呢？重跑就是重复下单。这个模糊状态**没有技术手段能自动判定**，只能交给人工。承认这一点比假装能自动处理更安全。

`ai_tool_log` 在这里的作用：两次「同意」都会写一条日志，但只有真正执行的那次 `replayed=0`，重放的那次 `replayed=1`。所以日志里能同时看到「发生过一次重放」这个事实——这正是 M9 验收时要断言的东西。

### 怎么验证这套东西是对的

自动化测试（M9 的验收）应该这样做：

```
1. 用一个只读工具 + 一个「可控失败」的副作用工具（测试替身，记录被真实调用的次数）
2. 跑一遍完整流程，不中断 → 记录结果 A、副作用工具的调用次数 n1
3. 再跑一遍，在第 2 步中断，然后恢复 → 记录结果 B、调用次数 n2
4. 断言：
     ├─ 结果 A == 结果 B                        ← 防失败模式 4（恢复后行为不一致）
     ├─ n1 == n2 == 1                          ← 防失败模式 1（重复执行副作用）
     ├─ ai_tool_log 里 replayed=1 的记录数 > 0   ← 证明重放机制真的走了
     └─ 重复插入同一个 idempotencyKey 会抛唯一键冲突 ← 证明防线有效
```

**第 4 条断言看起来像在测数据库**，但它其实是唯一能证明「防线还在」的方式——如果哪天有人把 `uk_idempotencyKey` 去掉了（比如为了「修复」某个插入报错），这条断言会立刻失败。

## ⑤ 边界、已知限制、坑

### 没做的

| 没做 | 影响 | 备注 |
|---|---|---|
| **自动恢复** | 挂起的运行必须用户手动点继续 | 想做的话，前提是能可靠判断「用户还想继续」 |
| **跨实例的实时中断** | 依赖 Redis 标志，不是消息推送 | 当前够用；标志有最多一个安全点的延迟 |
| **精确到 token 的续写** | 中断的 LLM 调用必须整段重新生成 | 模型 API 不支持，无解 |
| **工具执行中途的中断** | 工具要么不开始，要么执行完 | 有意的设计，见安全点说明 |
| **回滚已完成的副作用** | 中断恢复不会撤销已经建好的工单 | 补偿逻辑是业务范畴，不在状态机里 |
| **运行的去重** | 用户连点两次「发送」会创建两个运行 | 前端防抖 + 后端可用 `inputMessageId` 做幂等，暂未做 |

### 坑

#### 坑 1：`@Transactional` 加在 Agent 主循环上

**这是最容易犯、后果最严重的错误。** 因为给「一次完整的业务操作」加事务是本能反应。

```java
@Transactional   // ← 千万不要！
public void run(String runId) {
    while (...) {
        chatModel.chat(...);   // 几秒到几十秒的 HTTP 调用
        tool.execute(...);     // 可能几秒
        // 每一步都要写数据库
    }
}
```

**三个后果**：

1. **连接池耗尽。** 一个事务占着一个数据库连接几秒到几十秒；几个并发运行就能把连接池占满，整个应用（包括用户登录）全部卡死。
2. **回滚会抹掉副作用的证据。** 循环末尾任何异常 → 整个事务回滚 → **已经执行过的工具调用在数据库里没有记录**。而这条记录是中断恢复的唯一依据。丢了它，恢复时就只能重跑 → 重复执行副作用 → **这正是失败模式 1**。
3. **锁竞争。** 长事务持有行锁，会和其它操作互相阻塞。

**正确做法：每一步一个短事务，独立提交。**

```java
public void run(String runId) {
    while (...) {
        checkInterrupt();          // 安全点
        txTemplate.execute(() -> persistLlmStep(...));    // 短事务 1
        txTemplate.execute(() -> persistToolIntent(...)); // 短事务 2（提交后才能执行工具！）
        tool.execute(...);
        txTemplate.execute(() -> fillToolResult(...));    // 短事务 3
    }
}
```

注意短事务 2 的注释：**必须提交之后才能执行工具**。如果「落库意图」和「执行工具」在同一个事务里，事务还没提交时工具就已经真实执行了——这时如果事务回滚，数据库里就没有意图记录，等于白落。

#### 坑 2：幂等键直接对原始 JSON 字符串做 hash

见第三节。**必须规范化**（键排序 + 去空白），否则键不稳定，防线静默失效。这个坑的可怕之处在于**不报错**：一切看起来都正常，只是偶尔出现重复执行。

#### 坑 3：恢复时把只读工具也重跑了

**现象**：恢复后回答的内容和中断前不一致（引用了一段不同的资料）。

**原因**：只读工具被重跑了，数据已经变化（知识库刚增量更新过）。

**规避**：**所有已完成的工具统一重放**，不分只读/副作用。只读工具重跑虽然「安全」，但会破坏「恢复后行为一致」这个不变量（失败模式 4）。

#### 坑 4：把 SSE 重连当成续跑

**现象**：用户网络抖了一下，前端自动重连，结果 Agent 又从头上跑了一遍，工具被重复调用。

**原因**：把这两个动作混在一起了。它们是**完全不同**的两件事：

| | 重连 | 续跑 |
|---|---|---|
| 触发 | 网络断了 / 用户刷新页面 | 用户点「继续」 |
| 此时运行状态 | 可能还在跑（`RUNNING`），也可能已结束 | 已经挂起（`SUSPENDED`） |
| 接口 | `GET /agent/run/{id}/stream?lastEventId=` | `POST /agent/run/{id}/resume` |
| 做什么 | 补发漏掉的事件，**不改变运行状态** | 改变状态为 `RUNNING`，**从断点继续执行** |

**规避**：接口分开（不要用同一个 `POST /chat` 来处理两种情况），且重连接口**必须是幂等的读操作**。

#### 坑 5：半截输出被写成助手消息

**现象**：用户中断后继续，对话里出现两条助手回复。

**原因**：中断时把半截文本落成了 `conversation_message`，恢复后又生成了完整回复。

**规避**：半截文本只存 `agent_step.responseJson`，**运行结束时才写助手消息**。

**但要注意另一面**：如果用户中断后**永远不恢复**，这个会话里就会「有问无答」。所以需要一个定时任务把长时间挂起的运行**封存**：置为 `CANCELLED`，并把半截文本落成助手消息（`interrupted=1`）。这样界面上能看到「当时回答到一半就停了」，而不是空白。

#### 坑 6：僵尸运行

**现象**：进程崩溃后重启，某些运行永远停在 `RUNNING`，前端一直转圈。

**规避**：在 `ApplicationReadyEvent` 里扫描非终态运行并挂起：

```sql
UPDATE agent_run
   SET status = 'SUSPENDED', interruptType = 'SERVER_RESTART'
 WHERE status IN ('PENDING', 'RUNNING');

-- 同时处理步骤：结果为空但标记为已开始的工具调用，需要人工确认
UPDATE agent_step
   SET status = 'FAILED',
       errorMsg = '服务重启，执行结果未知，请人工确认'
 WHERE status IN ('PENDING', 'RUNNING')
   AND sideEffect = 1
   AND toolResultJson IS NULL;
```

**第二条 SQL 是关键**：那些「已经打算执行副作用工具、但不知道执行到哪了」的步骤，必须转成需要确认的状态，不能让恢复逻辑自作主张重跑。

**这个扫描只在启动时跑一次**，且必须是应用级别的（`ApplicationReadyEvent`），不能放在 `@PostConstruct`——那时候数据库可能还没就绪。

#### 坑 7：断点续跑时重复累计 token

**现象**：同一个运行的 `tokenIn` 看起来偏大。

**原因**：中断的 LLM 调用在 `agent_step` 里留了一行 `INTERRUPTED`，恢复时又插了一行新的 `LLM_CALL`。如果 token 统计把两行都算上，就重复了。

**规避**：这一点**其实是符合预期的**——被中断的那次调用确实消耗了 token（模型真的生成了那些字），应该计入成本。但要在统计逻辑里说明清楚，避免看到「一个 run 里 CHAT 被调了两次」时误判为 bug。**这也正是可观测性的价值**：它让「中断恢复是有成本的」这件事变得可见可量化。
