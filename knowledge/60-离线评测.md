# 离线评测（M1.5）

> 状态：✅ 已落地（2026-10-24）。语料 94 篇、评估集 30 条、5 个变体；
> 支持 opt-in 集成测试与 dev-only HTTP 两种触发方式。

## 一、治哪类病

检索链路有大量「改完不知道有没有变好」的参数和开关：`vector-recall`、`bm25-recall`、
`rrf-k`、`max-candidates`、`max-per-source`、`min-score`、rerank 开关、切片大小/重叠。
没有基线时，每次调整只能靠「随手搜几条看看」——这种判断有两个致命问题：

1. **不可复现**：这次觉得变好了，下次换个人、换几条查询，结论就反了。
2. **无法归因**：命中率下降时，分不清是「换了模型」「改了阈值」「语料变了」还是「检索坏了」。

离线评测要解决的不是「给检索打个绝对分」，而是**给每次改动做归因**：
用固定语料 + 固定查询集 + 同一套指标，把「改前 / 改后」「这个开关开 / 关」放在同一张表里。

## 二、只评检索，不评生成

本子系统只测**检索**：给定 query，看期望的文章有没有进 topK、排在第几。

原因：

- 生成质量评测需要 LLM 判分或人工标注，成本高、稳定性差，且和检索问题混在一起时无法归因。
- 本项目的核心风险在检索链路（混合召回、融合、多样性、阈值），不是「模型会不会说话」。

生成侧的评测留到将来单独做，不混进这份基线。

## 三、评估集与语料

### 语料

复用 salary-leap 已标注过的 JavaGuide 语料：**94 篇 UTF-8 文本**，放在
`docs/rag-eval/corpus/`。每篇首行是 `source: <url>`，其余是正文。

导入时会：

1. 去掉首行（元数据不能进切片和向量）；
2. 把正文落盘到 `uploads/{kbId}/`；
3. 写入 `knowledge_document`，**`name` 和 `sourceUrl` 都设为该 URL**；
4. 同步调用 `KbIndexService.indexDocument`，完整经过解析/切片/嵌入/Milvus/BM25。

`name = URL` 是刻意的：检索结果的 `Hit.docName` 直接就是来源标识，评估匹配不需要额外映射。

### 评估集

`docs/rag-eval/eval-set.json`：**30 条**「查询 → 期望来源」，期望来源写成 URL 路径片段
（如 `database/mysql/mysql-index.html`），匹配规则见 `EvalSourceMatcher`：

- 归一化：小写、去协议、去 `www.`、去锚点、去结尾斜杠；
- **保留查询串**（`?id=4647986` 不能被归一化成通配）；
- 比较用「相等 或 以 `/` 为边界互相结尾」，避免 `proxy.html` 误配 `dynamic-proxy.html`。

> 已知缺口：评估集里有一条期望来源是 `knowledge/testing.txt`，它不在 94 篇网页语料中。
> 报告会把它归为 **不在库（notInIndex）**，不擅自改评估集——这正好验证了「缺数据 vs 检索漏掉」的分类器。

### 为什么按「文档」而不是「切片」标注

期望来源是文章，不是某一段。切片大小/重叠一改，切片边界就变；如果标签绑在切片上，
每次改切片参数都要重标评估集，没有可持续性。按文档标注，切片参数可以自由调。

## 四、指标口径

一个变体跑完全部用例后汇总出下面这些指标（见 `RetrievalMetrics`）：

| 指标 | 含义 | 口径 |
|---|---|---|
| `Hit@K` | 至少命中一个期望来源的用例占比 | 用例级 |
| `MRR@K` | 第一个命中片段名次的倒数均值（未命中记 0） | 名次从 1 开始 |
| `Recall@K` | 被覆盖的期望来源 / 全部期望来源 | **微平均**（先累加再相除） |
| `Precision@K` | 命中期望来源的返回片段 / 返回片段总数 | 切片级 |
| `Diversity@K` | 不同文档数 / 返回片段数 | 切片级；必须和平均返回数一起看 |
| `AvgReturned` | 平均返回片段数 | — |
| `EmptyRate` | 检索成功但一条都没返回的用例占比 | 高值先查链路是否正常 |
| `P50 / P95` | 单条检索耗时 | 最近秩百分位 |

几个容易误读的点：

1. **K 是每个变体自己的 topK**。`all-on` 的 Hit@K 是 Hit@5，`topk-10` 的是 Hit@10，
   两组数字不能直接横向比较；表格下方专门有一行提醒。
2. **Recall/Precision 用微平均**：期望来源多的用例权重更大，不掩盖覆盖面差异。
3. **Diversity 可以被「少返回」刷高**：所以必须和 `AvgReturned` 同屏看。
4. 分母为 0 一律返回 0，不产生 NaN。

### 未命中分类：这份报告最该先看的一列

- **不在库（notInIndex）**：期望文章根本不在索引里 → **数据**的锅，补语料/修导入。
- **检索漏掉（missed）**：文章在索引里但没进 topK → **检索**的锅，才轮到调参。
- **调用失败（error）**：那一趟检索直接抛异常 → 看日志。

## 五、变体设计

变体 = 在同一套生产配置上改一两个开关。定义在 `EvalVariant`：

| 变体 | 改动 | 回答什么问题 |
|---|---|---|
| `all-on` | 生产配置原样 | 当前线上水平 |
| `no-hybrid` | 关 BM25，只剩向量 | 混合检索贡献了多少 |
| `no-diversity` | `maxPerSource=0` | 来源限制是帮忙还是帮倒忙 |
| `no-rerank` | 关 rerank | 精排贡献了多少（模型不可用时与 all-on 相同） |
| `topk-10` | topK=10 | 正确答案有多少排在 6~10 位（召回天花板） |

**没有**移植 salary-leap 的 `no-rewrite`（本项目没有查询改写）和 `vector-only`
（rerank 默认关闭时它与 `no-hybrid` 相同，会得到一张重复行）。

## 六、执行链路

```
ensureCorpus(false)
  ├─ 找/建专用用户 rag-eval
  ├─ 找/建专用知识库 rag-eval-corpus
  ├─ 逐篇导入缺失语料（同步索引），已 INDEXED 的跳过
  └─ 集合丢失 / 模型不一致时自动整库重建
        ↓
快照索引来源（INDEXED 文档名集合）、collection、rerank 是否可用
        ↓
for 变体 × 用例：KnowledgeSearchService.searchWithOptions(...)
        ↓
RetrievalMetrics 算分 → 汇总 → 与上一份同名变体算 delta
        ↓
docs/rag-eval/reports/{runId}/report.json + report.md
```

几个设计点：

- **专用用户/知识库**：评测数据隔离，不出现在真实用户的知识库列表里。`rag.eval.user-id`
  可覆盖；默认自动创建/复用 `rag-eval`。
- **同步导入**：不走异步上传 + 轮询，导入结果确定；仍然完整经过解析/切片/嵌入/双写。
- **重建触发条件**：语料内容变了、切片参数变了、换 embedding 模型、Milvus 集合丢了。
  HTTP 的 `POST /rag/eval/corpus/rebuild?full=true` 会删库重建（新 kbId / 新集合）。
- **单线程串行**：一次评估几百次检索，串行没有性能损失，且进度可信。
- **不缓存**：本项目检索链路没有缓存，不存在「变体之间互相命中缓存」的污染问题。

## 七、怎么跑

### 前置条件

- JDK 21（本机默认 11，必须显式指定）
- MySQL、Redis、Milvus 可达
- 语料/评估集在项目根目录下（路径是相对 CWD 的）

### 方式一：集成测试（推荐，不暴露接口）

```bash
export JAVA_HOME=/e/Java/jdk-21.0.5

# 全量：5 个变体 × 30 条用例
mvn test -Dtest=RagEvalIT -DfailIfNoSpecifiedTests=false

# 冒烟：只跑 all-on + 2 条
mvn test -Dtest=RagEvalIT \
  -Drag.eval.it.variants=all-on \
  -Drag.eval.it.caseIds=java-proxy-01,jvm-memory-01 \
  -DfailIfNoSpecifiedTests=false

# 语料整库重建
mvn test -Dtest=RagEvalIT -Drag.eval.corpus.full=true -DfailIfNoSpecifiedTests=false
```

类名以 `IT` 结尾，Surefire 默认不包含，普通 `mvn test` 不会执行。

### 方式二：HTTP（dev-only）

`rag.eval.http-enabled=true` 时装配 `RagEvalController`，必须登录：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/rag/eval` | body `{variants?, caseIds?}`，异步触发 |
| `GET` | `/rag/eval/status` | 当前状态与进度 |
| `GET` | `/rag/eval/report/latest` | 最近一份报告（JSON） |
| `POST` | `/rag/eval/corpus/rebuild?full=true` | 同步导入/重建语料 |

```bash
# 先登录（session cookie 由 /user/login 返回）
curl -X POST 'http://localhost:8102/api/rag/eval' \
  -H 'Content-Type: application/json' \
  -d '{"variants":["all-on","no-hybrid"]}'
curl 'http://localhost:8102/api/rag/eval/status'
```

> ⚠️ 首次触发会同步导入 94 篇语料（本地 ONNX，本机实测约 75 秒），客户端要放宽超时。
> 生产环境必须把 `rag.eval.http-enabled` 设为 `false`。

## 八、报告怎么读

`docs/rag-eval/reports/{runId}/report.md` 是给人读的，顺序建议：

1. **先看语料是否完整**：`corpusComplete=false` 或空结果率 > 20% 时，后面的命中率没有分析价值。
2. **看变体对比表**：`all-on` 是当前水平；`no-hybrid` 与 `all-on` 的差就是 BM25 的贡献。
3. **看「与上次的差值」**：只在同名变体之间比。`Δ=0` 也是结论，说明改动只影响耗时。
4. **看未命中明细**：先处理「不在库」（补数据），再处理「检索漏掉」（调检索）。

`report.json` 是同一份数据的机器可读版本，下次运行用它算 delta。

## 九、边界与已知坑

1. **原始 M1.5「远端 vs 本地」的比较已经错过**。最初的计划是先对远端 embedding 跑基线，
   再换本地模型对比；实际代码早已切到本地 bge-small-zh，远端基线无法复现。
   本实现的定位是**当前链路的回归基线**，不是「远端 vs 本地」的实验。
2. **语料是静态的**。改了 `docs/rag-eval/corpus/` 里的正文，增量导入不会察觉（文档已 INDEXED）。
   必须 `full=true` 重建。删掉语料文件同理：旧文档会留在库里，报告用 `staleDocs` 提醒。
3. **rerank 模型默认关闭**。`models/` 已 gitignore，换机器不一定有模型；此时
   `no-rerank` 与 `all-on` 完全相同，报告会标注 `rerank 模型不可用`。
4. **HTTP 返回的 Long 是字符串**。全局 Jackson 配置把 `Long/long` 序列化成字符串
   （`JsonConfig`），所以 `startTime` / `costMillis` / `p50Millis` 在 HTTP 响应里是字符串；
   `report.json` 用独立 ObjectMapper，仍是数字。
5. **报告目录相对 CWD**。不在项目根目录运行时，`docs/rag-eval/reports` 会落到别处；
   集成测试通过 Maven 运行时 CWD 就是项目根目录。
6. **评估会写业务表**。专用用户、知识库、文档、切片都会落库；这是有意的隔离，
   不是临时数据。删除评测库请走 `full=true` 重建或手工清理。
7. **首次运行慢**。94 篇本地嵌入是主要成本；之后复用索引，主要耗时是 150 次检索。
8. **评测集不是产品指标**。它从现有语料反推期望来源，是回归防护网，
   不能代表真实用户满意度，也不能拿来宣传「准确率 90%」。

### 首份基线（2026-10-24）

运行 ID `20261024-175703-527`；语料 94 篇 / 3648 个切片；评估集 30 条；
MySQL + Redis + Milvus 全部就绪，rerank 模型不可用（`ai.rerank.enabled=false`）。
重跑一次后所有命中类指标 delta 全为 0，只有 P50/P95 有几毫秒波动——链路是确定性的。

| 变体 | Hit@K | MRR@K | Recall@K | Precision@K | Diversity@K | 平均返回 | 空结果率 | P50 | P95 |
|---|---|---|---|---|---|---|---|---|---|
| 全开（生产基线，K=5） | 86.7% | 0.598 | 68.9% | 32.0% | 0.727 | 5.0 | 0% | 41ms | 62ms |
| 关混合检索（向量 only，K=5） | 76.7% | 0.593 | 64.4% | 31.3% | 0.720 | 5.0 | 0% | 29ms | 35ms |
| 不限制同一来源（K=5） | 83.3% | 0.584 | 55.6% | 46.7% | 0.500 | 5.0 | 0% | 32ms | 46ms |
| 关 rerank（K=5） | 86.7% | 0.598 | 68.9% | 32.0% | 0.727 | 5.0 | 0% | 32ms | 39ms |
| 全开但 K=10 | 96.7% | 0.610 | 84.4% | 25.0% | 0.687 | 10.0 | 0% | 32ms | 47ms |

**读数结论（只针对这 30 条用例，不外推成产品指标）：**

1. **BM25 贡献约 10 个百分点 Hit@5**（86.7% vs 76.7%），但 MRR 几乎不变（0.598 vs 0.593）。
   说明混合检索主要把「原本完全没进 top5」的正确答案捞了进来，而不是把已有命中的名次提前。
2. **来源多样性限制在「覆盖」和「精度」之间做交换**：关掉它后 Precision 从 32.0% 涨到 46.7%，
   但 Recall 从 68.9% 掉到 55.6%、Hit@5 掉 3.3pp、Diversity 掉到 0.5。
   原因是 Precision 是切片级的——不限来源时同一篇会占满 5 个格子，「命中切片占比」自然虚高。
   结论：`maxPerSource=2` 在**召回覆盖**上是有价值的，不要为了 Precision 好看而关掉它。
3. **最大的天花板是 K=5**：K=10 时 Hit 从 86.7% 涨到 96.7%、Recall 涨到 84.4%，
   说明有 3 条用例的正确答案稳定排在 6~10 位。下一步该用评测集标定「topK 与上下文预算」的平衡，
   而不是继续微调融合参数。
4. **rerank 这一次没有结论**：模型不可用，`no-rerank` 与 `all-on` 完全相同。
   等模型文件就位后重跑，才能量出精排的贡献。
5. **链路健康**：30 条用例 0 失败、0 空结果，P95 < 100ms。
6. `testing-interview-01` 的 `knowledge/testing.txt` 被稳定归为 **不在库**，
   同时它期望的另一篇百度文章能正常命中——「缺数据 vs 检索漏掉」分类器生效。

基线文件在 `docs/rag-eval/reports/20261024-175703-527/`（已 gitignore）。
以后每次改检索参数，先跑一次，和这份基线比 delta，再决定是否保留改动。

## 十一、下一步

评测立起来之后，才轮到用它做决定：

1. **标定 `minScore`**：当前 0.0，等于不过滤；试 0.4/0.5/0.6 看 Recall 掉多少、Precision 涨多少。
2. **标定召回数**：`vectorRecall` / `bm25Recall` 从 20 调到 10/30/50，看 P95 与命中的平衡。
3. **切片参数**：`chunkSize` / `chunkOverlap`（当前 400/80）对长文的影响。
4. **工具化检索的代价**：M7 把「自动检索」改成「模型择机调用 `searchKnowledge`」，
   这里只测得到「检索本身」，测不到「模型是否愿意调工具」——那需要另一套 Agent 行为评测。
5. **Milvus v2 评估**：等这笔技术债到期时，用同一套评估集对比服务端 BM25 与手写 bigram。
