# 文档写作约定

## 一、为什么要定约定

这套文档的读者是「三个月后的自己」和「新接手的人」。他们不缺信息渠道，缺的是**判断依据**——为什么当初这么做。所以这套文档的重点不是「描述代码在做什么」（读代码更快），而是**记录代码为什么是这个样子**。

## 二、每篇模块文档的固定五段式

每个模块文档按顺序写这五段。**顺序不能改**，因为它是「从抽象到具体」的认知顺序。

### ① 这个模块治的是哪类病（通用问题定义）

**先不看本项目。**回答：

- 这是一个**什么类别**的问题？业界普遍怎么称呼它？
- 它处在整条链路的**哪个位置**？上游是谁、下游是谁？
- 它的**边界**在哪——哪些事归它管，哪些事明确不归它管？
- 它有哪几类**典型的失败模式**？（这部分最重要：一个模块存在的意义通常就是防住某几种失败）

**反面例子**（不要这样写）：

> ❌「我们的对话偶尔会超长导致模型报错，所以做了个裁剪功能。」

这是把**本项目的症状**当成了问题定义。它的问题在于：读者无法判断这个设计是否适用于别的场景，也无法判断当初为什么选了这个方案——因为「模型报错」这句话没说明白是上下文窗口的问题、还是 payload 大小的问题、还是别的。

**正面写法**：

> ✅「大模型是无状态的：它不记得上一次对话。所以每次请求都要把历史重新发送一遍。但上下文窗口有上限，而超出上限的表现是请求直接失败（不是自动截断）。因此『记忆』这个模块要解决的本质问题是：**在一份固定的 token 预算里，决定放哪些历史进去、丢哪些。**
>
> 它只负责『选哪些消息』，不负责『消息存在哪』（那是持久化的事），也不负责『把旧对话压缩成摘要』（那是独立的总结策略，本模块暂不做）。
>
> 三类典型失败：① 预算超出导致请求失败；② 选进来的历史里工具调用请求和工具结果被拆散，导致模型 API 报错；③ token 成本随对话轮次线性上涨。」

### ② LangChain4j 官方怎么做

- 给出**官方文档链接**和**具体的类名/接口名**
- 官方提供的能力边界在哪，哪些是它明确不做的
- 如果官方版本之间差异很大，要点明**我们用的是哪个版本、它有什么**
- **不要写「框架不支持 X」这种绝对的话**，除非确认过最新版本也不支持。要写「X 在 N 版本才有，我们用的是 M 版本」——这种说法可验证，也能随版本升级更新

> **这一条是踩了坑之后加的。** 「中断与恢复」那篇的原版写着「LangChain4j 没有 Agent 概念」，作为「所以必须自研」的论据。后来一查，那是 1.4.0 的事实，而最新版（1.20.0）**有** agentic 模块——**整段论证的前提失效了**，不得不回头重写。把「特定版本的限制」写成「框架的限制」，就是这样翻车的。

这一段的用途：**将来升级框架时，这段是改动清单**。

### ③ 本项目为什么这么落地

- 哪些部分直接用官方的，哪些自研
- **自研的部分必须写理由**，而且要写「为什么官方方案在这里不合适」，不能只写「我们觉得自研更好」
- 如果是一时的权宜之计，明说是权宜之计

### ④ 数据结构与流程时序

- 涉及的**表结构**（字段 + 一句话说明，不用贴完整 DDL，DDL 在 [10-数据模型总览](10-数据模型总览.md)）
- 流程用**时序图或编号步骤**表示
- 如果有算法，写**伪代码**，不贴实现代码——实现会变，思路不会

### ⑤ 边界、已知限制、踩过的坑

- 明确**没做什么**（比做了什么更重要，否则读者会以为已经覆盖了）
- 已知的局限
- 踩过的坑：**现象 → 原因 → 规避方式**，三样都要有

## 三、写作纪律

### 不写什么

| 不写 | 原因 |
|---|---|
| 代码原文 | 代码会变，复制进文档立刻过期。引用「类名 + 文件路径 + 方法名」即可 |
| 「显而易见」的套话 | 「这里做了参数校验」没有信息量。要写就写**校验的是什么、不校验会怎样** |
| 大段的框架入门介绍 | 官方文档已经写得很好了，给链接。文档里只写官方**没说但踩过**的部分 |
| 未加区分的「最佳实践」 | 凡是要写「应该怎样」，必须能说出**在什么前提下**才是对的 |

### 要写什么

| 要写 | 例子 |
|---|---|
| **决策的备选方案** | 「考虑过 X，但 X 在多实例部署下会……，所以选了 Y」 |
| **具体数字和它的来源** | 「切片长度取 400 字符——因为 bge tokenizer 对中文的切分下，500 字符约对应 550 token，超出模型的 512 上限」 |
| **反直觉的地方** | 「这里先落库再执行，顺序不能反——反了的话进程崩溃就不知道副作用发生过没有」 |
| **不知道的地方** | 「这个值理论上应该在 0.2~0.3 之间，但需要实测确定」。**写「待验证」比编一个数字好** |

### 关于「待验证」

凡是**没有实测过的数字或结论**，必须显式标注 `待验证`，并写清楚**怎么验证**。

编一个看起来很专业的数字，比留一个空白危害大得多——因为空白会让人去验证，编的数字会被直接采信。

## 四、命名与编号

### 文件命名

```
<两位编号>-<模块名>.md
```

- 编号规则见 [00-索引与阅读顺序](00-索引与阅读顺序.md)
- 文件名用中文，方便在文件树里一眼看懂
- 不加日期、不加版本号——文档应该**原地更新**，不是叠版本

### 术语统一

**一个概念只能有一个名字。** 本项目固定用法：

| 统一用 | 不要混用 | 含义 |
|---|---|---|
| 会话 | 对话、聊天、session | `conversation`，用户可见的对话容器 |
| 消息 | chat、message | `conversation_message` 一条记录 |
| 知识库 | KB、知识库集合 | `knowledge_base`，用户创建的独立检索单元 |
| 文档 | 文件、资料 | `knowledge_document`，知识库里的一篇 |
| 切片 | 分块、chunk、段 | `knowledge_chunk`，文档切出来的检索单元 |
| 工具调用 | 函数调用、function call | 模型要求调用某个后端能力 |
| 副作用 | 写操作 | 会改变系统状态、重复执行有后果 |
| 一次运行 | run、任务 | `agent_run`，一次完整的「用户提问 → 得到回答」 |
| 挂起 | 暂停、suspend | `SUSPENDED`，状态机的正常状态 |
| 续跑 | 恢复、resume | 从挂起点接着往下走 |

**注意「会话」和「一次运行」的区别**：一个会话里可以有多次运行（用户问一次就是一次运行）。「中断对话」实际上是中断**当前这次运行**，会话本身不受影响。

### 代码标识符

文档里提到类名、表名、字段名时**加反引号**，并且和代码里的写法完全一致：

- 类名：`AgentRunner`、`RunStateMachine`
- 表名：`agent_run`、`conversation_message`（小写下划线，因为是表名）
- 字段名：`promptVisible`、`idempotencyKey`（**camelCase**，因为本项目数据库列名就是 camelCase，见 [10-数据模型总览](10-数据模型总览.md)）
- 状态值：`SUSPENDED`、`WAITING_APPROVAL`（全大写，因为是枚举值）

### 引用

- 引用本项目其他文档：用**相对路径链接**，如 `[11-对话记忆](11-对话记忆.md)`
- 引用官方文档：给链接，并注明**是哪个版本**的文档
- 引用代码：`路径:行号` 或 `类名#方法名`

## 五、前端契约文档的额外约定

`frontend/` 目录下的文档面向**不了解后端实现**的读者，所以额外要求：

1. **每个接口都要有可复制的请求/响应示例**（JSON 原文，不是字段表）
2. **字段表里写清楚类型和是否必填**，并且注意 Java 的 `Long` 在 JSON 里是**字符串**（见 [frontend/01-通用约定](../frontend/01-通用约定.md)）
3. **写清楚失败时会怎样**，包括 HTTP 状态码是不是 200、错误码是什么、前端该做什么
4. **不要出现只有后端懂的术语**，比如「逻辑删除」「BaseResponse」。如果必须提，就解释清楚

## 六、更新约定

| 情况 | 做法 |
|---|---|
| 实现和文档不一致 | **文档错了**，改文档；如果是设计变了，同时把「原设计为什么不成立」记进「边界与坑」 |
| 发现文档漏了一个坑 | 补进「边界与坑」，不要只记在脑子里 |
| 一个模块要拆成两篇 | 拆分时同步改 [00-索引](00-索引与阅读顺序.md) 的进度表 |
| 文档过时了 | 删掉或重写。**过期的文档比没有文档更糟**——它会主动误导人 |
