# 总体架构与路线图

## 一、这个项目要做什么

一句话：**一个能对话、能查自己的知识库、能调后端接口干活、能被随时打断再续上的 Agent。**

和「套个壳调大模型 API」的区别在这几件事上：

| 能力 | 用户感受到的 | 工程上的实质 |
|---|---|---|
| 对话记忆 | 能追问「那第二条呢？」 | 每轮把历史重新拼进 prompt，并在 token 预算内裁剪 |
| RAG | 回答里带着自己上传的资料的依据 | 文档切片的向量化、混合检索、重排 |
| 工具调用 | 问「北京今天天气」它真去查了 | 把后端接口暴露成模型能调用的工具，并处理模型乱调 |
| 中断/续跑 | 点停止就真停，回来还能接着干 | 执行状态从进程内存搬到数据库，恢复时不重复执行副作用 |
| 流式输出 | 字是一个个蹦出来的 | SSE + 事件持久化 + 断线重连补偿 |

**这五件事里，只有「工具调用」是 LangChain4j 帮你做完的。其余四件，框架只提供零件，装配得自己来。** 这是本项目的一个基本立场，下面第三节展开。

## 二、分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  接入层  controller                                            │
│  ├─ user        已有（Phase 1）                                │
│  ├─ conversation 会话与消息 CRUD                                │
│  ├─ chat        对话，普通响应 + SSE 流式                        │
│  ├─ agent       run 的中断 / 恢复 / 状态查询                    │
│  └─ knowledge   知识库、分类、文档的增删改查                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ DTO / VO（BaseResponse 统一信封）
┌───────────────────────────▼─────────────────────────────────┐
│  编排层  agent                                                 │
│  ├─ AgentRunner        ReAct 主循环（LLM → 工具 → LLM …）       │
│  ├─ RunStateMachine    状态流转 + 中断检测 + 断点续跑            │
│  ├─ ToolRegistry       工具注册与契约校验（副作用分级）           │
│  ├─ MemoryBuilder      从 conversation_message 重建 prompt      │
│  └─ EventPublisher     事件落库 + 推给 SSE 连接                  │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  能力层                                                        │
│  ├─ 检索  RetrievalService   向量召回 + BM25 + RRF + rerank     │
│  ├─ 索引  KbIndexService     解析 → 切片 → 向量化 → 入 Milvus    │
│  ├─ 工具  *ToolExecutor      查知识库、查业务库、调后端接口       │
│  └─ 评测  (离线，不参与线上)                                    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  模型层  model                                                 │
│  ├─ 对话模型  ChatModel       DeepSeek 官方·V4.1-Flash（流式） │
│  ├─ 向量模型  EmbeddingModel  本地 ONNX bge-small-zh（512 维）   │
│  └─ 重排模型  ScoringModel    本地 ONNX bge-reranker            │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  存储层  store                                                 │
│  ├─ MySQL    业务数据 + 会话消息 + Agent 状态 + 调用日志（权威源）  │
│  ├─ Milvus   向量索引（派生数据，可重建）                        │
│  ├─ Redis    登录态 + 验证码 + 运行中的中断标志                   │
│  └─ 文件系统  上传的原始文档 + 本地模型文件                       │
└─────────────────────────────────────────────────────────────┘
```

**关键的一条设计原则**：**MySQL 是权威源，Milvus 是派生索引。**

向量库里存的每一段文本，MySQL 里都有对应记录；反之不要求。这样做的理由是：向量库只擅长「按相似度找」，不擅长「列表、统计、改状态、事务」；如果让 Milvus 当主存，做不了「这个文档解析到哪一步了」这种查询。而且向量库换了、模型换了、集合重建了，业务数据都不该丢。

代价是**双写**，所以要有对账机制（见 [22-知识库与文档生命周期](22-知识库与文档生命周期.md)）。

## 三、LangChain4j 用到哪，哪里自研

这是本项目最重要的一个立场，先讲清楚，后面每篇文档都会引用。

**把 LangChain4j 当「厂商适配层 + 数据模型」，不当「架构骨架」。**

| 能力 | 谁做 | 理由 |
|---|---|---|
| 消息模型（`ChatMessage` / `UserMessage` / `ToolExecutionResultMessage`）、`@Tool` 的 JSON Schema 生成、`AiServices` 的 JSON→POJO 绑定、`MilvusEmbeddingStore`、`DocumentSplitters.recursive`、`OnnxEmbeddingModel`、`OnnxScoringModel`、`StreamingChatModel` / `TokenStream` | **LangChain4j** | 这些是它真正做得好且无争议的部分：协议转换、schema 生成、厂商适配。自己写没有收益。 |
| 消息持久化、记忆窗口裁剪、Agent 状态机、工具幂等与重放、SSE 事件落库与回放、混合检索融合、rerank 编排、增量索引、来源多样性 | **自研** | 这四类是「和自有业务数据强耦合」的逻辑。框架的抽象（`ChatMemoryStore` / `RetrievalAugmentor` / `ChatMemoryProvider`）会要求你把业务数据塞进它的模型里，而我们的消息本身已经是业务数据（要展示、要审计、要分页、要支持截断重发），再存一份到框架的 store 里，就是**双写 + 一致性问题**，收益为负。 |

一个具体的例子说明这个取舍：官方 `MessageWindowChatMemory` 能帮你做「只保留最近 N 条消息」这件事——听起来正好是我们要的。但它把消息存在自己的 `ChatMemoryStore` 里，而我们的消息存在 `conversation_message` 表里。如果两边都存，就会出现「用户删了消息但记忆里还在」这种不一致。所以正确的做法是**借用它的策略思想（窗口大小、系统消息常驻、不拆散工具消息对），但实现完全自研**，直接读自己的表。见 [11-对话记忆](11-对话记忆.md)。

## 四、一次对话的完整链路

以「帮我把上周那份年假政策整理成工单」为例，走一遍全链路：

```
前端               后端                                    存储
 │
 ├─ POST /api/chat/stream ────────────────────────────────────────►
 │                  │
 │                  ├─ 1. session 取 userId（未登录直接返回 JSON 40100）
 │                  ├─ 2. 落库用户消息                    ──► conversation_message(role=USER)
 │                  ├─ 3. 建 agent_run(status=RUNNING)    ──► agent_run
 │                  ├─ 4. 开 SSE，回 run_start 事件        ──► agent_event
 │                  │
 │   ◄── event: run_start
 │                  │
 │                  ├─ 5. MemoryBuilder 从 conversation_message 取历史
 │                  │      （预算不够就裁剪，不拆散工具消息对）
 │                  ├─ 6. 检索：向量 + BM25 → RRF → rerank
 │                  │      命中「年假政策」相关切片
 │                  ├─ 7. 调 LLM（带工具清单 + 检索片段）
 │   ◄── event: message_delta（不落库，逐个 token 推）
 │                  │
 │                  ├─ 8. LLM 决定调 searchKnowledge 工具
 │                  ├─ 9. 落 tool_call 意图行（先落库再执行！） ──► agent_step(PENDING)
 │   ◄── event: tool_call                                ──► agent_event
 │                  ├─10. 执行工具，结果写回同一行        ──► agent_step(SUCCEEDED, toolResultJson)
 │   ◄── event: tool_result                              ──► agent_event
 │                  │
 │                  ├─11. 再一次 LLM（这次历史里带上了工具结果）
 │                  │
 │                  ├─12. LLM 决定调 createTicket（有副作用！）
 │                  ├─13. 需要人工确认 → 挂起
 │                  ├─14. run → status=WAITING_APPROVAL  ──► agent_run
 │   ◄── event: interrupt(APPROVAL_REQUIRED, pendingTool=createTicket)
 │                  │
 │  ... 用户点「同意」 ...
 ├─ POST /api/agent/run/{runId}/approve ──────────────────────────►
 │                  ├─15. 校验幂等键还没被用过
 │                  ├─16. 执行 createTicket（只执行一次）
 │                  ├─17. run → RUNNING，继续循环
 │   ◄── event: message_delta … event: run_end
 │                  │
 │                  ├─18. 落库助手消息                    ──► conversation_message(role=ASSISTANT)
 │                  └─19. run → COMPLETED                 ──► agent_run
```

几个**容易被忽略但很关键**的设计点，先在这里点名，后面各自展开：

1. **第 9 步「先落库再执行」** —— 顺序不能反。先落库，进程崩了才知道「这一步打算做什么」；反过来先执行再落库，崩了就永远不知道那个副作用发生过没有，恢复时只能重跑（可能重复下单）。
2. **第 7 步的 message_delta 不落库** —— 每个 token 一行会把事件表撑爆。断线重连时靠别的方式补偿，见 [31-流式输出SSE](31-流式输出SSE.md)。
3. **第 5 步的记忆重建发生在每一轮 LLM 调用之前** —— 不是每轮请求一次，是每轮循环一次，因为工具结果要进历史。
4. **第 13 步的「挂起」不是异常** —— 它是状态机的一个正常状态，线程可以正常释放。

### 版本对齐的说明

LangChain4j 的**核心模块和集成模块版本号是分开的**：`langchain4j-core` / `langchain4j` 走 **`1.20.0`** 稳定线，而 `milvus` / `reactor` / `embeddings-*` / `onnx-scoring` / `document-parser-*` 这些集成是 **`1.20.0-beta30`**。

**例外：`langchain4j-open-ai`（对话模型用）在稳定线 `1.20.0`，不在 beta 线。** 它的坐标还带连字符（`open-ai`，不是 `openai`）——按其他集成那样写 `langchain4j.beta.version` 会拉不到包（beta 线上没发它，只会得到一堆只有 `.lastUpdated` 的失败缓存，这是我们 2026-10-11 实测踩到的）。

**这不是我们刻意挑的组合，而是官方发版的兼容方式**——集成的 pom 里声明的就是稳定版 core。已实测确认：`langchain4j-milvus:1.20.0-beta30` 和 `langchain4j-document-parser-apache-pdfbox:1.20.0-beta30` 依赖的都是 `langchain4j-core:1.20.0`，对齐。

**升级时这几个版本号要一起动，不能只升一个。**

### 为什么从 1.4.0 换到 1.20.0（2026-09-21 决策记录）

项目最初按 salary-leap 的选型钉在 `core 1.4.0 + 集成 1.4.0-beta10`，原因是**离线 Maven 仓库里只有那一套**。后来查了阿里云镜像（本项目实际用的源），发现：

- 最新稳定线是 **`1.20.0`**，集成是 **`1.20.0-beta30`**——我们落后了 **16 个 minor 版本（约 14 个月）**
- 我们需要的模块**在最新线上全都有**，而且都在镜像上可拉取（core、`embeddings-bge-small-zh-v15-q`、`onnx-scoring`、`milvus`、`community-dashscope-spring-boot-starter`、`reactor`、`document-parser-*`、`agentic`）

**决定升级的决定性理由是「切换成本此刻最低」**：当时项目**一行 LC4j 代码都还没写**（pom 里连依赖都还是注释）。唯一的代价是移植 salary-leap 代码时重新对齐 API——而那段代码本来就要改包名、要把 `RagIndexService` 重写成 `KbIndexService`，返工量高度重叠。

升级拿到的实际收益：

1. **PDF/Word 解析能力**（官方 parser 模块，且它的 core 依赖在 1.20.0 已对齐——salary-leap 时期正是因为这个不对齐才放弃了 parser 方案、退回 jsoup）
2. **agent 可观测性**的官方设施（`AgentListener` / `AgentMonitor` / `MicrometerChatModelListener`）
3. 官方 `langchain4j-agentic`（我们**评估后仍未采用**，理由见 [12-中断与恢复的状态机](12-中断与恢复的状态机.md)）
4. 不必踩「legacy 模块将被移除」的迁移债（见下）

### ⚠️ 一笔已知的技术债：Milvus 用的是 legacy 模块

`langchain4j-milvus`（依赖 `milvus-sdk-java:2.5.9`）是**旧模块，官方宣布会在 LangChain4j 2.0 移除**，由 `langchain4j-milvus-v2`（依赖 `milvus-sdk-java:2.6.14`）顶替并改名。

**我们仍然选了 legacy，是刻意的权衡**：

| | legacy（我们选的） | v2 |
|---|---|---|
| Milvus 服务端 | **2.5.27 不用动**（SDK 版本和现在完全一致） | 要升到 2.6.x，且 SDK 2.6 对 2.5 服务端的兼容性需实测 |
| 检索能力 | 只有稠密向量 | 稠密 + BM25 + RRF 全在服务端 |
| 对我们现有设计的影响 | 保留「搬 salary-leap 的 BM25+RRF」方案 | 要重写混合检索那一篇 |

**选择理由**：v2 的服务端 BM25 用的是 Milvus 自己的文本分析器，中文分词质量取决于 analyzer 配置；而 salary-leap 手写的中文 bigram 分词是**已在真实评测集上验证过**的。在不换 Milvus 服务端、不引入两处新不确定性的前提下，先用 legacy 把链路跑通，**等评测体系立起来、能用数据说话时再评估 v2**。

**这笔债的到期时间**：LangChain4j 2.0 发布时（届时必须迁移）。**不是现在要解决的问题，但要不定期回来看一眼。**

### 为什么对话模型用远端、向量模型用本地

| | embedding / rerank | 对话模型 |
|---|---|---|
| 调用频次 | 每次检索都调，一篇文档切 50 片就要 50 次 | 每轮对话 1~3 次 |
| 单次耗时要求 | 高（要压进检索延迟） | 相对宽松（反正要流式输出） |
| 效果差距 | 小模型（512 维）和大模型对**检索**的效果差距有限，且可以用 rerank 补救 | 开源小模型和 DeepSeek-V4.1-Flash 这类闭源大模型在**指令遵循、工具调用**上差距明显 |
| 成本 | 按量计费的话，入库一次就是一笔钱，且重复入库重复花钱 | 有成本但可控 |
| 结论 | **本地部署**（一次性下载模型文件，之后零成本零延迟） | **远端 API**（效果优先） |

这个决定带来的直接后果：**embedding 维度从占位的 1536 变成 512，`milvus.dimension` 必须同步改**。所有受影响的地方汇总在 [21-本地Embedding与Rerank](21-本地Embedding与Rerank.md)。

### 对话模型选型：DeepSeek-V4.1-Flash（2026-10-11）

**当前选择：DeepSeek 官方 API 直连**（`https://api.deepseek.com`），模型 DeepSeek-V4.1-Flash，
经通用的 `langchain4j-open-ai`（OpenAI 兼容协议）接入。

**为什么不用 `langchain4j-community-dashscope-spring-boot-starter`（最初规划的 qwen 路线）**：
那个 community starter 是 Spring **自动配置**，强制要求 `langchain4j.community.dashscope.chat-model.api-key`，
**缺 key 会让整个应用启动失败**（本项目早先因此把它押后）。改用普通适配器 `langchain4j-open-ai` 指向
OpenAI 兼容端点：没配 key 时靠条件装配跳过、不拖垮启动，也把「厂商适配」收敛到最通用的 OpenAI 协议上。

**选 DeepSeek 本身不是为了「效果更好」**——那还没实测过（要测先得有评测集，见 [60](60-离线评测.md)）。

**⚠️ 换 provider 时，这三个「由服务提供方定义」的东西必须一起改，否则会静默出错：**

| | DeepSeek 官方（当前） | 阿里云百炼 DashScope |
|---|---|---|
| `baseUrl` | `https://api.deepseek.com` | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `modelName` | `deepseek-flash` | `deepseek-v4.1-flash` |
| 环境变量 | `DEEPSEEK_API_KEY` | `DASHSCOPE_API_KEY` |

**同一个模型，model ID 在不同 provider 上是不同的串**——别按产品名自己拼，也别把一个 provider 的 ID
抄到另一个上。实测：拿百炼的 key 打 DeepSeek 官方端点 → `Authentication Fails`。换 provider 时
`baseUrl` + `modelName` 要一起改。（这两行是本项目实际来回切过一次的教训，所以专门列表记下来。）

**落地要点**（代码在 `config/ChatModelProperties` + `config/ChatModelConfig` + `ai/DeepSeekChatModelTest`）：

- api-key 从系统环境变量 **`DEEPSEEK_API_KEY`** 读。
- ⚠️ **`langchain4j-open-ai` 的坐标带连字符、且走稳定线 `1.20.0`**（见上面「版本对齐」的例外说明）——按 beta 线写会拉不到包。
- 思考模式待验证：DeepSeek V4 系列默认可能返回 `reasoning_content`（思维链）。要不要它、带不带延迟/成本代价，等接上链路后实测再定。

## 六、里程碑

每个里程碑都能**独立端到端验证**——不能验证的里程碑是没拆好的。

| # | 里程碑 | 怎么验证 | 风险 |
|---|---|---|---|
| **M0** | 引入依赖并验证能拉通 | `mvn dependency:tree` 能看到全部目标 artifact；写段代码 embed「你好」断言得到 512 维向量 | ~~高~~ **中**：见下面的「M0 进展」 |
| **M1.5** | 先搬评测子系统，对**远端** embedding 跑基线 | 产出一份含 Hit@K / MRR / Recall 的报告 | 低 |
| **M1** | 换成本地 embedding，维度 512，每库一个集合 | 索引一篇文档能召回；与 M1.5 基线对比质量未明显下降 | **高**：质量风险 |
| **M2** | 本地 rerank 接入 | 中文 query 下重排后排序合理 | 中：取决于模型文件来源 |
| **M3** | 搬检索内核（向量+BM25+RRF+rerank+多样性） | 增量重建只动改动的那篇文档的切片 | 低 |
| **M4** | 会话/消息表 + CRUD + 非流式对话 | 一问一答落库，历史按序号取回 | 低 |
| **M5** | 对话记忆 | 多轮追问生效；裁剪不拆散工具消息对 | 中 |

### M0 已完成（2026-09-21）

**结论：本地模型这条路走通了，但踩到一个必须记住的坑。**

| 验证项 | 结果 |
|---|---|
| 全部目标 artifact 从阿里云镜像可拉取 | ✅ 含 onnxruntime、`ai.djl.huggingface:tokenizers:0.36.0`、pdfbox 3.0.7、poi 5.5.1 |
| `ScoringModel.scoreAll(List<TextSegment>, String)` 签名未变 | ✅ 读 1.20.0 源码确认 → rerank 移植不受影响 |
| `MessageWindowChatMemory` / `AiServices` 的模块归属 | ✅ 在**聚合模块** `langchain4j`，不在 `core` |
| 512 维向量实际产出 | ✅ 单测通过 |
| dashscope 配置前缀未变 | ✅ 仍是 `langchain4j.community.dashscope.chat-model`，salary-leap 的 yml 可照抄 |
| **onnxruntime 原生库能加载** | ⚠️ **必须先显式钉到 1.20.0**，见下 |

**踩到的坑（详见 [21-本地Embedding与Rerank](21-本地Embedding与Rerank.md) 的坑 1）**：

LC4j 的两个模块**各自声明了不同版本的 onnxruntime**——`embeddings`（向量）→ `1.20.0`，深度 2；`onnx-scoring`（重排）→ `1.22.0`，深度 1。Maven「取近者」选了 1.22.0，而 **1.22.0 的原生库在这台机器上加载失败**：

```
UnsatisfiedLinkError: ...\onnxruntime.dll: 动态链接库(DLL)初始化例程失败
```

已在 `dependencyManagement` 里显式钉 `1.20.0` 后通过。**这个报错信息里完全没有版本线索**，不记下来下次还得重新排查一遍（VC++ 运行库、CPU 指令集、jar 完整性全排除了才算到版本头上）。

守着这些结论的测试：`src/test/java/com/xiaohua/star/ai/LocalEmbeddingModelTest.java`，**不启 Spring**（要验的恰恰是本地模型能否脱离框架跑）：

```
export JAVA_HOME=/e/Java/jdk-21.0.5 && mvn test -Dtest=LocalEmbeddingModelTest -DfailIfNoSpecifiedTests=false
```

**M0 之后唯一还没跑通的是 rerank**：官方 `OnnxScoringModel` 只收模型文件路径、**不打包模型**，所以模型文件从哪来（ModelScope / hf-mirror）还没定，见 [21](21-本地Embedding与Rerank.md)。

### 一个必须坚持的顺序

**M1.5 要在 M1 之前做。**

原因：M1 会把 embedding 从远端 1536 维换成 本地 512 维，检索质量**一定会变**（可能变好也可能变差）。如果没有 M1.5 的基线，就分不清质量变化是「换了模型」造成的，还是「换模型时把某个参数改错了」造成的。评测集在这里的作用不是给学生打分，是给**改动做归因**。

顺带一提，M1.5 本身还有个额外好处：它会把「检索质量到底怎么样」这件事第一次量化出来——在此之前所有判断都是凭感觉。

## 七、阶段划分

| 阶段 | 包含里程碑 | 目标 | 状态 |
|---|---|---|---|
| **Phase 1** | — | 骨架 + user 模块，端到端跑通 | ✅ 已完成 |
| **Phase 2** | M0–M3 | RAG 从远端搬到本地，评测体系先立起来 | ✅ M0–M3 已完成（M1.5 评测基线未做，见 [60-离线评测](60-离线评测.md)） |
| **Phase 3** | M4–M6 | 会话、记忆、流式——「能用起来」 | 🟡 M4 / M5 已完成，M6 最小版已完成（2026-10-12） |
| **Phase 4** | M7–M10 | 工具调用 + 中断续跑——「像 Agent 了」 | 🟡 M7 / M8 已完成（2026-10-14）；M9–M10 待做 |
| **Phase 5** | M11–M13 | 知识库管理、可观测性、前端联调——「能交付」 | 待开始 |

Phase 2 先于 Phase 3 的理由：RAG 是对话的**能力来源**，记忆和流式是**交互体验**。先把能力做扎实，再包裹体验。反过来做的话，会得到一个交互很流畅但答不出正确内容的空壳，而那时再改检索，前面所有联调都要重来。
