# 混合检索与融合

> 本篇讲检索链路的核心：**怎么把「召回了什么」变成「排出最相关的几条」**。
> 上游是 [22 知识库与文档生命周期](22-知识库与文档生命周期.md)（切片怎么来的），
> 下游是对话层（把检索结果拼进 prompt）。向量化/重排模型本身见 [21](21-本地Embedding与Rerank.md)。
> 增量维护（改了文档只重建这一篇）见 [24](24-增量索引.md)。

## ① 这个模块治的是哪类病（通用问题定义）

### 问题定义

检索要回答两个**不同**的问题，它们对应链路的两个阶段，也对应两类完全不同的失败：

| 阶段 | 要回答 | 失败长什么样 | 靠什么压 |
|---|---|---|---|
| **召回（recall）** | 真答案**有没有被捞进来** | 库里明明有，却一条都没召回到 | 切片质量、embedding、**多路召回** |
| **精度（precision）** | 捞进来的一堆里**谁最相关** | 召回了相关的，但也混进一堆无关的，模型被带偏 | **重排（rerank）**、来源多样性 |

**这两类失败必须分开治**，因为一个阶段的手段救不了另一个阶段：召不回来的东西，后面排序再准也没用；而召回进来的一堆噪声，只能靠排序压下去。

### 单路召回各自的盲区

只用一路召回，一定会在某一类查询上翻车：

| 召回方式 | 擅长 | 盲区 |
|---|---|---|
| **向量（稠密）** | 语义相近、同义改写（「年假」↔「带薪休假」） | **专有名词、术语、编号**——向量化会把「布隆过滤器」「Seata」「第一条」这类精确 token 平滑掉 |
| **BM25（稀疏/字面）** | 精确 token 命中，术语、代码符号、人名 | 同义改写完全无效（用户换个说法就召不回） |

两路的盲区**几乎不重叠**，所以把它们各召回一批、融合起来，覆盖面天然比单路宽——这就是「混合检索」。

> 有一个容易混淆的点：**本项目 M1 实测发现向量分数的绝对区分度很差**（无关问题「今天天气怎么样」得 0.676，相关 0.783，只差 0.1，见 [20](20-RAG-概述与LangChain4j官方链路.md) §⑤）。这**正是**混合检索的立项依据：既然向量自己也分不清谁相关，就多给它一路参考（BM25 的字面命中是极强的相关信号），并交给重排模型做最终判决。

### 位置与边界

```
query ──► [向量召回] ──┐
          [BM25召回] ──┴──► 【融合 RRF】 ──► 【rerank 重排】 ──► 【来源多样性】 ──► topK
```

| 归它管 | 不归它管 |
|---|---|
| 多路召回**怎么合并**、候选**怎么排序** | 文本 ↔ 向量怎么算（[21](21-本地Embedding与Rerank.md)） |
| 最终交出几条、每篇文档占几格 | 文档怎么切、怎么入库（[22](22-知识库与文档生命周期.md)） |
| 单路失败时的降级 | 索引**怎么增量更新**（[24](24-增量索引.md)） |
| | 查询改写（把口语问题改写得更适合检索）——**本项目暂不做** |

### 四类典型失败模式

1. **量纲不可加。** 向量余弦分在 `[-1,1]`，BM25 分无上界；直接把两路分数相加，等于默认「BM25 分大的那路说话更响」，结果被 BM25 的尺度绑架。→ 这就是选 RRF（只用排名，不看分数）的原因。
2. **同一篇文档霸屏。** 相邻切片自带重叠，一篇内容多的文档可能占满 topK，把格子浪费在近似重复的内容上。→ 靠来源多样性（每源上限）压。
3. **单个环节挂掉拖垮整条链。** 向量库连不上 / 重排模型报错，不该让整个检索返回空或抛错。→ 每路独立降级（见 §④）。
4. **融合顺序被误当最终顺序。** RRF 分只是「融合出候选并粗排」，它不代表最终相关性；有重排时必须用重排分覆盖。（本项目里表现为：`score` 到底是谁的分，见 §⑤。）

## ② LangChain4j 官方怎么做

官方文档：<https://docs.langchain4j.dev/tutorials/rag>（本项目 1.20.0 / 1.20.0-beta30）。

| 职责 | 官方类 | 提供的 | 不提供的 |
|---|---|---|---|
| 单路召回 | `ContentRetriever`（`EmbeddingStoreContentRetriever`、`WebSearchContentRetriever`） | **一次向量召回** | 多路合并、BM25 |
| 结果重排/聚合 | `ContentAggregator`（`ReRankingContentAggregator`、`DefaultContentAggregator`） | 用 `ScoringModel` 重排、去重、限流 | 融合异构召回源 |
| 整链编排 | `RetrievalAugmentor`（`DefaultRetrievalAugmentor`） | 查询改写 → 召回 → 聚合 → 注入 prompt | —— |
| 查询改写 | `QueryTransformer`（`CompressingQueryTransformer` / `ExpandingQueryTransformer`） | 把问题改写/扩展 | —— |

**官方不提供的是「融合异构召回源」这一步。** `ContentRetriever` 的语义是「一条路召回」（`EmbeddingStoreContentRetriever` 只会做向量检索），多个 retriever 的结果在 `ContentAggregator` 里是被**合并去重**，而不是按排名做 RRF 融合——它缺的正是「把向量排名和 BM25 排名投票合成一张分表」这一步。所以混合检索的融合逻辑**必须自研**。

> **注意版本与模块**：Milvus 的 `langchain4j-milvus-v2`（1.19+，需 Milvus 2.6.x 服务端）在**存储层**提供了服务端 BM25 + RRF 的 `SearchMode.HYBRID`。但我们用的是 legacy `langchain4j-milvus`（Milvus 2.5.27，见 [01](01-总体架构与路线图.md) 的那笔债），没有这个能力，所以融合只能放在应用层自己写。这也是「用 legacy」这个取舍的一个连带成本。

## ③ 本项目为什么这么落地

**核心决策：直接移植 salary-leap 的检索内核，而不是照官方 Modular RAG 重搭。**

理由：salary-leap 那套（`Bm25Index` + RRF 融合 + rerank 回退 + 来源多样性）**已经在真实评测集上验证过**。重搭一遍官方组件，等于把「已知能跑、且被评测过」的东西换成「没验证过的」，收益为负。移植的改动集中在两处：

| 改造点 | salary-leap | 本项目 | 为什么必须改 |
|---|---|---|---|
| **索引粒度** | **全局一个** BM25 索引（单集合，启动时建） | **每库一个**（`Bm25IndexRegistry` 按 `kbId` 持有，惰性构建） | 我们是「每库一 Milvus 集合」（见 [22](22-知识库与文档生命周期.md)），检索只在一个库内做；且文档运行时增删 |
| **融合键** | 文本 `trim()`（因为没有稳定 id，见其 `accumulateRrf` 注释） | **`vectorId`**（确定性 UUID，见 [22](22-知识库与文档生命周期.md)） | 稳定 id 比文本精确，且能直接回表取详情，不用两套组装逻辑 |

**用什么、自研什么**：

| 环节 | 用现成的 | 自研 |
|---|---|---|
| Rerank 打分 | `ScoringModel`（`ObjectProvider` 注入，`ai.rerank.enabled` 开关） | —— |
| 向量召回 | `MilvusEmbeddingStore.search` | —— |
| **BM25 索引** | —— | ✅ 移植（`ai/Bm25Index`，中文 bigram，无外部依赖） |
| **RRF 融合** | —— | ✅ `ai/RrfFusion`（纯函数，可单测） |
| **来源多样性** | —— | ✅ `KnowledgeSearchServiceImpl.selectDiverse` |
| **多路编排与降级** | —— | ✅ `KnowledgeSearchServiceImpl` |

**为什么不用 `DefaultRetrievalAugmentor` 编排整条链？** 它的抽象是「一批 retriever → 一个 aggregator → 注入 prompt」，但我们要在中间塞 RRF、按 `vectorId` 回表、按 `docId` 做多样性——这些都和自有数据结构（切片、文档）强耦合。用它得先把自己的候选塞进 `Content`/`TextSegment` 再解释回自己的模型，绕。这与 [01](01-总体架构与路线图.md) 第三节的立场一致：官方当零件用，编排自研。

## ④ 数据结构与流程时序

### 全流程

```
query
 │
 ├─(1)─► 向量召回：embedQuery → Milvus.search(maxResults=vectorRecall, minScore) → [id 按分数降序]
 │            失败 → warn + 空列表（由 BM25 顶上）
 │
 ├─(2)─► BM25 召回：Bm25IndexRegistry.search(kbId, query, bm25Recall) → [id 按 BM25 降序]
 │            失败 / hybrid 关闭 → 空列表
 │
 ├─(3)─► RRF 融合：两路排名累加进同一张分表 → 按融合分降序取前 maxCandidates
 │
 ├─(4)─► 回表取详情：按 vectorId 批量查 knowledge_chunk + knowledge_document → 组装 Hit
 │            （Milvus 只给 id 和分数；正文、文档名一律回 MySQL）
 │
 ├─(5)─► rerank（可选）：候选数 > topK 时调 ScoringModel 重排
 │            抛异常 / 分数数量不匹配 → 退回融合顺序
 │
 └─(6)─► 来源多样性：按 docId 限制每源上限，不足时用跳过的补齐 → topK 个 Hit
```

### RRF 伪代码

```
fused = {}                      # id -> 融合分
for list in [vectorIds, bm25Ids]:
    for rank, id in enumerate(list):     # rank 从 1 开始
        fused[id] += 1 / (k + rank)      # k = rrfK（默认 60）

candidates = top(fused, maxCandidates)   # 按分降序截断
```

**为什么是 `1/(k+rank)` 而不是别的**：它单调递减（排名越高分越大），且有上界 `1/(k+1)`，
所以多路累加不会让「某一路独自霸榜」的分碾压「两路共识」的分。`k` 起平滑作用：
`k` 越小，第一名相对第二名的优势越大（越激进）；`k=60` 是原论文默认值。

### M1→M3 实测：RRF 的「投票」在分数上是看得见的

用两篇文档（`handbook.txt`、`long.txt`，共 3 个切片）+ 4 条 query 实测（`rrf-k=60`，rerank 关闭）：

| query | 相关？ | top1 得分 | 观察 |
|---|---|---|---|
| 年假有多少天 | 相关 | **0.0328**（`≈1/61+1/61`） | 向量和 BM25 **两路都投了它** → 分翻倍 |
| 远程办公怎么申请 | 相关 | **0.0328** | 同上，命中正确文档 |
| 二级以上医院的诊断证明 | 相关 | **0.0328** | 字面短语，BM25 强命中 |
| 今天天气怎么样 | **不相关** | 0.0164 / 0.0161 / 0.0159 | 三条全是**单路分**（`1/61、1/62、1/63`）——**两路没有共识** |

两条可直接用的结论：

1. **`0.0328`（双路共识）与 `0.016x`（单路）是两个台阶**，这给了一个「两路是否都认可」的弱信号。
   但**它不是相关性阈值**——不相关查询也会拿到单路分。别把它当 `minScore` 用。
2. **对比关掉 hybrid**：同一批 query 的分数变成清一色单路值（`0.0164/0.0161/0.0159`），
   且「远程办公怎么申请」里 `handbook.txt`（也含「申请」）从第 2 掉到第 3——**这就是 BM25 那一路确实在起作用的直接证据**。

### 参数表（`knowledge.search.*`，**全部未标定**）

| 配置键 | 默认 | 含义 | 状态 |
|---|---|---|---|
| `hybrid-enabled` | `true` | 关掉退化成 M1 的纯向量检索 | — |
| `vector-recall` | `20` | 向量这一路召回多少候选 | **未标定**，待 [60](60-离线评测.md) |

### BM25 索引的失效点（⚠️ 漏一个就出问题）

BM25 索引是**纯内存、每库一份、惰性构建**的。凡是改变库内切片的操作，都必须让它失效，
否则会出现「新文档搜不到 / 删掉的还能搜到」。当前调用点（`bm25IndexRegistry.invalidate`）：

| 调用点 | 所在方法 |
|---|---|
| 文档索引结束（**成功或失败都算**，失败也可能已写了切片行） | `KbIndexServiceImpl.indexDocument` 的 `finally` |
| 删除文档的向量后 | `KbIndexServiceImpl.deleteVectors` |
| 重建知识库开始前 | `KbIndexServiceImpl.submitRebuild` |
| 删除知识库 | `KnowledgeBaseServiceImpl.delete`（用 `remove` 顺带清构建锁） |

### 代码落点

| 能力 | 类 |
|---|---|
| BM25 索引（中文 bigram，不可变快照） | `ai/Bm25Index` |
| 每库索引的持有与惰性构建 | `ai/Bm25IndexRegistry` |
| RRF 融合（纯函数） | `ai/RrfFusion` |
| 多路编排 / 重排 / 多样性 | `service/impl/KnowledgeSearchServiceImpl` |
| 参数 | `config/SearchProperties` |
| 多库合并（对话侧） | `ai/RetrievalContextBuilder` |

### 多库合并（对话侧，2026-10-13）

`KnowledgeSearchService.search` 是**单库**接口，但一个会话可关联多个知识库。对话侧接入时（`ai/RetrievalContextBuilder`）**不能把各库结果按 `score` 全局排序再截断**：

- RRF 分只由**名次**决定——每个库的 rank-1 恒为 `1/(k+1) = 1/61`，跨库全是并列，按 score 排等于按「库的顺序」排，毫无意义；
- 即使 rerank 开着，各库候选规模不同，分数也难保证同量纲。

**做法**：各库给个小 `topK`（对话侧用 3）→ 按 `chunkId` 去重 → **round-robin 交错**各库结果（各库第 1 名 → 各库第 2 名 → …）→ 取上限（对话侧 5）。交错是为了避免「某一库命中多、霸屏」，与库内 `max-per-source` 的动机同源。

**边界**：每库 `topK` 与合并上限目前是 `RetrievalContextBuilder` 里的常量（3 / 5），**不是配置项**——等有评测数据再决定要不要提成 `ai.chat.*` 配置。某库被删 / 越权 / 模型不匹配时 `search` 会抛异常，对话侧逐个 catch 跳过，退化为少用/不用该库。

## ⑤ 边界、已知限制、踩过的坑

### 坑 1：**绝不能照抄 salary-leap 的 `MIN_SCORE = 0.2`**

salary-leap 的向量召回带了 `minScore=0.2`。但这个值是**远端 `text-embedding-v2`（1536 维）**的分数分布下定的。

本地 `bge-small-zh`（512 维）的分布完全不同：M1 实测，**完全不相关**的问题「今天天气怎么样」也拿到 **0.676**，和相关的 0.783 只差 0.1（见 [20](20-RAG-概述与LangChain4j官方链路.md) §⑤ 的实测表）。`0.2` 对本地模型等于「不过滤」。

所以本项目 `min-score` **默认 `0.0`（不过滤）**，并且**故意不给一个拍出来的默认阈值**——真要设，必须先用评测集标定（`未标定`，待 [60](60-离线评测.md)）。

**连带影响**：不过滤时，非空知识库对任何问题都会返回 topK 条，前端「没找到相关内容」的空状态只在「库为空」时出现。

> 教训抽象一下：**相似度阈值是模型相关的，不能跨模型搬运。** 换 embedding 模型时，连同阈值一起作废。

### 坑 2：BM25 索引惰性构建，首次检索某库会慢一拍

第一次检索某个知识库时，要读出该库**全部切片**建索引（`Bm25IndexRegistry.getOrBuild`），
库大时首查有明显延迟；之后走缓存。失效用「丢弃快照、下次重建」而非增量更新。
[24](24-增量索引.md) 只做了**向量侧**的增量，**BM25 仍是整库重建**。当前语料规模下够用，**库很大时要重新评估**。

### 坑 3：`score` 的语义随配置变

响应里的 `score` 是**最后一级输出的分数**：

| 配置 | `score` 是什么 |
|---|---|
| rerank 开启（`ai.rerank.enabled=true`） | rerank 模型分 |
| rerank 关闭（**无论 hybrid 开关**） | **RRF 融合分**，很小，约 `1/60` 量级 |

> rerank **已接入**（`bge-reranker-base` int8，见 [21](21-本地Embedding与Rerank.md)），但**默认关闭**——
> 本机内存不足以跑它的推理。所以现在线上实际生效的是第二行（RRF 分）。启用方法见 21 的内存坑。

> **注意第二行**：即使把 `hybrid-enabled` 关掉退化成纯向量，`score` **仍然是 RRF 分**（`1/(k+rank)`），
> 不是向量余弦——因为多路融合这一步对「只有一路的列表」同样生效（单路 RRF 恰好保持向量顺序）。
> 这一点实测确认过：关闭 hybrid 后同一批查询的 `score` 是 `0.0164/0.0161/0.0159`（即 `1/61、1/62、1/63`），
> 不是 `0.6~0.8` 的余弦值。

两种量纲不同，所以 `score` **只适合相对比较**，前端绝不能当百分比展示（[frontend/50](../frontend/50-knowledge-知识库管理.md) 已写明）。

### 坑 4：所有参数都是「起点」不是「最优」

`vector-recall / bm25-recall / rrf-k / max-candidates / max-per-source` 全部沿用 salary-leap 的经验值。
**本项目语料不同（中文制度文档 vs 技术文章），这些值大概率不是最优。** 它们能跑，但没有依据说它们最好。
在 [60 离线评测](60-离线评测.md) 用评测集量出「混合比纯向量召回率高多少」之前，任何关于「哪个参数更好」的判断都是猜测。

### 没做的

| 没做 | 影响 | 备注 |
|---|---|---|
| **查询改写（`QueryTransformer`）** | 口语化问题直接检索，召回可能受影响 | 后置 |
| **增量更新 BM25** | 任何写入都整库重建索引 | [24](24-增量索引.md) 只做了向量侧增量，**BM25 增量仍未做** |
| **响应暴露「命中来自哪一路」** | 前端看不出某结果是被向量还是 BM25 召回的 | 契约没要求，排查时可用日志 |
| **参数标定** | 全部是经验值 | [60](60-离线评测.md) |
| **多语言/英文分词优化** | 英文按整词切，中文按 bigram | 当前语料以中文为主 |
