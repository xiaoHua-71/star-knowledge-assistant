# 会话与消息管理

## ① 这个模块治的是哪类病（通用问题定义）

**大模型是无状态的，而且进程重启就什么都不记得。** 要让「多轮对话」成立，产品必须把每一轮的消息**落到自己能长期保存的地方**，并在需要时**按正确的顺序取回来**。所以本模块要解决的本质问题是：

> **把用户与助手的一来一回，持久化成可长期保存、可按序取回、可编辑重发的记录。**

它和 [11-对话记忆](11-对话记忆.md) 是两件事，容易混：**本模块管「消息存在哪、怎么取」；记忆管「取回来之后，挑哪些、按什么预算拼进 prompt」**。本模块是记忆的**载体**——没有它，记忆无从谈起。

### 它的边界

| 归它管 | 不归它管 |
|---|---|
| 会话与消息的增删改查、分页 | 取回历史后**怎么裁剪**进 prompt（那是 [11-对话记忆](11-对话记忆.md)） |
| 消息的**顺序**（`seq`）与取回顺序 | token 逐个推给前端（那是 [31-流式输出SSE](31-流式输出SSE.md)） |
| 「截断重发」的落库语义 | 工具调用的执行与幂等（那是 [30-工具调用](30-工具调用.md)、[12-中断与恢复的状态机](12-中断与恢复的状态机.md)） |
| 会话归属校验（只能看自己的） | 用模型自动起标题（**待定**，本模块不承诺） |

### 三类典型失败模式

1. **顺序错乱。** 助手消息和用户消息可能在**同一毫秒**落库；用 `createTime` 排序，同毫秒内谁前谁后不确定。表现是偶发的「答在问前」。
2. **计数漂移。** 会话上冗余了一个 `messageCount`（用于列表展示，也用于生成下一条序号）。一旦它与真实行数不一致，序号就会**跳号或撞号**——撞号会直接触发唯一键冲突。
3. **删了又「复活」/ 重发撞键。** 「截断重发」（用户改了自己的话重发）要求把被删的序号**腾出来**再写一次。如果删除是逻辑删（行还在），唯一键会被旧行占着，重发就插不进去。

（还有一类：越权读到别人的会话——这是所有「按 id 取资源」接口的通病，对策是每次操作都校验归属。）

官方文档：<https://docs.langchain4j.dev/tutorials/chat-memory/>

和「持久化」直接相关的是两个概念（**模块归属已按 `1.20.0` 的 sources jar 实测确认，见 [11-对话记忆](11-对话记忆.md)**）：

| 类 / 接口 | 作用 |
|---|---|
| `dev.langchain4j.store.memory.chat.ChatMemoryStore` | **持久化 SPI**：`getMessages(Object id)` / `updateMessages(Object id, List<ChatMessage>)` / `deleteMessages(Object id)` |
| `dev.langchain4j.memory.ChatMemory` | **容器**语义：`add` / `messages` / `clear`，容器内部用一个 `ChatMemoryStore` 落盘 |

官方给了一批 `ChatMemoryStore` 实现（Redis、CosmosDB、Cassandra、Neo4j……），也有默认的 `InMemoryChatMemoryStore`。

**官方这套东西明确不管的**：分页、按业务序号排序、用户可见的「删除某条消息」、以及「截断重发」。它把消息当成一段**不透明的会话缓冲**（整个会话一把存取），而我们的消息是**要展示、要分页、要单条删除、要审计**的业务数据。**这个错位，是本模块必须自研的根本原因。**

**版本**：本项目用 `langchain4j-core:1.20.0` + 聚合模块 `langchain4j:1.20.0`（见 [01-总体架构与路线图](01-总体架构与路线图.md)）。升级时回来核对这两个类有没有换模块。

## ③ 本项目为什么这么落地

### 结论：不用 `ChatMemoryStore`，自研两张表

理由和 [11-对话记忆](11-对话记忆.md) 完全一致（那里已论证）：**双写一致性问题**。消息本身就是业务数据，已经存在 `conversation_message` 里；再往 `ChatMemoryStore` 里存一份，就会出现「用户在界面上删了一条，框架的 store 里还留着，模型下一轮依然记得」。要么每次删都同步两个 store（引入事务边界之外的写，失败即不一致），要么接受不一致——两条路都不好。**所以正确的做法是不存第二份。**

**但保留官方的数据模型**：最终喂给 `ChatModel` 的仍是官方的 `ChatMessage` 及其子类（`SystemMessage` / `UserMessage` / `AiMessage`）。这些类型是厂商适配层认的，自己造一套再转换只会引入字段丢失和格式差异。分工见 [11](11-对话记忆.md) 的表。

### 消息的两种「删」不能混

| | `conversation`（会话） | `conversation_message`（消息） |
|---|---|---|
| 删除方式 | **逻辑删**（`isDelete=1`） | **物理删**（真的 `DELETE`） |
| 为什么 | 删除后仍要保留会话壳，用于列表过滤与审计 | `uk_conversationId_seq(conversationId, seq)` 要能被**重新占用**，否则截断重发撞唯一键 |

`conversation_message` **刻意没有 `isDelete` 字段**。全局逻辑删（配置在 `application.yml` 的 `logic-delete-field: isDelete`）只对**自己声明了 `isDelete`** 的实体生效；没有这个字段的实体不受影响——所以它的 `delete()` 是真的 `DELETE`。**这是个绊线**：谁要是「顺手」给这个实体加上 `isDelete`，就会静默地把真删变成假删，截断重发随即报唯一键冲突。

### 顺序用显式 `seq`，不用时间戳

`createTime` 只到毫秒（`DATETIME(3)`），而流式输出时助手消息可能在用户消息之后**几毫秒**内写入；同一毫秒内多条消息的顺序也不确定。所以用一个显式的会话内序号 `seq`（从 1 开始）作为**唯一权威顺序**——重建 prompt 的顺序和前端展示的顺序都以它为准。

`seq` 的生成方式是 `seq = conversation.messageCount + 1`。`messageCount` 既是列表展示的「共几条」，也是序号发生器，两者在同一个事务里更新，不会不一致。

**为什么不用 `SELECT max(seq)+1`**：截断（真删）之后 `max(seq)` 会**回退**，而 `messageCount` 不会——于是 `max+1` 与 `messageCount+1` 会给出不同的值，且 `max` 还得再查一次。让 `messageCount` 当唯一真相，只用它，简单且自洽。

### 并发下的 `seq`：会话行锁 + 短事务

两个请求同时往**同一个会话**追加消息，如果各自「读 `messageCount` → 算 `seq` → 写」，就会读到同一个值、生成同一个 `seq`，第二条插入直接撞 `uk_conversationId_seq`。对策：**追加前先对该会话行加锁**（`SELECT ... FOR UPDATE`），把「读计数 → 写消息 → 改计数」放进一个**短事务**。

**关键约束：事务绝不能跨越模型调用。** 模型调用是几十秒的远程 I/O，把它包进事务会让数据库连接和会话行锁被占住几十秒（连接池耗尽、同会话后续请求全部排队）。所以一次对话是**两个短事务**：先落用户消息（事务 1），再在事务外调模型，最后落助手消息（事务 2）。中间失败就留下一条「孤儿用户消息」——补救手段正是截断重发（见坑 6）。

### 非流式 `/chat/message` 是**权宜实现**

本模块顺带提供一个**非流式**的对话接口（`POST /api/chat/message`），一次性返回整段回答。它的定位是**权宜**：

- **没有检索**：不会去知识库找资料（那是 [23-混合检索与融合](23-混合检索与融合.md) 的活，留给后续接入）。
- **没有 run**：不创建 `agent_run`，因此没有中断 / 续跑 / 重连——那些是 [12-中断与恢复的状态机](12-中断与恢复的状态机.md) / [31-流式输出SSE](31-流式输出SSE.md) 的范畴。
- 它存在的意义：在流式（M6）落地之前，先让「一问一答落库」这条主链路**端到端可验证**，也方便脚本 / 冒烟测试。

**什么时候该删掉它**：当流式成为唯一交互方式、且非流式不再被任何调用方（脚本、定时任务、健康检查）依赖时。在那之前它比流式少一大块错误处理，维护成本低。

## ④ 数据结构与流程

### 两张表

字段与类型见 [10-数据模型总览](10-数据模型总览.md)，DDL 在 `sql/conversation_tables.sql`。这里只列**影响逻辑的字段**：

`conversation`（会话）：

| 字段 | 作用 |
|---|---|
| `userId` | 归属，每次操作都要校验 |
| `title` | 标题，默认「新会话」 |
| `kbIds` | 关联知识库，**逗号分隔字符串**（空表示不用 RAG）。只按会话查库、不需反向查，故不建关联表（改成关联表的条件见 [10](10-数据模型总览.md)） |
| `pinned` | 置顶，列表排序第一位因素 |
| `messageCount` | 消息数，**同时是 `seq` 发生器** |
| `lastMessageTime` | 列表排序第二位因素 |
| `isDelete` | 逻辑删 |

`conversation_message`（消息）：

| 字段 | 作用 |
|---|---|
| `seq` | **会话内序号，唯一权威顺序** |
| `role` | `USER` / `ASSISTANT`（本模块只写这两种） |
| `content` | 正文 |
| `toolCallsJson` | 该轮用过的工具**原始 JSON**，**仅供展示 / 审计，绝不进 prompt**（见坑 4） |
| `promptVisible` | 是否参与 prompt 重建，默认 1 |
| `tokenCount` | token 数（可空） |
| （无 `isDelete`） | **真删** |

### 五个流程

**创建**：`title` 默认「新会话」，`kbIds` 列表格式化成逗号串（空 → NULL），`messageCount=0`。

**列表**：按 `pinned DESC, lastMessageTime DESC` 排序（置顶在前、最近说话的在前；`lastMessageTime` 为 NULL 的新会话排最后）；只返回当前用户的、未删的。

**消息分页**：按 `seq DESC` **取**最近一页，但**页内反转成正序返回**。这样 `current=1` 看到最新的一屏、且屏内是正序；`current` 递增拿到的是**更早**的一批（前端插到列表头部，不要替换）。

**截断重发**（`POST /conversation/message/delete {conversationId, fromSeq}`）：删掉 `seq >= fromSeq` 的**全部**消息（真删），并把 `messageCount` 按**实际删除行数**回退。返回删除条数。

**一次对话（非流式）**：

```
1. 校验会话归属（不存在 → 40400，非本人 → 40101）
2. 取 ChatModel（没配 key 时该 bean 不存在）→ 缺则 50001，且在此之前不写任何数据
3. 落用户消息（事务 #1）：seq = messageCount+1；messageCount ← seq；lastMessageTime ← now
4. 取该会话全部 promptVisible=1 的消息，按 seq 升序
5. 组装 prompt：首条 SystemMessage（常量），其余 USER→UserMessage、ASSISTANT→AiMessage（只取 content）
6. 调模型（事务外）：失败则转 50001，助手消息不落库
7. 落助手消息（事务 #2）：seq = messageCount+1
8. 返回助手 MessageVO
```

`appendMessage` 的伪代码（事务边界就在这里）：

```
@Transactional
appendMessage(conversationId, userId, role, content):
    c = SELECT * FROM conversation WHERE id = ? FOR UPDATE     # 锁会话行
    if c is null:        raise NOT_FOUND(40400)
    if c.userId != userId: raise NO_AUTH(40101)
    seq = c.messageCount + 1
    INSERT INTO conversation_message(conversationId, seq, role, content, promptVisible=1, ...)
    UPDATE conversation SET messageCount = seq, lastMessageTime = now WHERE id = ?
    return 插入的消息
```

## ⑤ 边界、已知限制、坑

### 没做的

| 没做 | 影响 | 什么时候需要做 |
|---|---|---|
| **token 预算裁剪** | 历史全量拼进 prompt；对话一长，超上下文窗口 → 请求失败 | M5（[11-对话记忆](11-对话记忆.md) 的 `MemoryBuilder`） |
| **自动起标题** | 标题一直是「新会话」 | 需要时再加（用模型据首条消息生成） |
| **历史全文搜索** | 不能按关键词找旧消息 | 用的时候加 |
| **删除会话级联删消息** | 删会话后消息行仍在库（不可达，仅审计） | 一般不需要；级联会丢审计 |
| **RUNNING 运行拦截截断** | 运行进行中也能截断 | M8（有了 `agent_run` 再加校验） |

### 坑

#### 坑 1：用 `createTime` 排序

**现象**：偶发「答在问前」，或同毫秒两条消息顺序随机。

**原因**：毫秒精度不足以区分助手 / 用户消息的写入顺序；同一毫秒多行顺序不确定。

**规避**：一律用 `seq` 排序与取回，任何地方都不许用时间排序。

#### 坑 2：`messageCount` 与实际行数漂移

**现象**：新消息的 `seq` 跳号（中间缺号），或插入直接报唯一键冲突。

**原因**：`messageCount` 被更新了，但实际行数不是那个值（例如截断时按「`messageCount - fromSeq + 1`」**推算**删除数，而实际删掉的行数并不等于它）。

**规避**：**按实际删除行数回退**——`messageCount = max(0, messageCount - 实际删除行数)`。删除语句的返回值就是真实行数。

#### 坑 3：给 `conversation_message` 加 `isDelete`

**现象**：截断重发时报唯一键冲突（`uk_conversationId_seq`）。

**原因**：一旦这个实体有了 `isDelete`，全局逻辑删接管——删除变成 `UPDATE isDelete=1`，旧行仍然占着唯一键；重发要插同一 `(conversationId, seq)` 就撞键。

**规避**：这张表**永远不要加 `isDelete`**。实体上的注释就是绊线。

#### 坑 4：把 `toolCallsJson` 拼进 prompt

**现象**：模型 API 报错（有工具调用请求、没有对应结果），且信息含糊。

**原因**：`toolCallsJson` 存的是**原始工具调用 JSON**，格式与 `assistant(tool_calls)` 消息要求的**不一致**，而且**没有配套的工具结果**。当成消息塞进 prompt 会违反「请求与结果成对」规则（见 [11](11-对话记忆.md) 规则 2/3）。

**规避**：重建 prompt 时 `ASSISTANT` 消息**只取 `content`**；`toolCallsJson` 只用于前端展示与审计。代码里要有注释，因为非常反直觉。

#### 坑 5：并发下的 `seq` 撞号

**现象**：同一会话快速连发两条，第二条插入报唯一键冲突。

**原因**：「读计数 → 写消息 → 改计数」没有互斥，两个请求读到同一个计数。

**规避**：追加消息前对该会话行 `SELECT ... FOR UPDATE`，且把这段放进**不含远程调用**的短事务。**不得**把模型调用包进这个事务。

#### 坑 6：模型失败留下孤儿用户消息

**现象**：模型调用失败后，历史里有一条用户消息、没有对应回答；用户重试会再落一条同样的用户消息。

**原因**：用户消息在调模型**之前**就落库了（与流式一致：建流成功即落用户消息）。这是**有意为之**——先落库，进程崩了才知道用户问过什么。

**规避**：这是设计取舍，不是 bug。补救是**截断重发**（前端已具备：删掉 `seq >=` 那条再发）。若将来要「自动回滚」，需引入运行状态机（M8）。
