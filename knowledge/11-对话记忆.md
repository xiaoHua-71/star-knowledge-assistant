# 对话记忆

## ① 这个模块治的是哪类病（通用问题定义）

**大模型是无状态的**：它不记得上一次对话。所以每次请求都必须把「需要它知道的历史」重新发送一遍——这不是设计缺陷，是 API 的形态。

但上下文窗口有上限，而**超出上限的表现是请求直接失败**（不是自动截断，也不是丢弃最早的消息）。所以「记忆」这个模块要解决的本质问题是：

> **在一份固定的 token 预算里，决定放哪些历史消息进去、丢哪些。**

### 它的边界

| 归它管 | 不归它管 |
|---|---|
| 决定哪些历史消息进 prompt | 消息**存在哪**、怎么查（那是持久化的事） |
| 在预算内做取舍、按规则裁剪 | 把长对话**压缩成摘要**（那是独立的「总结」策略，本模块不做） |
| 保证裁剪后消息结构合法 | 控制模型输出的长度（那是 `maxTokens` 参数） |

**中间那一行是常见的误解**：很多人以为「记忆 = 摘要压缩」。其实摘要只是诸多策略之一，而且它有自己的代价——摘要有信息损失，且**额外调用一次模型**（多一次成本和延迟）。本模块先做最朴素的「滑动窗口 + 预算限制」，不引入摘要。

### 三类典型失败模式

1. **预算超出 → 请求失败。** 这是硬失败，用户看到的是报错。
2. **结构被破坏 → 请求失败。** 工具调用请求和它的结果必须**成对出现**。裁剪时如果把 `assistant(tool_calls)` 丢了却留下 `tool(result)`，模型 API 会直接拒绝（因为它收到一个「结果」却找不到对应的「请求」）。这类错误信息通常很含糊，极难定位。
3. **成本随轮次线性上涨。** token 用量每轮增长，第 30 轮的请求可能比第 3 轮贵 10 倍。这不是 bug，但需要被意识到——所以裁剪除了「防超窗」，也在控成本。

官方文档：<https://docs.langchain4j.dev/tutorials/chat-memory/>

**核心接口与类**。下面这些类的**模块归属**已用 `1.20.0` 的 sources jar 实测确认过（2026-09-21）——注意它们**不在同一个 jar 里**：

`dev.langchain4j:langchain4j-core`（放接口和 SPI）：

| `dev.langchain4j.store.memory.chat.ChatMemoryStore` | 持久化 SPI |
| `dev.langchain4j.store.memory.chat.InMemoryChatMemoryStore` | 默认实现，进程内存 |
| `dev.langchain4j.model.TokenCountEstimator` | token 计数接口（`TokenWindowChatMemory` 依赖它） |

`dev.langchain4j:langchain4j`（聚合模块，放具体实现和服务层）：

| 类 / 接口 | 作用 |
|---|---|
| `dev.langchain4j.memory.chat.MessageWindowChatMemory` | 按**条数**保留最近 N 条的**实现** |
| `dev.langchain4j.memory.chat.TokenWindowChatMemory` | 按 **token 数**保留的实现 |
| `dev.langchain4j.memory.chat.ChatMemoryProvider` | 按 `@MemoryId` 给每个会话创建独立记忆 |
| `dev.langchain4j.service.AiServices` | 把接口变成 AI 服务的入口 |
| `dev.langchain4j.service.MemoryId` | 注解，把方法参数标记为会话 id |

**所以 pom 里 `core` 和聚合模块两个都要显式引**，别只引 core 然后指望传递依赖带全。

**关于取哪个版本**：本项目用 **`langchain4j-core:1.20.0` + `langchain4j:1.20.0`**（集成模块是 `1.20.0-beta30`，见 [01-总体架构与路线图](01-总体架构与路线图.md)）。**升级 LangChain4j 时这一段要重新核对**——类可能换模块，这个坑我们刚踩过一次。

**几个值得借鉴的细节**：

| 类 / 接口 | 作用 |
|---|---|
| `dev.langchain4j.memory.ChatMemory` | 记忆容器。核心方法 `add(ChatMessage)`、`messages()`、`clear()` |
| `dev.langchain4j.memory.chat.MessageWindowChatMemory` | 按**条数**保留最近 N 条 |
| `dev.langchain4j.memory.chat.TokenWindowChatMemory` | 按 **token 数**保留最近若干条 |
| `dev.langchain4j.memory.chat.ChatMemoryProvider` | 按 `@MemoryId` 给每个会话创建独立的 `ChatMemory` |
| `dev.langchain4j.store.memory.chat.ChatMemoryStore` | 持久化 SPI：`getMessages(Object)` / `updateMessages(Object, List<ChatMessage>)` / `deleteMessages(Object)` |
| `dev.langchain4j.store.memory.chat.InMemoryChatMemoryStore` | 默认实现，**进程内存，重启即丢** |
| `dev.langchain4j.service.MemoryId` | 注解，把方法参数标记为会话 id |

**官方内置的两个策略，各有几个值得借鉴的细节：**

`MessageWindowChatMemory` 不只是「保留最近 N 条」，它还做了两件正确但容易忽略的事：

1. **系统消息永远保留。** 它不会被计入窗口被淘汰——否则聊得久了，系统提示词自己先被挤出去，模型行为会莫名其妙地变。
2. **自动清理孤儿工具消息。** 当一个 `assistant(tool_calls)` 被窗口挤出去时，它对应的 `tool(result)` 会被一起清掉。这正是上面第 2 类失败模式的对策——**官方已经帮你想到了这一点**。

`MessageWindowChatMemory` 还有 `maxMessagesProvider`，支持动态窗口大小。

`TokenWindowChatMemory` 需要一个 `TokenCountEstimator`（因为要按 token 而不是条数算）。官方在 core 里提供了这个接口，但**具体模型的 tokenizer 要自己提供**——这是个隐藏成本。

**关于持久化：** `ChatMemoryStore` 是个 SPI，官方给了一批现成的实现（Redis、CosmosDB、Cassandra、Neo4j、Oracle、Tablestore……，见 <https://docs.langchain4j.dev/integrations/chat-memory-stores/>）。**但这些集成模块不在本项目的依赖里**，本项目也没打算用——理由见下一节。

**官方明确不做的事：** 摘要压缩。官方文档把「对话总结」放在另一处讲，`ChatMemory` 系列不做这件事。

## ③ 本项目为什么这么落地

### 结论：借用策略，不用它的容器

**`MessageWindowChatMemory` 的三个策略我们全都要**（窗口、系统消息常驻、工具消息成对清理），但**不用 `ChatMemory` 这个容器，也不用 `ChatMemoryStore`**。

### 理由：双写一致性问题

如果用了 `ChatMemoryStore`，系统里就有**两份**消息：

```
conversation_message （MySQL，业务数据）  ─┐
                                          ├─ 同一批消息，存两处
ChatMemoryStore     （框架容器）          ─┘
```

而我们的消息**本身就是业务数据**：要展示在界面上、要支持分页、要支持用户删除、要审计、要统计 token。这些需求都在 MySQL 那份上实现。

于是就会出现这类不一致：

> 用户在界面上删掉了一条消息 → MySQL 里的行删了 → 但 `ChatMemoryStore` 里还留着 → 下一次对话，模型依然「记得」那条被删掉的消息。

要么在每次删除时同步清理两个 store（引入了事务边界之外的写，失败就是不一致），要么接受不一致。**两条路都不好，所以正确的做法是不存第二份。**

### 那官方的抽象就白给了吗

不是。`ChatMemory` 接口的价值在于**它定义了「记忆」这个概念的操作集合**（添加、取全部、清空）。我们按它的语义自研一个 `MemoryBuilder`，核心方法签名甚至可以对齐。这样：

- 将来若要换成官方实现，边界是清晰的
- 别人读代码时，能直接对应上官方文档里的概念

### 只用官方的数据模型

`ChatMessage` / `UserMessage` / `AiMessage` / `SystemMessage` / `ToolExecutionResultMessage` 这套消息模型**直接用官方的**。理由：这些类最终要交给 `ChatModel` 发请求，官方模型适配层认的就是这套类型；自己造一套再转换，中间的字段丢失和格式差异会引入难查的问题。

所以本项目的分工是：

| 层 | 谁 |
|---|---|
| 消息**数据模型** | LangChain4j（`ChatMessage` 及其子类） |
| 消息**持久化** | 自研（`conversation_message` 表） |
| 记忆**裁剪策略** | 自研（`MemoryBuilder`） |
| 记忆**容器** | 不用（每次重建，见下） |

**「每次重建」是个关键设计**：不维护一个长期存活的记忆对象，而是在**每次 LLM 调用前**从数据库重建一次 prompt。理由是消息会随时变化（用户删除、截断重发、另一个标签页发了消息），维护一个内存态容器的失效逻辑比重建更贵。重建一次的成本是一条 `SELECT`，可以忽略。

## ④ 数据结构与流程

### 消息存在哪：一张表，两种角色

只有**用户消息**和**最终的助手消息**进 `conversation_message`（详见 [10-数据模型总览](10-数据模型总览.md)）：

| role | 什么时候写 | `content` | `toolCallsJson` |
|---|---|---|---|
| `USER` | 用户发消息时立即写 | 用户输入 | 无 |
| `ASSISTANT` | **一次运行结束时**写 | 最终回答文本 | 该轮调用过的工具**摘要**（供前端展示） |

**工具调用的中间消息（模型要求调工具、工具返回结果）不落 `conversation_message`，只落 `agent_step`。**

这个决定的理由：

1. **用户可见的对话里不该出现这种噪声。** 用户问一句、答一句，中间调了几次工具是他的「执行细节」，前端可以单独展示（从 `agent_step` 取），但不该混进对话正文。
2. **避免跨轮次的工具消息配对问题。** 上一轮的工具调用细节如果进了历史，重建 prompt 时就要处理「跨轮次的组装」，容易出错。而只保留「用户一句 / 助手一句」的话，历史天然是干净交替的。
3. **省 token。** 上一轮的工具调用参数和结果往往很长，而模型在下一轮通常不需要它们——只需要知道「上轮回答了什么」。

**因此本模块要处理的「工具消息配对」问题只存在于一次运行内部**（见下面的组装规则），比官方面对的情况更简单。

### 重建 prompt 的流程

```
输入：conversationId、当前用户消息、本次运行内已有的中间步骤（来自 agent_step）
输出：List<ChatMessage>，可直接交给 ChatModel

1. messages = []
2. 计算预算：
     historyBudget = contextWindow                  ← 模型上下文上限（待实测）
                   - reserveForOutput               ← 给输出留的（待实测）
                   - systemPromptTokens             ← 系统提示词占用
                   - retrievedChunksTokens          ← 检索片段占用（见 23-混合检索）
3. messages.add(SystemMessage)                     ← 系统提示词，永远第一位
4. 从 conversation_message 按 seq 倒序取历史消息（只要 promptVisible=1）
     逐条累积 token，直到 historyBudget 用完为止
     取到的消息按 seq 正序放回 messages
5. 追加本次运行内的中间步骤（从 agent_step 按 seq 正序取）
     ★ 整组操作：assistant(tool_calls) 和它下面的全部 tool(results) 一起加或一起不加
6. 追加当前用户消息（如果有检索片段，拼在用户消息里一起发）
7. 返回 messages
```

### 四条必须遵守的组装规则

| # | 规则 | 违反会怎样 |
|---|---|---|
| 1 | **系统消息永远保留**，不参与预算裁剪 | 聊久了系统提示词被挤掉，模型行为漂移 |
| 2 | **工具调用请求和结果必须成对**，裁剪时整组取舍 | 模型 API 报错，且错误信息含糊难查 |
| 3 | **不能以 `assistant(tool_calls)` 结尾**（必须有对应的结果） | 模型 API 报错：你让它调工具，却没给它结果 |
| 4 | **最后一条必须是当前用户消息** | 模型会答非所问（接着旧话题说） |

规则 2 和 3 是同一件事的两面。实现上最简单的做法是：**把「一轮工具交互」当作一个不可分割的组**，组内要么全要、要么全不要。

### 裁剪的粒度：按「组」而不是按「条」

```
一次运行内的中间步骤，按组划分：

  组 1: [assistant(tool_calls: searchKnowledge)] + [tool(searchKnowledge 的结果)]
  组 2: [assistant(tool_calls: createTicket)]    + [tool(createTicket 的结果)]
  组 3: [assistant(最终回答文本)]

裁剪时：组 3 → 组 2 → 组 1 依次丢弃（从旧到新），不会拆开任何一组。
```

### token 怎么算

**这是本模块最不确定的一处，必须诚实说明。**

理想做法是用模型的 tokenizer 精确计算。但：

- 远端 DashScope 的 qwen **没有提供 Java 的本地 tokenizer**
- 官方的 `TokenCountEstimator` 接口存在，但**实现要自己提供**
- 本地 embedding 模型有 tokenizer，但那和对话模型的 tokenizer **不是同一套**，算出来的数不能混用

所以本项目的做法是：**按字符数近似，并留安全余量。**

| 措施 | 说明 |
|---|---|
| 估算公式 | `tokens ≈ charCount × 系数`。中文的系数明显大于英文，具体值**待实测**（用 `ai_call_log` 里记录的真实 `promptTokens` 反推） |
| 安全余量 | 预算只用到上限的 80%，留 20% 吸收估算误差 |
| 校准数据来源 | `ai_call_log.promptTokens` 是真实值，`promptJson` 里有对应的 prompt 原文，两者一对照就能拟合出系数 |
| `conversation_message.tokenCount` | 落库时记录估算值，便于统计和校准 |

**为什么敢用估算？** 因为记忆裁剪的精度要求不高：预算用 80%、系数偏大 10%，结果只是「少放几条历史」——用户几乎无感。而精确计算的成本（维护两套 tokenizer、跨版本对齐）远大于收益。

**但这个取舍有前提**：如果将来要支持「精确控制成本」或「贴着上限塞满上下文」，就必须换成真实 tokenizer。这个前提变了，方案也要变。

## ⑤ 边界、已知限制、坑

### 没做的

| 没做 | 影响 | 什么时候需要做 |
|---|---|---|
| **摘要压缩** | 超长对话只能丢旧消息，早期的信息永久丢失 | 用户抱怨「它忘了我们开头说的」时 |
| **精确 token 计算** | 预算靠估算 + 余量 | 需要精确控成本时 |
| **跨会话记忆** | 每个会话独立，不会「记得你在别的会话说过什么」 | 需要「长期用户画像」时 |
| **向量化历史检索** | 不会从很久以前的历史里「检索相关片段」（RAG 只检索知识库，不检索对话历史） | 对话轮次多到几百轮时 |
| **消息编辑后的历史重写** | 用户改了旧消息，后面的回答不会重算 | 一般不需要（改了就重发） |

**第 4 条值得展开说**：业界有「把历史消息也向量化，按相关性召回」的做法（长对话记忆）。它解决的是「几百轮之后，早期相关信息已经被窗口挤掉」的问题。本项目不做，因为：

- 实现成本高（要对每条消息向量化、维护索引）
- 收益只有在**超长对话**场景才体现
- 而超长对话本身可能是产品设计问题（是否应该引导用户开新会话）

### 坑

#### 坑 1：裁剪时把工具消息拆散了

**现象**：长对话后突然报模型 API 错误，信息含糊；短对话完全正常。

**原因**：窗口从旧到新丢消息，丢到某一条 `assistant(tool_calls)` 时如果它的 `tool(result)` 没一起丢（或反之），消息序列就不合法了。

**规避**：按「组」裁剪（见上面）。**并且要有测试覆盖**——这类问题只在窗口边界处出现，手工测不出来。测试方法：构造一组消息，把窗口大小设成刚好卡在组中间，断言裁剪结果里没有落单的工具消息。

#### 坑 2：系统提示词被计价进了预算但没算准

**现象**：偶尔在很长的对话里报超窗，但按估算不应该超。

**原因**：系统提示词本身可能很长（几万字符，含工具说明和格式要求），如果没把它算进预算，实际可用预算就比以为的少。

**规避**：预算计算里显式减去 `systemPromptTokens`（见流程第 2 步）。**并且系统提示词变化时要重新校准**——加一个工具就可能多几百 token。

#### 坑 3：被中断的助手消息怎么处理

**现象**：用户点「停止」，助手消息存了半句。下一轮重新生成 prompt 时，这半句话要不要带进去？

**决策**：**带进去，保持原文。** 理由：

- 这半句话是真实的对话历史，删掉会让模型以为「上一轮什么都没说」
- 模型对「话说到一半停了」这种情况处理得还不错

**但要额外做一件事**：被中断的消息如果**只生成了几个字**（比如不到 10 个字符），**不落库**。因为那种消息对上下文毫无价值，反而会干扰模型（它会以为自己说的话是「嗯，好的，那」这种碎片）。所以有一条规则：`interrupted=1` 且内容过短 → 直接丢弃。阈值**待定**，先用 10 字符。

#### 坑 4：`promptVisible` 被误用

**现象**：用户删了一条消息，但模型好像还记得。

**原因**：如果「删除消息」实现成了置 `promptVisible=0` 而不是真删，那么消息还在表里，只是不进 prompt——这看起来是对的。但**顺序错了**：删除应该是真删（见 [10-数据模型总览](10-数据模型总览.md) 里 `conversation_message` 不用逻辑删除的理由）。

`promptVisible=0` 的正确用途是**「保留消息但排除出上下文」**，这是一个**独立的功能**（比如用户说「别管我上面提的那句」），不是删除的替代实现。

#### 坑 5：`toolCallsJson` 不能进 prompt

**现象**：聪明反被聪明误——把 `conversation_message.toolCallsJson` 也拼进 prompt，想着「让模型知道自己上轮用了什么工具」。

**为什么会出问题**：这个字段是「该轮调用过的工具摘要」，**格式和 `tool_calls` 消息要求的格式不一样**，而且**没有对应的工具结果**。把它当作 `assistant(tool_calls)` 塞进 prompt，会立刻违反规则 3（有请求没结果），模型 API 直接报错。

**规避**：重建 prompt 时，`ASSISTANT` 消息**只取 `content`**，`toolCallsJson` 只用于前端展示和审计。这条要写在代码注释里，因为它非常反直觉。
