# 数据模型总览

## 一、先讲三条约定（不遵守会出问题）

这三条不是风格偏好，是**本项目现有配置决定的硬约束**。第三条尤其容易踩。

### 约定 1：数据库列名用 camelCase

`application.yml` 里 `mybatis-plus.configuration.map-underscore-to-camel-case: false`。

MyBatis 默认会把 `create_time` 这类下划线列名自动映射到 Java 的 `createTime` 属性。本项目**关掉了这个自动映射**，同时**数据库列名本身就用 camelCase**（见 `sql/create_table.sql` 里的 `user` 表：列名是 `createTime`、`userRole`，不是 `create_time`）。

效果是：列名和 Java 属性名**逐字符相同**，于是默认的精确匹配就能工作，不需要任何 `@TableField` 注解或 `resultMap`。

**所以新表的列名必须继续用 camelCase。** 如果你从别处拷来一段下划线列名的 DDL，它会静默地全都映射不上——`selectById` 返回的对象除主键外全是 `null`，不报错。这是本项目最容易浪费时间的一个坑。

### 约定 2：逻辑删除字段叫 `isDelete`

全局配置：

```yaml
mybatis-plus.global-config.db-config:
  logic-delete-field: isDelete   # 逻辑删除字段名
  logic-delete-value: 1          # 已删除
  logic-not-delete-value: 0      # 未删除
```

配了全局之后，MyBatis-Plus 会在**查询**时自动追加 `AND isDelete = 0`，在**删除**时自动把 `deleteById` 变成 `UPDATE ... SET isDelete = 1`。

**但要注意两件它不管的事**（第六条展开）：

1. 它不影响**唯一索引**——已逻辑删除的行仍然占着唯一索引
2. 它不作用于**自定义 SQL / XML 里的手写查询**——那些得自己加条件

### 约定 3：主键策略

| 表类型 | 策略 | 理由 |
|---|---|---|
| 业务实体（`knowledge_*`、`conversation`、`agent_run`） | `BIGINT AUTO_INCREMENT` | 和现有 `user` 表一致；单库单表场景下自增最省事，且天然有序 |
| 高写入量的事件/日志表（`agent_event`、`ai_call_log`、`ai_tool_log`、`agent_step`） | `BIGINT AUTO_INCREMENT` | 同上。**且自增 id 天然按时间有序**，正好当 SSE 的事件游标用 |
| 向量主键（`knowledge_chunk.vectorId`） | `CHAR(36)` 确定性 UUID | 不是自增——因为要让「同一段文本」在重建时得到**同一个** id，见 [24-增量索引](24-增量索引.md) |

**为什么不一开始就用雪花 ID？** 因为目标部署是单库。自增主键有个雪花 ID 给不了的好处：**可读、有序、能当游标**。将来真要分库分表再换，改动集中在 `@TableId` 注解上。

**注意**：`Long` 类型在主键上不影响前端。`JsonConfig` 把 `Long` 序列化成字符串（见 [frontend/01-通用约定](../frontend/01-通用约定.md)），所以前端拿到的是 `"1844674407370955161"` 这样的字符串，不存在 JS 精度丢失问题。

## 二、一条设计原则：MySQL 是权威源，Milvus 是派生索引

```
        写入                          读取
用户 ──► MySQL（权威）              SQL 查询列表/状态/统计
          │
          └─► Milvus（派生）  ──►  按语义相似度召回
```

**为什么不让 Milvus 当主存？** 因为向量库擅长的事很窄：给一个向量，找最相似的几个。它不擅长：

- 「这个知识库下有哪些文档、哪些解析失败了」（列表 + 过滤 + 排序）
- 「这个文档解析到哪一步了」（状态字段 + 乐观更新）
- 「把这些操作放在一个事务里」（向量库没有事务）
- 「统计这个知识库有多少切片、共多少 token」（聚合查询）

所以：**文字和元数据存在 MySQL，向量和冗余文本存在 Milvus，两边靠 `vectorId` 对应。**

代价是双写，所以配了两个机制：**删除顺序**（第五节）和**对账任务**（第六节）。

## 三、12 张表

分四个域。所有表都在 `star_assistant` 库里，`utf8mb4` / `utf8mb4_unicode_ci`。

### 3.1 知识库域

#### `knowledge_base` —— 知识库

```sql
CREATE TABLE `knowledge_base` (
  `id`             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '知识库id',
  `name`           VARCHAR(80)  NOT NULL                COMMENT '知识库名称',
  `description`    VARCHAR(512) DEFAULT NULL            COMMENT '描述',
  `categoryId`     BIGINT       DEFAULT NULL            COMMENT '所属分类id，NULL 表示未分类',
  `embeddingModel` VARCHAR(64)  NOT NULL                COMMENT '向量模型标识，如 bge-small-zh-v15-q',
  `dimension`      INT          NOT NULL                COMMENT '向量维度，必须与模型一致',
  `collectionName` VARCHAR(128) NOT NULL                COMMENT 'Milvus 集合名，规则 star_kb_{id}',
  `chunkSize`      INT          NOT NULL DEFAULT 400    COMMENT '切片长度（字符）',
  `chunkOverlap`   INT          NOT NULL DEFAULT 80     COMMENT '切片重叠（字符）',
  `status`         VARCHAR(20)  NOT NULL DEFAULT 'EMPTY' COMMENT 'EMPTY/BUILDING/READY/FAILED',
  `docCount`       INT          NOT NULL DEFAULT 0      COMMENT '文档数（冗余计数，便于列表展示）',
  `chunkCount`     INT          NOT NULL DEFAULT 0      COMMENT '切片数（冗余计数）',
  `userId`         BIGINT       NOT NULL                COMMENT '创建人',
  `createTime`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime`     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `isDelete`       TINYINT      NOT NULL DEFAULT 0      COMMENT '0 正常 1 已删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_collectionName` (`collectionName`),
  KEY `idx_userId_isDelete` (`userId`, `isDelete`),
  KEY `idx_categoryId` (`categoryId`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='知识库';
```

**为什么存 `embeddingModel` 和 `dimension` 而不是写死在配置里？** 因为检索时要用**和入库时同一个模型**去向量化 query。如果只写在配置里，将来换了模型，老库里的向量就成了「用 A 模型编码、用 B 模型检索」——维度可能对不上直接报错，维度凑巧对上的话结果是完全乱掉的（两个模型的向量空间不通用），而且**不报错**。把模型标识记在库里，就能在检索前校验并给出明确错误。

**为什么 `uk_collectionName` 是唯一索引？** `collectionName` 由 `id` 派生（`star_kb_{id}`），本来天然唯一。加唯一索引是防**代码 bug**：如果哪次改逻辑导致两个知识库指向同一个集合，向量会混在一起，且这种错误在检索时表现为「串味」而不是报错，极难排查。这个索引让它插入就失败。

**为什么 `chunkSize` / `chunkOverlap` 存在库里？** 换切片参数必须重建整个知识库（存量切片是用老参数切的）。把参数记在库里，就能判断「当前参数和入库参数是否一致」，不一致时提示需要重建。

**为什么冗余 `docCount` / `chunkCount`？** 知识库列表页要显示「12 篇文档 / 340 个切片」。不冗余的话每行都要两个子查询。代价是删除文档时要同步维护——放在同一个事务里，不会漂移。

#### `knowledge_category` —— 知识库分类树

```sql
CREATE TABLE `knowledge_category` (
  `id`         BIGINT      NOT NULL AUTO_INCREMENT COMMENT '分类id',
  `name`       VARCHAR(80) NOT NULL                COMMENT '分类名称',
  `parentId`   BIGINT      NOT NULL DEFAULT 0      COMMENT '父分类id，0 表示根分类',
  `level`      TINYINT     NOT NULL DEFAULT 1      COMMENT '层级，从 1 开始',
  `sortOrder`  INT         NOT NULL DEFAULT 0      COMMENT '同级排序，值小的在前',
  `userId`     BIGINT      NOT NULL                COMMENT '创建人',
  `createTime` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `isDelete`   TINYINT     NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_userId_parentId` (`userId`, `parentId`, `isDelete`),
  KEY `idx_userId_name` (`userId`, `name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='知识库分类';
```

**⚠️ 这张表故意没有 `uk(userId, parentId, name)`，这是本次设计里最重要的一个决定。**

原因是逻辑删除和唯一索引会打架，具体见第六节。简单地讲：用户删掉分类「技术」再重建一个叫「技术」的，如果唯一索引存在，第二次插入会因为那条「已删除」的行而失败——用户会看到一个莫名其妙的「已存在」错误，而列表里根本找不到这个分类。

因此「同名分类」的检查必须在**应用层**用查询做（查询会自动带上 `isDelete = 0`），而不是交给数据库唯一索引。

**`level` 字段的用途**：限制树的最大深度（比如 3 层）。插入时校验 `parent.level < 3`，避免无限嵌套导致树形展示和递归查询出问题。**这个限制是产品决策，不是技术限制**，写在这里是为了让它可被修改。

**为什么不用 `sortOrder` 之外的东西排序？** `sortOrder` 相同时按 `id` 兜底，保证顺序稳定（否则每次查询顺序可能不同，前端列表会「跳」）。

#### `knowledge_document` —— 文档

```sql
CREATE TABLE `knowledge_document` (
  `id`          BIGINT        NOT NULL AUTO_INCREMENT COMMENT '文档id',
  `kbId`        BIGINT        NOT NULL                COMMENT '所属知识库id',
  `name`        VARCHAR(255)  NOT NULL                COMMENT '文档名称（原始文件名或标题）',
  `fileType`    VARCHAR(20)   NOT NULL                COMMENT 'PDF/DOCX/TXT/MD/HTML/URL',
  `filePath`    VARCHAR(512)  DEFAULT NULL            COMMENT '原始文件落盘路径',
  `fileSize`    BIGINT        DEFAULT NULL            COMMENT '文件大小（字节）',
  `sourceUrl`   VARCHAR(1024) DEFAULT NULL            COMMENT 'fileType=URL 时的来源地址',
  `contentHash` CHAR(32)      DEFAULT NULL            COMMENT '正文 MD5，增量索引的指纹',
  `charCount`   INT           DEFAULT NULL            COMMENT '正文字符数',
  `chunkCount`  INT           NOT NULL DEFAULT 0      COMMENT '切出的切片数',
  `status`      VARCHAR(20)   NOT NULL DEFAULT 'PENDING'
                COMMENT 'PENDING/PARSING/PARSED/INDEXING/INDEXED/FAILED/DELETING',
  `errorMsg`    VARCHAR(1024) DEFAULT NULL            COMMENT '失败原因',
  `userId`      BIGINT        NOT NULL                COMMENT '上传人',
  `createTime`  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime`  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `isDelete`    TINYINT       NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_kbId_status` (`kbId`, `status`, `isDelete`),
  KEY `idx_kbId_contentHash` (`kbId`, `contentHash`),
  KEY `idx_userId_isDelete` (`userId`, `isDelete`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='知识库文档';
```

**`contentHash` 是整个增量索引的支点。** 它是**正文文本的 MD5**（不是文件的 MD5——同一个 PDF 重新导出一遍，二进制变了但正文没变，按正文算才不会白白重建）。

**为什么没有 `uk(kbId, name)`？** 同样是逻辑删除的坑：用户删掉一篇文档再用同样的文件名传一遍，是完全正常的操作。重复上传的检测在应用层用 `contentHash` 做（同一个库里同一份内容没必要存两遍），而不是用文件名。

**`status` 的流转见 [22-知识库与文档生命周期](22-知识库与文档生命周期.md)。** 这里只说一点：`DELETING` 这个中间态的存在，是为了让「删 Milvus 向量」和「删 MySQL 记录」这两步能够重试——见第五节。

#### `knowledge_chunk` —— 切片

```sql
CREATE TABLE `knowledge_chunk` (
  `id`         BIGINT      NOT NULL AUTO_INCREMENT COMMENT '切片id',
  `kbId`       BIGINT      NOT NULL                COMMENT '所属知识库id（冗余，便于按库批量操作）',
  `docId`      BIGINT      NOT NULL                COMMENT '所属文档id',
  `chunkIndex` INT         NOT NULL                COMMENT '文档内序号，从 0 开始',
  `vectorId`   CHAR(36)    NOT NULL                COMMENT 'Milvus 主键，确定性 UUID',
  `content`    TEXT        DEFAULT NULL            COMMENT '切片正文',
  `tokenCount` INT         DEFAULT NULL            COMMENT 'token 数（实测，非估算）',
  `charCount`  INT         DEFAULT NULL            COMMENT '字符数',
  `createTime` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_vectorId` (`vectorId`),
  KEY `idx_docId_chunkIndex` (`docId`, `chunkIndex`),
  KEY `idx_kbId`
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='知识库文档切片';
```

**⚠️ 这张表没有 `isDelete`，删除是真删。** 理由：切片是纯派生数据，可以从文档正文重新切出来；保留已删除的切片行只有坏处（BM25 索引重建时会读到幽灵数据）。

**为什么 Milvus 里已经有正文了，这里还要再存一份 `content`？** 四个理由，按重要性排序：

1. **BM25 索引重建需要它。** 内存态的 BM25 索引每次启动都要重建，数据源如果是 Milvus，就得把整个集合的文本全捞出来扫一遍——慢且费内存。从 MySQL 按 `kbId` 分页读，可控得多。
2. **排查问题时不用连 Milvus。** 「召回了一段奇怪的文本」这类问题，直接在 MySQL 里查比查向量库方便。
3. **对账。** 第六节的对账任务需要对比「MySQL 认为该有哪些向量」和「Milvus 里实际有哪些」，没有本地的切片清单做不到。
4. **`tokenCount` 需要落库验证。** 切片长度是否合理只能靠实测的 token 数判断（见第五节）。

代价是正文存了两份，磁盘翻倍。文本类数据这个代价可以接受。

**`vectorId` 为什么是确定性 UUID 而不是自增？** 因为增量重建时要让「内容没变的切片」拿到**同一个 id**，这样 Milvus 里就是幂等覆盖而不是「删旧插新」。如果 id 随机，每次重建都会产生一批新 id，旧向量得靠额外手段清理。确定性 id 的生成方式见 [24-增量索引](24-增量索引.md)。

### 3.2 会话域

#### `conversation` —— 会话

```sql
CREATE TABLE `conversation` (
  `id`              BIGINT       NOT NULL AUTO_INCREMENT COMMENT '会话id',
  `userId`          BIGINT       NOT NULL                COMMENT '所属用户',
  `title`           VARCHAR(255) NOT NULL DEFAULT '新会话' COMMENT '会话标题',
  `kbIds`           VARCHAR(512) DEFAULT NULL            COMMENT '关联知识库id，逗号分隔，空表示不用 RAG',
  `pinned`          TINYINT      NOT NULL DEFAULT 0      COMMENT '是否置顶',
  `messageCount`    INT          NOT NULL DEFAULT 0      COMMENT '消息数（冗余，同时用于生成 seq）',
  `lastMessageTime` DATETIME     DEFAULT NULL            COMMENT '最后一条消息时间（列表排序用）',
  `createTime`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime`      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `isDelete`        TINYINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_user_list` (`userId`, `isDelete`, `pinned`, `lastMessageTime`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='会话';
```

**`kbIds` 用逗号分隔而不是建关联表。** 理由：一个会话关联的知识库通常只有个位数，且**只按会话查知识库、不需要反向查**（「这个知识库被哪些会话用了」不是需求）。建关联表要付出 join 成本和一个额外的表，收益很低。

**什么时候该改成关联表**：如果需要「删除知识库时提示它被哪些会话引用」，或者需要给关联关系附加属性（比如每个库的权重），那时候再改。

**`messageCount` 的双重职责**：既用于列表展示「共 12 条消息」，也用于生成下一条消息的 `seq`（`seq = messageCount + 1`）。这两个用途在同一个事务里更新，不会不一致。**但要注意**：删除消息时必须同步回退 `messageCount`，否则 `seq` 会跳号或撞号。

#### `conversation_message` —— 消息

```sql
CREATE TABLE `conversation_message` (
  `id`             BIGINT      NOT NULL AUTO_INCREMENT COMMENT '消息id',
  `conversationId` BIGINT      NOT NULL                COMMENT '所属会话id',
  `runId`          BIGINT      DEFAULT NULL            COMMENT '属于哪次 Agent 运行',
  `seq`            INT         NOT NULL                COMMENT '会话内序号，从 1 开始，决定顺序',
  `role`           VARCHAR(20) NOT NULL                COMMENT 'SYSTEM/USER/ASSISTANT/TOOL',
  `content`        MEDIUMTEXT  DEFAULT NULL            COMMENT '正文；TOOL 角色存工具结果',
  `toolCallId`     VARCHAR(64) DEFAULT NULL            COMMENT 'TOOL 消息对应哪次工具调用',
  `toolCallsJson`  MEDIUMTEXT  DEFAULT NULL            COMMENT 'ASSISTANT 消息里的工具调用请求（原始 JSON）',
  `promptVisible`  TINYINT     NOT NULL DEFAULT 1      COMMENT '是否参与 prompt 重建：0 仅展示',
  `interrupted`    TINYINT     NOT NULL DEFAULT 0      COMMENT '是否被中断截断',
  `tokenCount`     INT         DEFAULT NULL            COMMENT 'token 数',
  `createTime`     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_conversationId_seq` (`conversationId`, `seq`),
  KEY `idx_conversationId_createTime` (`conversationId`, `createTime`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='会话消息';
```

**⚠️ 这张表没有 `isDelete`，删除是真删。** 理由：如果软删，`uk_conversationId_seq` 就会挡住「删除后重新生成同序号消息」——而「截断重发」（用户改了自己那句话重发）正是这个操作。这个取舍在第六节和其他表的处理正好相反，对比着看会更清楚。

**`seq` 为什么不是用 `createTime` 排序代替？** 因为流式输出时助手消息可能在用户消息之后**几毫秒**内写入，时间精度不够；而且同一毫秒内多条消息的顺序不确定。用一个显式的序号才能保证「重建 prompt 时的顺序」和「前端展示的顺序」完全一致——这两处顺序不一致会导致非常难查的行为差异。

**`promptVisible` 的用途**：标记哪些消息参与 prompt 重建。会有这些用法：

- 系统提示词（可能作为一条 SYSTEM 消息存着）——通常期望重新生成，所以 `promptVisible=0`
- 被记忆裁剪掉的历史——不改数据库，只是在重建时跳过（所以这个字段更常见的用途是「永久排除」，比如用户手动「从上下文中移除」）
- 工具调用的中间消息——必须参与，否则模型不知道自己调过工具

**`toolCallsJson` 为什么存原始 JSON 而不是结构化字段？** 因为要原样回传给模型。转成我们自己的结构再转回去，中间任何字段名或嵌套结构的差异都会让模型困惑甚至 API 报错。

#### `agent_run` —— 一次运行

```sql
CREATE TABLE `agent_run` (
  `id`              BIGINT        NOT NULL AUTO_INCREMENT COMMENT '运行id',
  `conversationId`  BIGINT        NOT NULL                COMMENT '所属会话id',
  `userId`          BIGINT        NOT NULL                COMMENT '发起人',
  `status`          VARCHAR(20)   NOT NULL DEFAULT 'PENDING'
                    COMMENT 'PENDING/RUNNING/SUSPENDED/WAITING_APPROVAL/COMPLETED/FAILED/CANCELLED',
  `interruptType`   VARCHAR(32)   DEFAULT NULL
                    COMMENT 'USER_STOP/NEW_MESSAGE/SERVER_RESTART/APPROVAL_REQUIRED',
  `stepNo`          INT           NOT NULL DEFAULT 0      COMMENT '当前轮次',
  `maxRounds`       INT           NOT NULL DEFAULT 10     COMMENT '最大轮次护栏',
  `planVersion`     INT           NOT NULL DEFAULT 0      COMMENT 'todo 计划版本号',
  `inputMessageId`  BIGINT        DEFAULT NULL            COMMENT '触发本次运行的用户消息id',
  `outputMessageId` BIGINT        DEFAULT NULL            COMMENT '最终助手消息id',
  `errorMsg`        VARCHAR(1024) DEFAULT NULL,
  `tokenIn`         INT           NOT NULL DEFAULT 0      COMMENT '累计输入 token',
  `tokenOut`        INT           NOT NULL DEFAULT 0      COMMENT '累计输出 token',
  `startTime`       DATETIME      DEFAULT NULL,
  `endTime`         DATETIME      DEFAULT NULL,
  `createTime`      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime`      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_conversationId_createTime` (`conversationId`, `createTime`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='Agent 运行';
```

**这张表没有 `isDelete`，运行记录永不删除。** 它是审计数据——「这次回答是怎么产生的」唯一能查的证据。用户删会话时，运行的**内容**可能被清掉，但记录本身应该保留（或归档），否则出问题时无法复盘。

**`idx_status` 的用途**：启动时扫描非终态的运行（见 [12-中断与恢复的状态机](12-中断与恢复的状态机.md)）。这个索引的区分度很低（大部分行是 `COMPLETED`），但**查询频率极低**（只在启动时跑一次），所以可接受。

**`tokenIn` / `tokenOut` 累计在 run 上**：因为一次运行可能包含多次 LLM 调用（每轮一次），成本要按运行汇总。明细在 `ai_call_log`。

#### `agent_step` —— 执行步骤（状态机的核心）

```sql
CREATE TABLE `agent_step` (
  `id`              BIGINT        NOT NULL AUTO_INCREMENT COMMENT '步骤id',
  `runId`           BIGINT        NOT NULL                COMMENT '所属运行id',
  `stepNo`          INT           NOT NULL                COMMENT '第几轮',
  `seq`             INT           NOT NULL                COMMENT '运行内自增序号，决定重放顺序',
  `type`            VARCHAR(20)   NOT NULL                COMMENT 'LLM_CALL/TOOL_CALL/TOOL_RESULT',
  `status`          VARCHAR(20)   NOT NULL DEFAULT 'PENDING'
                    COMMENT 'PENDING/RUNNING/SUCCEEDED/FAILED/INTERRUPTED',
  `toolCallId`      VARCHAR(64)   DEFAULT NULL            COMMENT '模型给的调用id',
  `toolName`        VARCHAR(64)   DEFAULT NULL,
  `argumentsJson`   MEDIUMTEXT    DEFAULT NULL            COMMENT '工具入参（原始 JSON）',
  `toolResultJson`  MEDIUMTEXT    DEFAULT NULL            COMMENT '工具结果（重放时直接用）',
  `idempotencyKey`  VARCHAR(128)  DEFAULT NULL            COMMENT '副作用工具的幂等键',
  `sideEffect`      TINYINT       NOT NULL DEFAULT 0      COMMENT '是否改变系统状态',
  `requireApproval` TINYINT       NOT NULL DEFAULT 0      COMMENT '是否需要人工确认',
  `replayed`        TINYINT       NOT NULL DEFAULT 0      COMMENT '本次结果是否来自重放',
  `requestJson`     MEDIUMTEXT    DEFAULT NULL            COMMENT 'LLM 调用入参快照',
  `responseJson`    MEDIUMTEXT    DEFAULT NULL            COMMENT 'LLM 响应快照',
  `errorMsg`        VARCHAR(1024) DEFAULT NULL,
  `elapsedMs`       BIGINT        DEFAULT NULL,
  `startTime`       DATETIME(3)   DEFAULT NULL,
  `endTime`         DATETIME(3)   DEFAULT NULL,
  `createTime`      DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_runId_seq` (`runId`, `seq`),
  UNIQUE KEY `uk_idempotencyKey` (`idempotencyKey`),
  KEY `idx_runId_stepNo` (`runId`, `stepNo`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='Agent 执行步骤';
```

**这是整张数据模型里最关键的一张表。** 它有三个作用：

1. **审计**：这次运行到底调了哪些工具、传了什么、返回了什么
2. **重放**：`toolResultJson` 存着结果，续跑时不必重新执行工具
3. **幂等保证**：`uk_idempotencyKey` 是**唯一防线**——重复执行副作用工具会撞唯一键失败，而不是真的执行第二次

**`uk_idempotencyKey` 配 `DEFAULT NULL` 是刻意的**：MySQL 的唯一索引**允许多个 NULL**。所以只读工具（不生成幂等键，`idempotencyKey` 为 NULL）不会有任何冲突，只有副作用工具才参与唯一性约束。这个特性正好符合需求，不需要额外的过滤条件。

**`type` 三种值的含义**：

| 值 | 对应的行 | `toolResultJson` 有没有值 |
|---|---|---|
| `LLM_CALL` | 一次模型调用 | 无（结果在 `responseJson`） |
| `TOOL_CALL` | 工具调用的**意图**，执行前写入 | 执行完回填 |
| `TOOL_RESULT` | 是否需要单独的行？**不需要**——结果直接回填到 `TOOL_CALL` 那一行 | — |

**`TOOL_RESULT` 这个枚举值实际不落库**（保留在枚举里是为了日志和事件类型对齐）。之所以不拆成两行，是因为拆开的话「意图已落库但结果还没有」和「结果已落库」这两种状态的判定要靠 join，而回填同一行只需要判空。

#### `agent_todo` —— 计划项

```sql
CREATE TABLE `agent_todo` (
  `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '计划项id',
  `runId`       BIGINT       NOT NULL                COMMENT '所属运行id',
  `planVersion` INT          NOT NULL                COMMENT '第几版计划',
  `itemIndex`   INT          NOT NULL                COMMENT '计划内序号，从 1 开始',
  `title`       VARCHAR(512) NOT NULL                COMMENT '计划项描述',
  `status`      VARCHAR(20)  NOT NULL DEFAULT 'PENDING'
                COMMENT 'PENDING/IN_PROGRESS/DONE/SKIPPED',
  `note`        VARCHAR(1024) DEFAULT NULL           COMMENT '执行备注或结果摘要',
  `createTime`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updateTime`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

  KEY `idx_runId_planVersion` (`runId`, `planVersion`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='Agent 计划项';
```

**计划是「版本化」的：改计划不是 UPDATE，而是插入一版新行（`planVersion + 1`）。**

理由：计划变了这件事本身就是重要信息。如果原地 UPDATE，就看不到「它原来打算干 A，发现不行改成 B」这个过程。这对排查「它为什么走了弯路」很关键，也是 Codex 那种「逐步推进的计划」体验的来源——前端可以展示计划的变化历史。

代价是行数随版本数增长。但一次运行里计划通常只改 1~3 次，项数在 10 以内，可忽略。

**不做逻辑删除**：计划项是记录，不是业务数据。但要**注意** `uk_runId_planVersion_itemIndex` 和逻辑删除的冲突——这里没配 `isDelete`，所以没有这个问题。

#### `agent_event` —— SSE 事件流

```sql
CREATE TABLE `agent_event` (
  `id`             BIGINT      NOT NULL AUTO_INCREMENT COMMENT '事件id，同时用作 SSE 的 event id',
  `runId`          BIGINT      NOT NULL                COMMENT '所属运行id',
  `conversationId` BIGINT      NOT NULL                COMMENT '所属会话id',
  `eventType`      VARCHAR(32) NOT NULL
                   COMMENT 'run_start/todo_update/tool_call/tool_result/interrupt/run_end/error/message_snapshot',
  `dataJson`       MEDIUMTEXT  NOT NULL                COMMENT '事件体（原始 JSON）',
  `createTime`     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  KEY `idx_runId_id` (`runId`, `id`),
  KEY `idx_conversationId_id` (`conversationId`, `id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='Agent 事件（SSE 回放用）';
```

**自增 `id` 直接当 SSE 的 `event id` 用**，一举两得：既是主键，又是天然有序、可比较的游标。前端断线重连时带上最后收到的事件 id，后端 `WHERE id > ?` 就能精确补发漏掉的部分。

**⚠️ `message_delta`（逐 token 的增量文本）不落这张表。** 这是本次设计里第二个重要决定。

理由很直接：一次回答 500 个 token 就是 500 行。一天 1000 次对话就是 50 万行纯冗余数据（因为完整文本已经存在 `conversation_message.content` 里了），而且这些行除了「刚推给当前连接」之外没有任何用途。

那断线重连怎么办？答案见 [31-流式输出SSE](31-流式输出SSE.md)：重连时**先补发漏掉的里程碑事件**（这张表里的），再**发一条 `message_snapshot`**（当前已生成的部分文本，从内存或 `conversation_message` 取），然后**继续推后续的 delta**。这样既不需要存 delta，也不会让用户看到文本断掉。

`message_snapshot` 这个事件类型就是为这个场景保留的。

#### `ai_call_log` —— 模型调用日志

**`scene` 字段区分调用用途。** 因为一次对话里可能有多次不同性质的模型调用：生成回答、改写 query 用于检索、生成会话标题、规划计划。混在一起统计的话，「平均耗时」这种指标毫无意义。

**`firstTokenMs` 只在流式时才有值，且是**唯一能反映用户实际体验**的指标。总耗时对 SSE 场景没意义——用户早就在看输出了，`elapsedMs` 是 20 秒还是 30 秒，感受差异远小于首 token 是 300ms 还是 3 秒。

**`costYuan` 用 `DECIMAL` 而不是 `DOUBLE`**：金额不能用浮点数，累加会漂移。

```sql
  `argumentsJson`  MEDIUMTEXT    DEFAULT NULL,
  `resultJson`     MEDIUMTEXT    DEFAULT NULL,
  `success`        TINYINT       NOT NULL DEFAULT 1,

  `elapsedMs`      BIGINT        DEFAULT NULL,

  KEY `idx_idempotencyKey` (`idempotencyKey`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='工具调用日志';
```

**为什么和 `agent_step` 有重叠还要单独一张表？** 职责不同：

| | `agent_step` | `ai_tool_log` |
|---|---|---|
| 性质 | **状态**（状态机读写它来推进） | **日志**（只追加，不参与逻辑） |
| 幂等键索引 | **唯一**（防线） | **普通**（因为要能看到重放记录） |
| 生命周期 | 跟着运行走 | 长期保留，用于分析 |

关键在 `idempotencyKey` 的索引类型：`agent_step` 上是**唯一索引**（重复执行会失败，这是防线），`ai_tool_log` 上是**普通索引**（所以一次重放会留下两条日志：原来的执行 + 后来的重放）。这样既拦住了重复执行，又留下了「这里发生过重放」的证据。如果两边都是唯一索引，第二条日志就写不进去，重放这件事就查不到了。

**`replayed` 标记是验证 M9（中断续跑）是否正确的直接证据**：跑一个中断再续跑的测试，如果副作用工具的日志里有正好一条 `replayed=0` 和一条 `replayed=1`，且后端只真正执行了一次，就说明幂等生效了。

## 五、删除顺序（双写一致性）

MySQL 和 Milvus 双写必然会有「一边成功一边失败」的时刻。所以每类操作都要定一个**顺序**，让失败时停在「可重试」而不是「不一致」的中间态。

| 操作 | 顺序 | 失败会怎样 |
|---|---|---|
| **新增文档** | ① 插 `knowledge_document`（`PENDING`）→ ② 解析 → ③ 切片插 `knowledge_chunk` → ④ 向量入 Milvus → ⑤ 文档置 `INDEXED` | 任何一步失败，文档停在对应状态；重试从该状态继续。**不会产生「Milvus 有向量但 MySQL 没记录」** |
| **删除文档** | ① 文档置 `DELETING` → ② 删 Milvus 向量 → ③ 删 `knowledge_chunk` 行 → ④ 文档真删 | ②失败：停在 `DELETING`，可重试。**③失败**：MySQL 里还有切片行但向量已没了——这是**安全的**不一致（检索少召回几条，不会召回错内容），对账任务能修 |
| **重建知识库** | ① 新集合 → ② 全量写入 → ③ 更新 `knowledge_base.collectionName` → ④ 删旧集合 | ③之前失败：旧集合还在正常服务，用户无感。**④失败**：留下一个孤儿集合，占磁盘但无害，可手动清理 |

**共同的原则：先做「加」的动作，再做「减」的动作。** 因为「加了但没减」是安全的（有冗余），「减了但没加」是不安全的（有缺失）。删除文档的顺序里，先删向量再删 MySQL 行，也是同样的道理——宁可留下查不到的切片行（安全），不要留下指向不存在切片的向量……等等，这里正好相反：留下向量比留下切片行**更危险**，因为检索是从 Milvus 出发的，向量在就会被召回，而它的正文可能已经从 MySQL 删了。

**所以删除文档必须遵守：先删 Milvus 向量，再删 MySQL 行。** 顺序反了的话，中间的失败窗口里 Milvus 有向量而 MySQL 没对应行，检索会召回一段「查不到出处的文本」——轻则答非所问，重则把已删除的敏感内容答出来。

## 六、两个必须警惕的坑

### 坑 1：逻辑删除和唯一索引会打架

**现象**：用户删掉分类「技术」，再新建一个叫「技术」的分类 → 报「已存在」。但列表里明明没有「技术」。

**原因**：逻辑删除只是把 `isDelete` 置为 1，**那一行还在表里**。唯一索引看得见所有行，不管 `isDelete` 是几。所以第二次插入撞上了那条「已删除」的行。而查询时 MyBatis-Plus 自动加了 `AND isDelete = 0`，所以列表里看不到它。

**这不是 bug，是逻辑删除的固有代价。**

**规避方式**：新增表时要逐个审计——**「删掉再用同一自然键重建」是不是正常用户行为？**

| 表 | 自然键 | 会出现「删了重建」吗 | 处理 |
|---|---|---|---|
| `knowledge_category` | `(userId, parentId, name)` | **会**（删分类再建同名） | **不加唯一索引**，应用层查重 |
| `knowledge_document` | `(kbId, name)` | **会**（删文档再传同名） | **不加唯一索引**，用 `contentHash` 查重 |
| `knowledge_base` | `(userId, name)` | **会** | **不加唯一索引**，应用层查重 |
| `knowledge_base` | `collectionName` | **不会**（由 id 派生） | 加唯一索引（防代码 bug） |
| `user` | `username` / `email` | **不会**（用户被封号也不能重名） | 已有唯一索引，保持 |
| `agent_todo` | `(runId, planVersion, itemIndex)` | **不会**（无逻辑删除） | 加唯一索引 |
| `agent_step` | `(runId, seq)` / `idempotencyKey` | **不会**（无逻辑删除） | 加唯一索引 |

**审计方法**：写下唯一索引时问一句「如果这行被逻辑删除了，用户还能用同一组值重新创建吗？」——能，就不能加。

### 坑 2：`map-underscore-to-camel-case: false` 的静默失败

**现象**：`selectById` 返回的对象除主键外全是 `null`，日志里 SQL 执行成功。

**原因**：列名是 `create_time` 而属性是 `createTime`，且自动映射被关掉了，MyBatis 找不到对应关系就留 `null`（`mapUnderscoreToCamelCase` 为 false 时，MyBatis 用的是默认的 `PARTIAL` 自动映射，匹配不上的列直接忽略，**不报错**）。

**规避方式**：

1. 新表列名一律 camelCase
2. 建表后立刻跑一次插入 + 查询，确认字段能读出来——**不要等到业务逻辑写完才发现**
3. 从别处拷 DDL 时，逐列检查下划线

**如果确实需要用下划线列名**（比如对接已有表），必须显式写 `@TableField("create_time")` 或在 Mapper XML 里写 `resultMap`。本项目选择不这么做，统一 camelCase，减少一类错误来源。

## 七、对账机制

双写必然漂移。所以需要一个**可重复执行**的对账任务（M11 之后做，这里先定义清楚要做什么）：

| 检查项 | 发现漂移怎么办 |
|---|---|
| `knowledge_chunk` 里有行但 Milvus 里没有对应 `vectorId` | 重新向量化这一段并写入（补回来） |
| Milvus 里有 `vectorId` 但 `knowledge_chunk` 里没有 | 从 Milvus 删掉该向量（清孤儿） |
| 文档 `status=INDEXED` 但 `chunkCount=0` | 置为 `FAILED` 并提示重建 |
| `conversation.messageCount` 与实际消息行数不一致 | 以实际行数为准修正（`messageCount` 只是冗余计数） |
| `knowledge_base.docCount` / `chunkCount` 与实际行数不一致 | 同上 |

**对账任务的关键要求**：**幂等 + 可分批**。要能对单个知识库跑（不必全库），要能中途中断（几百万向量的库不可能一次跑完）。所以按 `kbId` 分片，每片一个事务。

**先不做，但要留位置。** 建表时把对账需要的字段都准备好（`vectorId` 唯一索引、`contentHash`、`status`），将来加任务是纯代码，不用改表。
