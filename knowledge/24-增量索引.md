# 增量索引

> RAG 组最后一篇。讲「文档变了之后，怎么用最小代价让索引追上变化」。
> 上游是 [22 知识库与文档生命周期](22-知识库与文档生命周期.md)（切片怎么入库），
> 本篇只改「重建」这一步的实现，不改数据结构。

## ① 这个模块治的是哪类病（通用问题定义）

### 问题定义

**建索引是有成本的，而文档是会变的。** 一个知识库建好后，会不断发生这些事：

| 触发 | 需要做什么 |
|---|---|
| 一篇文档的内容更新了 | 重建**这一篇**的切片与向量 |
| 有几篇当初索引失败了 | 重试**这几篇** |
| 切片参数 / 向量模型换了 | **全部**重建（存量切片是用旧参数切的） |
| 向量库和 MySQL 漂移了 | 对账，修**漂移的部分** |

如果只会「全部重建」，那么「改 1 篇」要付「重建 1000 篇」的代价——这在语料一变大后就不能接受了。
所以这个模块要解决的本质问题是：**给一次重建算出「到底哪些切片需要重新计算」，只做这部分。**

### 边界

| 归它管 | 不归它管 |
|---|---|
| 判断**哪些切片变了**、只重算这部分 | 怎么切、怎么解析（[22](22-知识库与文档生命周期.md)） |
| 「重建」的**全量 / 增量**两种语义 | 检索怎么用这些向量（[23](23-混合检索与融合.md)） |
| 变化时的**删旧增新**顺序 | 向量库与 MySQL 的**对账任务**（M11，见 [10](10-数据模型总览.md) 第七节） |

### 两类典型失败模式

1. **重复劳动**：内容没变却重新嵌入一遍。既慢又费钱（本地模型费 CPU、远端模型费钱）。**不报错**，只是慢。
2. **该重做的没重做**：某些切片该更新却没更新（比如参数变了却按内容没变跳过了），于是索引与内容**悄悄不一致**——检索结果里混着过时内容。

第 2 类更危险：它把「省事」和「正确」对立起来，一旦判断依据选错，就会静默错。

## ② LangChain4j 官方怎么做

官方在这一块能力**很薄**：

| 官方设施 | 提供 | 不提供 |
|---|---|---|
| `EmbeddingStoreIngestor.ingest(document)` | 一次性的「切片 + 向量化 + 入库」 | **任何 diff / 增量**；每次调用都是全量重做这份 document |
| `EmbeddingStore.addAll / removeAll` | 按 id 增删向量 | **算出「哪些 id 变了」**——那要调用方自己比 |
| `DocumentSplitter` | 重新切片 | 与旧切片的比对 |

也就是说，官方给到了「原子操作」（增、删、切），但**没说「怎么只做变化的部分」**。
这一步（算差集 + 决定增删）必须自研。（与 [20](20-RAG-概述与LangChain4j官方链路.md) 的判断一致：
官方提供零件，编排自研。）

## ③ 本项目为什么这么落地

### 使能条件：确定性 vectorId

增量之所以能做得又简单又精确，靠的是 M1 就埋下的一个设计（见 [22](22-知识库与文档生命周期.md)）：

```
vectorId = UUID(docId + "#" + chunkIndex + "#" + MD5(content))
```

**同一个 vectorId ⇔ 同一段内容在同一位置。** 所以：**id 相同就等于「这段没变」**，
不需要再去比较文本、不需要存额外的版本号。这是整篇文档能成立的前提。

### 决策：增量做在「切片级」，不做「文档级跳过」

考虑过两种粒度：

| 方案 | 做法 | 问题 |
|---|---|---|
| 文档级跳过 | 整篇的 `contentHash` 没变就跳过整篇 | 只对「内容没变**且切片参数也没变**」安全。**参数变了但内容没变时会误跳过** → 新参数永远不生效，且**静默**（用户点重建，什么都没发生，也不报错）。要修就得记录「入库时的切片参数」，而表里没这个字段 |
| **切片级 diff（采用）** | 拿新旧 vectorId 集合比，只增删变化的部分 | 每次仍要 re-parse + re-chunk（CPU 工作），但省掉**嵌入 + 写向量**（真正的瓶颈） |

**选切片级 diff**，因为它**天然同时正确处理「内容变」和「参数变」**：参数一变，新切片的
vectorId 与旧的**全不相同** → diff 判定「全新增 + 全删除」→ 全量重嵌。不需要额外记录参数，也不会误跳过。

- **代价**：增量的收益止步于「嵌入 + 写向量」，解析与切片仍对每篇做一遍。
- **待办**：`knowledge_base` 加一列「入库时的切片参数」后，可以做安全的文档级跳过（省掉 re-parse）。见文末「没做的」。

### `full` 的两种语义

| `full` | 语义 | 实现 | 用途 |
|---|---|---|---|
| `false`（增量） | 逐篇走切片级 diff，只处理变化的 | 不 drop、不删切片行 | 日常维护、重试失败文档 |
| `true`（全量） | 丢开 diff，全部重切重嵌 | **`dropCollection` + 删该库全部切片行**，再逐篇重建 | 换模型、换切片参数、对账 |

⚠️ `full=true` **必须连切片行一起删**——原因见坑 1，这是本模块最容易出事的地方。

## ④ 数据结构与流程时序

### 一篇文档的增量索引

```
parse(原文) → 文本
  │
  ├─ 切片（用知识库当前的 chunkSize/chunkOverlap）
  │      → newChunks，每片算出 vectorId
  │
  ├─ 查 MySQL：该文档现有的 vectorId 集合 oldIds
  │
  ├─ diff(oldIds, newIds)：
  │      toInsert = 新 − 旧      （要嵌入并写入）
  │      toDelete = 旧 − 新      （要从 Milvus 与 MySQL 删）
  │      交集                    （原样保留，不碰）
  │
  ├─ noChange() 且原本已是 INDEXED → 整篇跳过（不嵌、不写、状态都不动）
  │
  └─ 有变化：
        ① 先删：Milvus removeAll(toDelete) → MySQL 删这些行   （先减「会被召回的」）
        ② 再增：MySQL 插 toInsert 行 → Milvus addAll(toInsert 的向量)   （先 MySQL 后 Milvus）
        ③ 更新 chunkCount / contentHash，状态置 INDEXED
```

**删/增顺序**沿用 [22](22-知识库与文档生命周期.md) 的原则：删除时先删 Milvus 再删 MySQL，
新增时先写 MySQL 再写 Milvus——让失败窗口停在「多了」而不是「少了」。

### 实测（验收：改 1 篇只动 1 篇）

两篇文档 A（1 片）、B（2 片），`kbId=6`：

| 操作 | 日志 | MySQL 里的 vectorId |
|---|---|---|
| A 内容未变，`reindex` | `切片=1, 新增=0, 删除=0, 未变=1` | A 不变 |
| **只改 A 的原文**，`reindex` | `切片=1, 新增=1, 删除=1, 未变=0` | **A 的 id 变了（`517834a4`→`473f2f62`），B 一字未变** |
| `rebuild?full=false` | 两篇都 `文档内容未变化，跳过索引` | 都不变 |
| `rebuild?full=true` | 两篇都 `新增=1 / 新增=2`（全插入） | 全部重建；**检索仍能命中** |

### 代码落点

| 能力 | 类 |
|---|---|
| 切片集合 diff（纯函数） | `ai/IndexDiff` |
| 增量索引流程 | `service/impl/KbIndexServiceImpl.indexDocument` |
| 全量/增量语义 | `service/impl/KbIndexServiceImpl.submitRebuild` |
| 确定性 id | `KbIndexServiceImpl.vectorId` |

## ⑤ 边界、已知限制、踩过的坑

### 坑 1（最危险）：`full=true` 只 drop 集合、不删切片行 → 静默丢向量

**现象**：换模型/换参数走全量重建后，检索**什么都搜不到**，但没有任何报错。

**原因**：`full=true` 若只 `dropCollection`（Milvus 清空）而**没删 MySQL 的切片行**，
那么逐篇 `indexDocument` 时，切片级 diff 会看到「这些 vectorId 我这儿都有、没变」→ **跳过嵌入**
→ Milvus 被清空、向量却不再写入。MySQL 里切片行还在，看起来一切正常，**只有检索是空的**。

**修法**：`submitRebuild(full=true)` 在 `dropCollection` 之后**立即 `delete 该库全部切片行`**，
让 diff 看到的旧集为空 → 全部 toInsert → 全量重嵌。
守住它的验证：全量重建后必须**再检索一次**，确认能命中（见 §④ 实测表最后一行）。

**连带的运维事实**：`full=true` 会先丢弃整个集合再逐篇重建，所以**重建期间检索会短暂为空或只返回部分结果**。
因此全量重建应在无人使用时做，不要与在线检索并发。增量（`full=false`）没有这个问题——它只动变化的切片。

### 坑 2（实现时踩到）：「原本是否 INDEXED」必须在改状态**之前**取

**现象**：增量重建里，明明内容没变，却走了完整流程（日志打的是「索引完成」而不是「未变化跳过」），
状态还从 INDEXED 无谓地绕了一圈 PARSING→PARSED→INDEXING。

**原因**：`indexDocument` 一开始就 `setStatus(doc, PARSING)`，把**内存对象**的状态改掉了；
等到后面判断 `diff.noChange() && doc.getStatus()=="INDEXED"` 时，`doc.getStatus()` 早就是 `PARSING` 了，
条件恒为假。

**修法**：进方法时先记 `boolean wasIndexed = "INDEXED".equals(doc.getStatus())`，之后用这个变量判断，
不要用被改过的 `doc.getStatus()`。

> 抽象一下：**当一个对象的字段会被方法中途修改时，任何「依赖它旧值」的判断都要在修改前取值。**

### 已知限制

- **增量只省「嵌入 + 写向量」，不省解析与切片**：每篇文档仍会被 re-parse + re-chunk。
  对 PDF 这类解析较慢的格式，这是增量重建的主要残留成本。要省掉它需要文档级跳过（见「没做的」）。
- **BM25 索引没有增量**：任何写入都会让该库的 BM25 索引整体失效、下次检索整库重建
  （见 [23](23-混合检索与融合.md) 坑 2）。本篇只做了**向量侧**的增量。

### 没做的

| 没做 | 影响 | 备注 |
|---|---|---|
| **文档级 fingerprint 跳过** | 增量仍要 re-parse 每篇 | 需要 `knowledge_base` 加「入库时的切片参数」列 |
| **BM25 增量更新** | 关键词索引整库重建 | 库大时首查慢 |
| **对账任务** | MySQL 与 Milvus 漂移只能靠日志发现 | M11 |
| **内容级去重** | 同一份内容传两遍会存两遍 | 见 [22](22-知识库与文档生命周期.md) 待办 |
| **重建进度写入独立表** | 现在靠 `status` 现算（无状态，见 [22](22-知识库与文档生命周期.md)） | 够用 |
