# 工具调用机制与面试拷打

> **定位**：只回答三个问题——**一次工具调用在协议层到底发生了什么**、**模型凭什么决定调不调**、**轮次/步骤最多到哪、撞顶会怎样**。
>
> 本文是「机制 + 边界 + 高强度问答」。全链路走读见 [04-ReAct主循环全链路与面试讲解](04-ReAct主循环全链路与面试讲解.md)，状态机见 [12-中断与恢复的状态机](12-中断与恢复的状态机.md)，模块设计见 [30-工具调用](30-工具调用.md)。OpenAI 请求/响应/SSE 报文与通用参数速查见 [33-OpenAI-API请求响应与常用参数](33-OpenAI-API请求响应与常用参数.md)。本文不重复讲中断续跑的细节，只在边界处指路。
>
> 代码基线：LangChain4j `1.20.0`、`deepseek-flash`（OpenAI 兼容协议）、`AgentRunner` / `AgentToolRegistry`。

## 0. 先背这七句

1. **模型不执行工具，只输出「调用意图」；真正执行的是宿主。** 模型永远看不到工具实现，只能看到宿主回填的文本结果。
2. **调不调用不是一个 if-else，而是生成时的一次概率性决策。** 输入是 schema、描述、上下文和 `tool_choice`，输出是「这段文本」还是一个或多个 `tool_calls`。
3. **description 就是模型眼里的 API 文档。** 它不知道你的数据库、权限和代价；你不在描述里写清「何时该调」，它就只能猜。
4. **能引导，不能保证。** 宿主侧必须假设模型会漏调、乱调、编工具名、写错参数，并全部兜住。
5. **一轮 = 一次模型响应 + 它要求的一批工具执行。** 本项目上限 **8 轮**（`ai.agent.max-rounds`），不是 8 次工具。
6. **到 8 轮不算失败**：用最后一轮文本或兜底话术收尾，run 仍记 `COMPLETED`。第 8 轮要求的工具会执行并落库，但结果**不会再喂回模型**。
7. **真正的可靠性来自宿主**：意图先落库、错误回文本、结果截断、轮次护栏、副作用审批与幂等。prompt 只负责「让模型更可能做对」。

## 1. 通用问题定义：工具调用在治什么病

### 1.1 模型只会生成 token

大模型是一个无状态的条件文本生成器：

- 它不能读数据库、发工单、查实时天气；
- 它不知道「现在几点」，训练数据也有截止时间；
- 它没有你系统的权限、租户、业务规则；
- 它生成的任何「我帮你查了」都只是文本，不是事实。

要让它「做事」，必须引入一条**协议**：模型用结构化输出表达「我想调用哪个能力、参数是什么」；宿主解析并真正执行；再把执行结果作为新消息送回模型；模型据此继续。

### 1.2 协议的四步

```
① 宿主把「工具清单 + 每个工具的 JSON Schema」随对话一起发给模型
② 模型决定这一轮输出：普通文本，或一个/多个 tool_calls（name + arguments + id）
③ 宿主按 name 找到真实函数，绑定参数、执行，得到结果文本
④ 宿主把 assistant(tool_calls) 与 tool(tool_call_id, result) 追加进消息，再调一次模型
```

第 ④ 步之后，模型可能继续要工具，也可能给出最终回答。这个「模型 → 工具 → 模型」的交替，就是 **ReAct（Reasoning + Acting）**。**ReAct 是范式，tool calling 是实现协议。** 早期做法是让模型输出 `Thought:/Action:/Observation:` 文本再由宿主正则解析；原生 tool calling 把「行动」变成了结构化的 API 字段，更可靠、更易校验。

### 1.3 一张时序图

```
用户 ──► 宿主 ──► 模型
          │        │
          │◄───────┘  ① 文本回答（不调工具，结束）
          │
          │◄───────┘  ② tool_calls: [{id, name, arguments}]
          │
          ├─ 执行工具（宿主，模型不参与）
          │
          ├──► 模型（messages 追加 assistant.tool_calls + role=tool 结果）
          │◄─── 最终文本 / 继续要工具
          │
          └──► 用户
```

### 1.4 为什么通常需要「宿主自研循环」

官方 SDK（如 LC4j 的 `AiServices`）能开箱跑完这个循环，但它是内存里的黑盒：中间不给你钩子。生产系统需要在每次模型/工具调用前后插入：

- **可观测**：工具名、参数、结果、耗时、token；
- **可中断**：用户点停止，要停在安全点；
- **可恢复**：崩溃/中断后从断点续跑；
- **可治理**：副作用分级、人工确认、幂等。

所以本项目的立场是：**协议层用 LC4j 的零件（`@Tool` schema、`DefaultToolExecutor`），编排层和状态层自研**。详见 [30](30-工具调用.md) 与 [04](04-ReAct主循环全链路与面试讲解.md)。

### 1.5 两类问题要分开

| 类别 | 问题 | 谁能解决 |
|---|---|---|
| 模型侧 | 该调时不调、不该调时乱调、调错工具、参数写错 | 描述、`tool_choice`、上下文、评测、必要时路由/微调；**只能提高概率** |
| 宿主侧 | 调了不存在的工具、执行抛异常、结果太长、死循环、重复副作用、断线崩溃 | 校验、错误回填、截断、轮次护栏、审批、幂等、状态机；**必须确定性地兜住** |

面试里最容易失分的，是把第二类问题说成「靠 prompt 解决」。

## 2. 协议层：一次工具调用在线上长什么样

以下用 OpenAI 兼容协议的字段示意（DeepSeek 走同一套），省略了与本主题无关的字段。实际序列化由 LC4j 的 OpenAI 适配器完成。

### 2.1 第一次请求：把工具清单发给模型

```json
{
  "model": "deepseek-flash",
  "messages": [
    {"role": "system", "content": "你是「智能星」知识助手……"},
    {"role": "user", "content": "现在几点了？"}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "getCurrentTime",
        "description": "获取当前的日期和时间。当问题涉及『现在』『今天』『几号』『几点』等需要当前时刻的信息时调用。"
      }
    }
  ],
  "temperature": 0.3,
  "stream": true
}
```

几个容易讲错的点：

- **`tools` 是每次请求都要重发的**。Chat Completions 是无状态的，服务端不记得你上次给过什么工具。
- **`parameters` 是 JSON Schema**，不是 Java 类型。LC4j 通过 `ToolSpecifications.toolSpecificationFrom(method)` 反射生成；无参工具会**省略整个 `parameters`**（本项目坑 4）。
- **没有 `tool_choice` 字段**。本项目没设置它（`ChatRequest.builder().messages(...).toolSpecifications(...)`，`AgentRunner.java:193`），OpenAI 兼容协议的缺省语义是 `auto`：**调不调由模型决定**。

### 2.2 模型响应：它决定「这一轮要动手」

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_0f3a9c",
            "type": "function",
            "function": {
              "name": "getCurrentTime",
              "arguments": "{}"
            }
          }
        ]
      },
      "finish_reason": "tool_calls"
    }
  ]
}
```

关键语义：

- **`content` 可以为 `null`**。这一轮模型没有对用户说话，只表达了行动意图。
- **`arguments` 是一个 JSON 字符串**，不是对象。模型完全可能输出坏 JSON、缺字段、类型不对；provider 不一定按 schema 校验（除非开启 strict 结构化输出）。
- **`finish_reason = tool_calls`** 表示「本轮没说完，等宿主执行」。它不是最终回答。
- 一条 assistant 消息里**可能有多个 `tool_calls`**（并行工具调用）。是否发生由模型/provider 决定，宿主必须能处理 0 个、1 个、N 个。

### 2.3 回填：把「行动」和「观察」追加进消息

第二次请求的 `messages` 会变成：

```json
[
  {"role": "system", "content": "你是「智能星」知识助手……"},
  {"role": "user", "content": "现在几点了？"},
  {
    "role": "assistant",
    "content": null,
    "tool_calls": [
      {"id": "call_0f3a9c", "type": "function",
       "function": {"name": "getCurrentTime", "arguments": "{}"}}
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_0f3a9c",
    "content": "当前时间：2026-10-29 15:20:31（周四），时区 Asia/Shanghai"
  }
]
```

注意：

- **assistant 的 `tool_calls` 消息必须保留**，不能只发 `role=tool`；
- **每个 `tool_call_id` 必须有且只有一条对应的 `role=tool` 消息**，顺序紧随其后；
- 缺失、孤儿或 id 对不上，OpenAI 兼容服务端通常直接返回 400。这不是「最佳实践」，是协议硬约束。续跑时的「只重放完整轮」就是为了不拼出孤儿请求（见 [12](12-中断与恢复的状态机.md)）。
- **工具结果只是文本**。模型不会自动知道工单真的创建了，它只知道你回填了什么。

### 2.4 第二次响应：终于可以回答

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "现在是 2026 年 10 月 29 日 15:20，周四。"
      },
      "finish_reason": "stop"
    }
  ]
}
```

### 2.5 协议不变量（面试可以直接背）

| # | 不变量 | 违反的后果 |
|---|---|---|
| 1 | 每个 `tool_call.id` 与 `role=tool.tool_call_id` 一一配对 | 服务端 400；续跑重放失败 |
| 2 | assistant 的 `tool_calls` 消息必须留在历史里 | 结果没有「被观察的动作」，语义断裂 |
| 3 | `arguments` 是字符串，宿主负责解析/校验/绑定 | 直接当对象用会解析失败 |
| 4 | `content` 可能为 null | NPE，整轮崩 |
| 5 | `finish_reason=tool_calls` 不是最终回答 | 提前收尾，用户只看到半句话 |
| 6 | `tools` 每轮重发，模型不记忆工具 | 第二轮没工具，模型无法继续调用 |

### 2.6 流式下的工具调用：结束才完整

流式响应里，文本以 `delta` 逐 token 到达；工具调用参数也是**分片拼装**的：

```
delta 1: tool_calls[0].id = "call_0f..."
delta 2: tool_calls[0].function.name = "getCurrent"
delta 3: tool_calls[0].function.arguments = "{\"qu"
delta 4: tool_calls[0].function.arguments = "ery\":\"年假\"}"
...
finish: 完整 tool_calls 才成型
```

LC4j 的适配器负责拼装，最终只在 `onCompleteResponse(ChatResponse)` 里给出完整的 `aiMessage().toolExecutionRequests()`。所以本项目的 `tool_call` 事件是在**该轮响应结束后**才发，而不是「模型一开始决定调用就发」（坑见 [30](30-工具调用.md) 坑 3）。要更早提示，得用 `onPartialToolCall`，本项目未用。

### 2.7 协议字段 ↔ 本项目类

| 协议字段 | LC4j / 本项目 | 说明 |
|---|---|---|
| `tools[].function.name/description/parameters` | `ToolSpecification` | `@Tool` + `@P` 反射生成 |
| `assistant.tool_calls[]` | `AiMessage.toolExecutionRequests()` | 一个响应可含多个 |
| `tool_calls[].id` | `ToolExecutionRequest.id()` | 本项目会归一化空 id（见 4.3） |
| `tool_calls[].function.arguments` | `ToolExecutionRequest.arguments()` | JSON 字符串 |
| `role=tool` 消息 | `ToolExecutionResultMessage` | 用 `from(req, text)` 保证 id 配对 |
| `tool_choice` | `ChatRequest.toolChoice()` | 本项目为 null，等价 auto |
| 流式 delta | `StreamingChatResponseHandler.onPartialResponse` | 只给文本；工具调用在结束时才完整 |
| 完整响应 | `onCompleteResponse` | 本项目用 `CompletableFuture` 桥接成阻塞 |

## 3. 模型怎么决定「要不要调」

这是面试官最爱追问、也最容易答虚的一块。先把结论说死：

> **模型不是先判断「该不该调」再执行，而是在生成这条 assistant 消息时，直接决定输出普通文本还是 `tool_calls`。** 判断和执行是同一个前向过程；没有独立的分类器。

### 3.1 决策发生在生成里

对支持 function calling 的模型，训练数据里包含大量「用户请求 → 输出结构化工具调用」的样本。推理时，模型看到：

- system prompt；
- 历史消息（包括上一轮的工具结果）；
- 当前用户消息；
- `tools` 的 JSON Schema 文本；
- `tool_choice` 约束；
- 采样参数（本项目 `temperature=0.3`）。

它按概率生成下一个 token。当上下文与某个工具的「使用场景」高度匹配时，生成 `tool_calls` 结构的概率上升；否则更可能生成普通文本。**同一个问题跑两次，可能一次调、一次不调**，这不是 bug，是生成式模型的固有波动。

一句话版本：

> **它不是「知道」，它是「觉得此刻该输出调用格式」。**

### 3.2 影响决策的五个输入

| # | 输入 | 作用 | 本项目的现状 |
|---|---|---|---|
| 1 | 工具名 | 语义锚点，越像「动作」越好 | `getCurrentTime` / `searchKnowledge` / `createTicket` |
| 2 | 工具描述 | **最重要的引导**：写清「何时该调、何时不该调」 | 三个工具都写了触发场景，例如时间工具明确列了「现在/今天/几号/几点」 |
| 3 | 参数描述 | 降低参数名/格式错误 | `@P(name, description)` 显式写死，不赌 `-parameters` |
| 4 | `tool_choice` | 强制/禁止/放权 | 未设置，等价 `auto` |
| 5 | 对话上下文 | 历史里的成功调用、用户措辞、系统提示 | 系统提示只要求「简洁准确、不编造」，没有强推检索 |

此外还有两个隐性因素：

- **模型的 function-calling 能力**：不同模型/版本差异很大；
- **provider 的解码约束**：有的 provider 用语法约束保证工具名和 JSON 合法，有的不做。约束能降低语法错误，**不能保证语义选对**。

### 3.3 `tool_choice` 四档

| 值 | 含义 | 代价 |
|---|---|---|
| `auto`（缺省） | 模型自由决定调不调、调哪个 | 可能漏调或乱调 |
| `none` | 禁止调用，只许文本 | 需要工具时也无能为力 |
| `required` | 至少调用一个工具 | 闲聊也会被强制调，模型可能乱填参数 |
| 指定函数 | 强制调用某个具体工具 | 只能这一个，失去自主性 |

本项目为什么用 `auto`：

1. 同一入口既要支持闲聊（「你好」）又要支持检索/建单，`required` 会把闲聊也变成工具调用；
2. 强制指定函数需要先做意图路由，等于把「模型决策」换成「规则决策」，引入另一套复杂度；
3. 副作用工具已经有人工确认兜底，不依赖 `tool_choice` 保安全。

**注意**：`required` 和「指定函数」在不同 provider 上的支持程度不一致，跨厂商移植时要查文档；本项目没有依赖它们。

### 3.4 怎么提高「该调时调、调对」的概率

按投入产出排序：

1. **把 description 当成 API 契约写**：写清触发场景、输入含义、边界和反例。对比：
   - 差：「查询信息」
   - 好：「在用户当前会话关联的知识库中检索相关内容。当问题可能与用户上传的资料/知识库有关时，调用它来获取可引用的依据，再据此回答。」
2. **参数名和描述显式化**：`query` 而不是 `q`；说明是自然语言还是关键词；封闭集合用枚举。
3. **system prompt 加行为引导**：例如「涉及用户资料时先检索再回答」。本项目目前较弱，是已知缺口。
4. **用历史做 few-shot**：在上下文里放一两次成功的工具调用示例，代价是 token。
5. **路由/规划**：先用小模型或规则判断意图，再只下发相关工具（减少 schema 干扰和 token），或直接指定 `tool_choice`。
6. **评测驱动迭代**：建「该调/不该调/调哪个/参数是什么」的评估集，改一版描述跑一遍，而不是凭感觉。
7. **微调/约束解码**：成本最高，通常最后才考虑。

### 3.5 为什么不能保证

- **概率性**：`temperature=0.3` 降低随机性，不等于确定性；`temperature=0` 也不保证跨版本稳定。
- **描述歧义**：自然语言描述必然有边界模糊，「可能有关」到底多可能？
- **上下文干扰**：历史里的错误调用、用户说「别查了」、工具结果里的注入文本，都会改变决策。
- **长上下文稀释**：工具 schema 和历史混在长 prompt 里，模型可能「看不见」。
- **模型能力上限**：工具一多、描述一像，选择准确率就下降。
- **provider 差异**：同一 prompt 换模型/换版本，行为可能明显变化。

所以工程上正确的姿势是：**用 prompt 提高概率，用宿主保证底线**。

### 3.6 怎么评测「决策对不对」

M1.5 的离线评测只测**检索本身**（Hit@K、MRR 等），测不到「模型是否愿意调 `searchKnowledge`」。要评测工具决策，需要单独的行为评估集：

| 维度 | 指标 | 例子 |
|---|---|---|
| 调不调 | 该调未调率、不该调却调率 | 「年假政策」应调检索；「你好」不应调 |
| 调哪个 | 工具选择准确率 / 集合完全匹配 | 应调 `searchKnowledge`，却调了 `getCurrentTime` |
| 参数 | 参数名/值正确率（结构化比对或语义判定） | `query` 是否抓住了问题核心 |
| 收敛 | 平均轮次、撞 8 轮比例 | 简单问题应 1–2 轮 |
| 结果 | 任务成功率、答案有据率（LLM-as-judge） | 回答是否引用了检索内容 |
| 稳定性 | 同题多次运行的方差 | 跑 5 次看调用一致性 |

当前项目**没有这套评测**，这是 [60-离线评测](60-离线评测.md) 第十一节明确记录的缺口。面试时主动说出来，比被问出来好。

### 3.7 本项目的关键取舍：检索从「自动」改成「工具」

M7 起，检索不再是每次对话自动执行，而是模型按需调用 `searchKnowledge`（决策记录见 [30 3.3](30-工具调用.md)）。

- **收益**：无关问题不检索，省 token；检索过程变成可见的 `tool_call`；工具与检索统一。
- **代价**：**召回取决于模型判断**。模型不调，就没有 RAG。自动检索是「必召回」，改工具后是「择机召回」。
- **退路**：加强系统提示；对特定知识库恢复强制检索；或在上游做意图路由后指定 `tool_choice`。

这是「模型决策」直接影响业务效果的最典型例子，面试官问「你怎么保证召回」时，必须承认这一层。

## 4. 宿主侧：收到 `tool_calls` 之后做什么

### 4.1 启动期：注册与校验

`AgentToolRegistry` 在构造时扫描所有 `AgentToolPack` Bean 的 `@Tool` 方法：

```
ToolSpecifications.toolSpecificationFrom(method)  → 生成 schema
name 全局唯一                                      → 重名直接启动失败
必须有 @ToolMeta                                   → 缺了启动失败
副作用工具必须「后端幂等」或「需人工确认」           → 否则启动失败
@ToolMemoryId 参数类型必须是 RunContext             → 否则启动失败
new DefaultToolExecutor(pack, method)              → 方法级执行器
```

**失败快原则**：配置错误在启动时炸，而不是等第一次对话。代价是工具集**启动后固定**，动态增删工具要重启（当前可接受，见第 7 节）。

### 4.2 一轮的完整顺序

`AgentRunner#drive`（`AgentRunner.java:162`）：

```
while (round < maxRounds):                       // 176
    SP1 查中断标志
    round++; seq++
    beginLlmStep(round, seq, 请求快照)            // PENDING
    streamOnce(ChatRequest{messages, specs})      // 阻塞桥接，delta 推 SSE
    归一化 toolCallId
    累计 token / 写 ai_call_log
    SP2 查中断标志（无条件）
    finishLlmStep(SUCCEEDED | INTERRUPTED)
    messages += aiMessage
    if 没有 toolExecutionRequests:
        return finish(ai.text)                    // 最终回答
    executeToolBatch(...)                         // 执行这一批
return finish(lastText 或 MAX_ROUNDS_MESSAGE)     // 撞护栏
```

`specs` 在进入 `drive` 时取一次（`AgentRunner.java:164`），整个 run 内不变；每轮都随请求重发。

### 4.3 执行单个工具

`executeAndRecord`（`AgentRunner.java:368`）与 `AgentToolRegistry#execute`（`AgentToolRegistry.java:201`）：

```
① 查 sideEffect / requireApproval（未知工具按 false）
② beginToolStep：先落一行 PENDING 意图（toolName / arguments / stepNo / seq）
③ 发 tool_call 事件
④ 需审批 → 整批挂起 WAITING_APPROVAL，线程释放
⑤ 副作用 → 幂等认领（认领时写 idempotencyKey）
⑥ registry.execute：
     - 未知工具 → 返回「未知工具 + 可用清单」，isError=true
     - DefaultToolExecutor.executeWithContext：
         JSON 参数 → 方法入参绑定 → 反射调用
         InvocationContext.chatMemoryId = RunContext（@ToolMemoryId 注入）
     - 任何异常 → catch → 返回错误文本，绝不向上抛
⑦ 结果截断（默认 4000 字符）
⑧ finishToolStep 回填同一行（SUCCEEDED / FAILED）
⑨ 发 tool_result 事件、写 ai_tool_log
⑩ messages += ToolExecutionResultMessage.from(req, text)
```

几个设计点：

- **意图行先提交，再执行**。崩溃后能知道「本来要做什么」，这是副作用治理的基础（[12](12-中断与恢复的状态机.md)）。
- **错误也是结果**。模型拿到「工具 X 执行失败：参数 assignee 缺失」后，可以下一轮改参数；如果直接抛异常，整个 run 就废了。
- **`@ToolMemoryId` 参数不进 schema**。`userId / conversationId / kbIds` 由宿主注入，模型看不到也改不了，这是防越权的关键（见 Q22）。
- **截断发生在回填前**，数据库和事件里都是截断后的文本；事件用 `truncated=true` 告知前端。
- **toolCallId 归一化**：模型偶尔不给 id，`normalizeToolCallIds` 补成 `call-{round}-{i}`（`AgentRunner.java:572`）。响应快照、`agent_step.toolCallId`、回填消息三处必须一致，否则续跑重放会拼出孤儿请求。

### 4.4 一批工具：顺序执行，整批成对

模型一次返回 N 个 `tool_calls` 时（`executeToolBatch`，`AgentRunner.java:267`）：

- **顺序执行**，不是并行。原因：副作用顺序、幂等认领、状态机简单、事件顺序可解释；
- 每个工具独立 `seq++`、独立意图行、独立 `tool_call` / `tool_result`；
- 遇到需审批的工具，**当前及之后的工具都不执行**，整批暂停；用户同意后从这一批继续，拒绝/停止时把剩余工具补成「未执行」的结果；
- 无论成功、失败、拒绝、停止，**每个 `tool_call` 最终都要有对应的结果消息**，否则下一轮请求不合法。

**并发不是不能做，是当前不做**：只读工具理论上可并行，但收益被模型调用耗时和状态写入复杂度抵消；副作用工具并行会破坏顺序和幂等语义。要做得先区分只读/副作用，再引入批次屏障。

### 4.5 工具结果的两种可见性（容易踩的坑）

| 范围 | 模型能看到什么 | 依据 |
|---|---|---|
| **同一次 run 内** | 完整消息链：assistant(tool_calls) + 每条 tool 结果 | `messages` 在内存里逐轮追加 |
| **下一次用户消息/新 run** | 只有 `conversation_message` 里的文本：用户消息 + 最终助手回答 | `MemoryBuilder` 重建，只取 `content` |

`MemoryBuilder` 明确不把 `toolCallsJson` 和工具结果放进 prompt（`MemoryBuilder.java:120` 附近）。原因：

1. 历史里的 tool_calls 和 tool 结果必须成对，重建时很容易拼出孤儿；
2. 工具结果通常很长，会把 16K 的历史预算吃光；
3. 最终回答已经是对结果的提炼，原始结果对下一轮未必有价值。

**代价**：用户下一轮追问「刚才你查到的第一条是什么」，模型看不到原始片段，只能重新调工具。这是有意的取舍，不是遗漏。副作用证据在 `agent_step`，不在对话记忆里。

### 4.6 事件与日志

| 事件 | 时机 | 内容 |
|---|---|---|
| `run_start` | run 开始 | runId / conversationId / messageId |
| `message_delta` | 每个文本分片 | 增量文本 |
| `tool_call` | 该轮响应结束后、执行前 | stepId / toolCallId / toolName / arguments / sideEffect |
| `tool_result` | 执行/重放后 | stepId / toolCallId / success / elapsedMs / result / truncated |
| `interrupt` | 挂起/待审批 | status / interruptType / pendingTool |
| `run_end` | 正常结束 | messageId / elapsedMs / rounds |

`ai_call_log` 记每轮模型调用（token、首 token 延迟、请求/响应快照），`ai_tool_log` 记每次工具执行（含 `replayed`、幂等键）。详见 [50-可观测性](50-可观测性.md)。

## 5. 上限：轮次、步骤、时间、token

### 5.1 先把三个词分开

这是面试官最容易抓混的地方，必须先定义：

| 词 | 定义 | 本项目对应 |
|---|---|---|
| **轮（round）** | 一次模型响应 + 它要求的一批工具执行 | `agent_step.stepNo`；`maxRounds` 计数单位 |
| **工具调用（tool call）** | 模型响应里的一条 `tool_calls[]` | `ToolExecutionRequest`；一行 `agent_step(type=TOOL_CALL)` |
| **步骤（step）** | 状态表里的一行：一次 LLM 调用或一次工具调用 | `agent_step`；`seq` 全局递增 |

一次运行的计数关系：

```
LLM 步数 = 轮数 R
工具步数 = 各轮工具调用数之和 T
总步数 = R + T
seq 最大值 = R + T（每次 LLM 占 1，每个工具占 1）
```

例：3 轮，每轮分别要 1、2、1 个工具 → 3 个 LLM 步 + 4 个工具步 = 7 个 step，seq 到 7。

### 5.2 `maxRounds` 是多少、在哪生效

- 默认 **8**（`AgentProperties.java:22`，配置项 `ai.agent.max-rounds`）；
- 创建 run 时会把当前值写入 `agent_run.maxRounds`（`AgentStateServiceImpl#createRun`），作为运行记录；
- 但 `AgentRunner#drive` 每次执行时读的是**当前配置**（`agentProperties.getMaxRounds()`，`AgentRunner.java:165`），
  不是 `agent_run.maxRounds`。所以运行中改配置再续跑，实际护栏会跟着变，**记录值与实际值可能不一致**；
- 循环条件在 `AgentRunner.java:176`：`while (round < maxRounds)`；
- 每轮开头 `round++`，**计数的是模型调用次数**，不是工具数。

所以：

- 最多 **8 次模型调用**；
- 每轮可以执行 **N 个工具**，N 由模型/provider 决定，本项目**没有单独的工具数上限**；
- 理论上最多 8 × N 次工具执行；实际 N 通常很小（1–3）。

### 5.3 撞到 8 轮会发生什么

代码路径（`AgentRunner.java:244-246`）：

```
log.warn("撞到 maxRounds")
answer = lastText 非空 ? lastText : MAX_ROUNDS_MESSAGE
return finish(answer, ..., maxRoundsHit=true)
```

具体行为：

1. **第 8 轮模型仍要求调工具时，工具照样执行并落库**（`executeToolBatch` 在循环体内）；
2. 执行完后 `round=8`，循环条件不满足，退出；
3. **这些工具结果追加进了内存 messages，但没有下一次模型调用去读它们**；
4. 最终回答取 `lastText`——第 8 轮 assistant 的文本（可能为 null/空），否则用兜底话术；
5. run 状态是 **`COMPLETED`**，不是 `FAILED`；`run_end` 里 `rounds=8`；`maxRoundsHit` 只在方法返回值里，**没有单独落库字段**。

这意味着一个真实边界：

> **第 8 轮的工具可能是「白跑」的**：副作用已经发生、结果已经记库，但模型没机会基于它给用户收尾。用户看到的是「我再查一下」或兜底提示。

面试官若追问「这算 bug 吗」，正确答法是：这是「护栏优先于完整性」的取舍。要修有两个方向：

- 在 `round == maxRounds` 且仍有工具请求时，**不再执行**，直接用兜底话术收尾，避免副作用白发生；
- 或者把护栏解释成「最多 8 轮行动 + 1 轮收尾」，允许第 9 次调用但强制不带工具（`tool_choice=none`）。本项目没做，属于已知改进点。

### 5.4 为什么是 8

- 这类 RAG 问答/轻量工具任务，正常 **1–2 轮**就结束；建单类最多 3 轮；
- 8 给了足够余量，同时把最坏成本和延迟压住；
- 它是**经验值，未标定**（和项目里其他参数一样，不假装有数据支撑）；
- 它的作用不是「保证任务能完成」，而是「保证不会无限烧钱」。

如果要更严谨，可以按任务类型配置、加 token 预算、或做「无进展检测」，但目前没有。

### 5.5 续跑会不会重置轮次

不会。`resume` 接收 `round0 / seq0 / in0 / out0`，从已完成轮数继续累加（`AgentRunner.java:151`）：

- 第 3 轮被中断（该轮不完整），续跑从 `round0=2` 开始、重新生成第 3 轮，总预算仍是 8；
- token 也接着累计，不重置；
- 中断、审批、崩溃恢复都**不会**给你「重新 8 轮」。

这是一个容易被忽略的点：**护栏是按 run 计的，不是按线程/按续跑次数计的**。

### 5.6 其他上限与闸门

| 闸门 | 值 | 作用范围 | 备注 |
|---|---|---|---|
| `maxRounds` | 8 | 每次 run 的模型调用次数 | 撞顶仍 `COMPLETED` |
| `maxToolResultChars` | 4000 字符 | 单个工具结果 | 截断后加「…（结果已截断）」，总长会略超 |
| 上下文预算 | 16000 token（`ai.memory.context-window`）；历史可用 ≈ (16000 − 2048 − 系统提示词) × 0.8 | **只在构建 prompt 时** | run 内新增的工具结果**不会**再按预算裁剪 |
| 单条用户输入 | 4000 字符 | 入口校验 | 与工具结果上限同值但无关 |
| LLM 超时 | 60s | 单次模型调用 | `ai.chat.timeout` |
| 工具超时 | **无** | 单次工具执行 | 工具卡住会占住 agent 线程 |
| run 总时长 | **无** | 整个 run | SSE 300s 只是连接生命周期，不是 run 超时 |
| SSE 连接 | 300s + 15s 心跳 | 单条 SSE | 超时只断连接，循环可能继续 |
| SUSPENDED 保留 | 24h | 挂起运行 | 超时封存为 `CANCELLED` |
| agent 线程池 | core 2 / max 4 / queue 100 | 并发 run | `CallerRunsPolicy` 背压 |

**重点承认**：本项目没有「单 run token 上限」「工具执行超时」「总时长上限」。这三项是生产化前应该补的。

### 5.7 一次运行最多多少 step

严格回答：

```
最多 LLM step = 8
最多 tool step = 8 × N（N = 单轮模型返回的工具数，无本项目上限）
最多 step 总数 = 8 + 8N
seq 最大值通常等于 step 总数（从 1 开始）
```

若面试官追问「为什么不定一个 step 总数上限」：

- step 数由模型单轮工具数决定，**不是宿主能提前知道的值**；
- 宿主必须处理模型给的全部 `tool_calls`，否则消息配对不完整；
- 要防工具爆炸，正确的位置是「限制单轮工具数」或「限制 run 总 token」，而不是事后限制 step 行数；
- 当前两者都没做，是已知边界。

### 5.8 这些护栏防什么、不防什么

| 能防 | 不能防 |
|---|---|
| 模型无限要求调工具导致的轮次爆炸 | 单轮返回大量工具造成的成本尖峰 |
| 结果过长顶爆上下文 | run 内累积结果超过 16K 预算（预算只在入口生效） |
| 副作用工具重复执行（同一步的恢复重放） | 模型在不同轮用相同参数重复调用（幂等键含 stepNo，不算重试） |
| 崩溃后不知道做了什么 | 工具内部卡死、第三方接口不返回 |
| 用户重复点击同意导致重复执行 | run 总时长失控 |

## 6. 两个完整例子

### 6.1 「现在几点了？」——最短的工具调用

```
用户消息落库
MemoryBuilder → [System, User("现在几点了？")]

round=1
  ChatRequest{messages, tools=[3 个]}
  模型返回：content=null, tool_calls=[getCurrentTime, id=call-1-1]
  messages += assistant(tool_calls)
  事件：tool_call {toolName:"getCurrentTime", arguments:{}}
  执行：返回「当前时间：2026-10-29 15:20:31（周四）……」
  事件：tool_result {success:true, elapsedMs:2}
  messages += tool(result)

round=2
  模型看到工具结果，返回：content="现在是 2026 年 10 月 29 日 15:20，周四。"
  messages += assistant(text)
  没有 tool_calls → finish
  落助手消息、run_end(COMPLETED, rounds=2)
```

模型侧发生了什么：时间工具的描述里明确写了「现在/今天/几号/几点」，用户问题命中这些词，模型生成 `tool_calls` 的概率高。不是规则匹配，是语义相似 + 训练对齐。

### 6.2 「查一下年假政策，然后帮我建个工单」——多轮 + 审批

```
round=1
  tool_calls=[searchKnowledge(query="年假政策")]
  → tool_call / tool_result（检索片段）
  messages += 结果

round=2
  模型看到片段，决定建单：
  tool_calls=[createTicket(title="咨询年假政策", assignee="hr")]
  → 落意图行 PENDING
  → tool_call 事件
  → requireApproval=true → WAITING_APPROVAL
  → interrupt(APPROVAL_REQUIRED, pendingTool)
  → 循环 return，线程释放（不写助手消息）

用户点同意
  → approveRun：WAITING_APPROVAL → RUNNING（条件更新防双击）
  → 认领幂等键（此刻才生成）
  → 执行 createTicket 恰好一次
  → tool_result
  → ResumePlanner 重建消息（重放完整轮）
  → AgentRunner.resume(round0=2)

round=3
  模型看到工单号，返回最终回答
  → COMPLETED
```

如果用户拒绝：

```
→ denyApproval：WAITING_APPROVAL → SUSPENDED
→ 把待确认及后续工具补成「用户拒绝执行该操作，操作未执行。原因：…」
→ 模型下次续跑时能看到这条结果，换方案或向用户解释
```

这个例子里，模型负责「想做什么」，宿主负责「能不能做、做几次、失败怎么办」。

## 7. 边界与坑（带代码依据）

| # | 坑 | 现象/后果 | 依据 / 对策 |
|---|---|---|---|
| 1 | **模型不调工具** | 检索改工具后，模型不调 `searchKnowledge` 就没有 RAG | 只能靠描述/prompt/评测；退路见 3.7；未解决 |
| 2 | **第 8 轮工具白跑** | 工具已执行、结果已落库，模型看不到 | `AgentRunner.java:244`；改进见 5.3 |
| 3 | **跨轮重复调用无检测** | 模型每轮用相同参数调同一工具，会执行 8 次 | 只靠 `maxRounds`；幂等键含 `stepNo`，跨轮不算重试；副作用工具靠审批 |
| 4 | **工具结果是指令注入面** | 检索文档/接口返回里藏「忽略之前指令」 | 结果原样回填；当前只有只读 + 审批兜底，没有内容清洗（见 Q25） |
| 5 | **截断按字符不按 token** | 4000 字符约 6000 估算 token（系数 1.5） | 两个结果就可能超过 16K 历史预算；但模型上下文 1M，不会报错，只是成本失控 |
| 6 | **16K 预算只在入口生效** | run 内新增的工具结果不参与裁剪 | `MemoryBuilder` 只在建 prompt 时算预算；8 轮可能持续膨胀 |
| 7 | **工具没有执行超时** | 第三方接口卡住 → agent 线程一直占用 | 线程池只有 2/4；需要超时/熔断 |
| 8 | **「并行工具调用」实际串行** | 模型一次返回多个，宿主顺序执行，延迟叠加 | `executeToolBatch` 的 for 循环；安全优先 |
| 9 | **tool_call 事件滞后** | 模型开始生成工具调用时前端无感知，响应结束才发 | 流式参数分片，`onCompleteResponse` 才完整 |
| 10 | **审批整批暂停** | 一批里有一个需确认，后面的只读工具也不执行 | 保证消息配对与顺序；用户体验代价 |
| 11 | **工具集启动固定** | 新增工具需重启；run 进行中换工具集不可能 | 注册在构造器完成 |
| 12 | **非流式接口不接工具** | `POST /chat/message` 是简化路径，无检索、无 run | `ChatServiceImpl` 直接 `model.chat`，不传 tools |
| 13 | **跨 run 丢失工具上下文** | 下一轮模型看不到原始工具结果 | `MemoryBuilder` 只取 `content`；见 4.5 |
| 14 | **撞顶仍记 COMPLETED** | 监控上看起来「成功」，实际是兜底话术 | `finish(maxRoundsHit=true)` 未落库；需要加字段/事件 |
| 15 | **`tool_choice` 能力差异** | 换 provider 后 `required`/指定函数可能不接受 | 本项目只用 auto，规避了差异 |
| 16 | **多实例 SSE 不跨实例** | 重连到别的实例收不到后续 delta | `AgentStreamHub` 是进程内 Map；见 Q29 |
| 17 | **轮次配置的记录值与实际值可能不一致** | `agent_run.maxRounds` 是创建时快照，但循环每次读当前配置 | 运行中改 `ai.agent.max-rounds` 再续跑，实际护栏会变；见 5.2 |

## 8. 面试拷打 33 问

> 用法：先讲第 0 节的七句，再按追问挑。每题都尽量带「为什么」和「代价」，不要只背结论。

### 8.1 协议与模型（Q1–Q10）

**Q1：大模型是怎么「调用工具」的？它真的执行了吗？**

没有。模型只生成一条 assistant 消息，里面带结构化的 `tool_calls`（工具名 + JSON 字符串参数 + id）。真正执行的是宿主：查注册表、绑定参数、反射调用、把结果作为 `role=tool` 消息回填，再调一次模型。模型全程看不到工具实现，也不知道副作用是否真的发生；宿主才是事实源。

**追问：那模型怎么「知道」工具执行成功了？**

它不知道，只知道你回填了什么。所以工具结果必须诚实：失败就回失败文本，不能伪装成功。

**Q2：我给模型一个工具，它怎么知道什么时候该用？**

它在生成时做概率决策，输入包括工具名、description、参数 schema、`tool_choice`、system prompt、历史消息和当前问题。支持 function calling 的模型在训练中见过大量「这类请求 → 输出工具调用」的样本，所以语义匹配时会倾向生成 `tool_calls`。不是规则引擎，也不是独立的分类器。description 就是它眼里的 API 文档。

**追问：那它怎么知道「不该用」？**

同样靠训练和描述里的边界。但**无法保证**，所以宿主必须处理「不该调却调了」的情况（执行了只读工具、浪费 token；副作用工具还有审批）。

**Q3：`tool_choice` 有哪些值？你为什么用 `auto`？**

四档：`auto`（模型自由）、`none`（禁止）、`required`（至少调一个）、指定具体函数（强制某个）。本项目不传 `tool_choice`，OpenAI 兼容协议缺省是 `auto`。原因：同一入口要兼容闲聊和工具场景，`required` 会把「你好」也变成工具调用；指定函数要先做意图路由，等于换一套规则决策。副作用安全已经由人工确认兜底，不需要靠强制。

**Q4：你能保证模型一定调用工具吗？**

不能保证「调对」，只能在特定场景强制「至少调一个」（`required`）或「只准调某个」（指定函数），但那会带来新的问题：闲聊被误调、参数乱填、失去自主性。本项目的选择是 `auto` + 描述引导 + 评测，接受「可能漏调」，并用宿主兜住其它错误。

**Q5：模型编了一个不存在的工具名怎么办？**

`AgentToolRegistry#execute` 查不到执行器时，不抛异常，而是返回一条结果：「未知工具「X」。可用工具：……。请只调用已提供的工具。」模型下一轮可以改口。如果它继续编，轮次护栏会兜住。关键点是：**错误作为观察回给模型，而不是炸掉整个 run**。

**Q6：参数 JSON 坏了、字段类型不对怎么办？**

`DefaultToolExecutor` 负责 JSON → 方法入参绑定；绑定失败会抛异常，`AgentToolRegistry#execute` 统一 catch 成 `ToolRunResult(isError=true)`，再把错误文本回填。模型看到「assignee 缺失/类型不对」后可以重试。宿主不会因为模型写了坏 JSON 就中断运行。

**追问：那会不会无限重试坏参数？**

会消耗轮次，但最多 8 轮；没有专门的「同一参数错误重复 N 次就停」检测，这是已知缺口。

**Q7：模型一次返回多个工具调用，怎么处理？**

顺序执行。每个工具独立 `seq`、独立意图行、独立 `tool_call` / `tool_result`、独立结果消息。遇到需审批的工具整批暂停；无论成功失败，每个 `tool_call` 都必须有对应结果，否则下一次请求不合法。当前不做并行，原因是副作用顺序、幂等认领和状态机复杂度。

**Q8：一条 assistant 消息里既有文本又有 `tool_calls`，那段文本算最终回答吗？**

不算。只要 `hasToolExecutionRequests()` 为真，就继续循环。文本会先流给用户（看起来像「我查一下」），并记入 `lastText`；正常收尾时用最后一轮无工具的文本。边界是：如果撞到 8 轮，`lastText` 可能被当作最终答案，用户就会看到一句没头没尾的「我查一下」。这是 5.3 的已知问题。

**Q9：工具结果为什么要用 `role=tool` 回填，不能直接拼进用户消息吗？**

协议要求：`role=tool` 必须带 `tool_call_id`，与 assistant 的 `tool_calls` 一一配对。直接拼进 user 消息会破坏配对语义，模型也难以区分「用户说的」和「工具观察到的」；审计和重放也会失去边界。LC4j 用 `ToolExecutionResultMessage.from(req, text)` 保证 id 一致。

**Q10：模型看不到工具实现，怎么保证它参数填对？**

保证不了语义正确，只能降低错误率：参数名和描述写清楚、封闭集合用枚举、必填项标 required；宿主再做类型绑定和业务校验，错了回填错误让模型改。真正危险的参数（用户 id、知识库范围）根本不进 schema，由 `@ToolMemoryId` 注入。

### 8.2 循环与步数（Q11–Q20）

**Q11：工具调用最多几轮？**

默认 8 轮，配置项 `ai.agent.max-rounds`，创建 run 时写入 `agent_run.maxRounds`。一轮 = 一次模型响应 + 它要求的一批工具执行。注意是 8 次**模型调用**，不是 8 次工具。

**Q12：轮、step、工具调用有什么区别？**

轮是循环单位；工具调用是模型响应里的一条 `tool_calls[]`；step 是 `agent_step` 表里的一行（LLM_CALL 或 TOOL_CALL）。一次 run 的 LLM step 数 = 轮数，tool step 数 = 各轮工具数之和，seq 按发生顺序全局递增。

**Q13：为什么是 8？有数据支撑吗？**

没有标定，是经验值。正常 RAG 问答 1–2 轮，建单 2–3 轮，8 留了余量；它的目标是防无限循环和成本失控，不是保证任务完成。可以按任务类型配置或用 token 预算替代，但目前没做。

**Q14：第 8 轮模型还要调工具，会发生什么？**

工具仍会执行并落库，但循环退出，结果不会再喂给模型；最终回答取第 8 轮 assistant 的文本，没有就用兜底话术；run 记 `COMPLETED`，`rounds=8`。也就是说副作用可能已经发生，但模型没机会基于结果收尾。改进方向：撞顶时不再执行工具，或允许多一轮只收尾、强制 `tool_choice=none`。

**Q15：一次 run 最多执行多少次工具？**

没有单独上限。每轮 N 个，最多 8×N；N 由模型/provider 决定。宿主必须处理全部，否则消息配对不完整。要防工具爆炸，应该限制单轮工具数或 run 总 token，当前两者都没做。

**Q16：怎么防止模型死循环调同一个工具？**

当前只有轮次护栏：最坏执行 8 轮后停。没有「同工具同参数重复检测」。幂等键包含 `stepNo`，只防同一步的恢复重放，**不防模型在下一轮再次发起相同调用**；副作用工具靠每次人工确认兜底。要更强，可以加 `(toolName, canonical(args))` 最近 N 步去重，或检测无进展后提前收敛。

**Q17：中断续跑会把轮次重置吗？**

不会。`resume` 从 `round0` 继续，token 也接着累计。护栏是按 run 计的，不是按续跑次数计的。所以反复中断续跑不能绕过 8 轮上限。

**Q18：为什么不用 LangChain4j `AiServices` 的 `maxToolCallingRoundTrips`？**

它是内存循环，跑完才返回，中间没有钩子；本项目需要在每次模型/工具调用前后落 `agent_step`、发事件、查中断标志、做审批和幂等。于是借它的 `@Tool` schema 和 `DefaultToolExecutor`，循环自己写，`maxRounds` 就是自研版的 `maxToolCallingRoundTrips`。

**Q19：一次 run 最长能跑多久？**

没有总时长上限。LLM 单次调用有 60s 超时；工具执行没有统一超时；SSE 的 300s 只是连接生命周期，连接断了循环可能继续；挂起的 run 24h 后封存。工具卡死会一直占着 agent 线程，这是生产化前必须补的。

**Q20：循环跑在哪个线程？会阻塞吗？**

跑在专用 `agentExecutor`（core 2 / max 4 / queue 100 / `CallerRunsPolicy`）。LC4j 流式是回调式，`streamOnce` 用 `CompletableFuture` 桥接成阻塞等待，所以一次活跃 run 占一个线程；请求线程在建完 SSE 后就释放；挂起/等审批时线程也释放。并发能力目前很有限。

### 8.3 执行与可靠性（Q21–Q28）

**Q21：工具执行失败会中断整个 Agent 吗？**

不会。工具异常、参数绑定异常、未知工具都转成 `ToolRunResult(isError=true)` 回给模型，让模型自纠或改口。只有模型调用本身失败、系统异常才会走 `catch` → `FAILED`。这是「错误是观察，不是崩溃」的设计。

**Q22：为什么工具意图行要先落库再执行？**

为了崩溃安全：进程在「已执行、未记录」之间挂掉，是副作用系统最危险的状态。先落 PENDING 意图行，再执行，再回填结果；恢复时能判断「本来要做什么、做到哪一步」。同时它也是幂等认领和审计的锚点。

**Q23：副作用工具怎么保证只执行一次？**

三层：① 审批（`requireApproval`）让用户把关；② 幂等键（runId + stepNo + toolName + 规范化参数）在认领时写入，唯一索引防并发；③ 条件状态更新防双击 approve。撞键时有结果就重放，无结果就转人工，绝不自动重跑。注意：这只保证「同一步」恰好一次；模型在**不同轮**再次发起相同调用算新步骤，不在幂等覆盖范围内。

**Q24：用户拒绝审批后，模型看到什么？**

看到一条工具结果：「用户拒绝执行该操作，操作未执行。原因：…」。同时把这一批剩余工具补成未执行结果，保证消息配对；run 进入 `SUSPENDED`，用户续跑后模型能基于拒绝原因换方案。这样拒绝不是「静默消失」，而是可观察的反馈。

**Q25：工具结果里如果有恶意指令（间接提示注入）怎么办？**

确实存在：检索到的文档、第三方接口返回都可能包含「忽略之前指令」之类的内容，模型会把它当上下文。当前项目的缓解是：工具只读、副作用工具必须人工确认、`RunContext` 不进模型参数；但**没有对工具结果做内容清洗或隔离**。生产上要加来源标记、指令/数据分离、输出过滤，以及最小权限。这是已知风险，不应粉饰。

**Q26：为什么工具调用的中间消息不落 `conversation_message`？**

因为下一步重建 prompt 时，必须保证 assistant(tool_calls) 和 tool 结果成对；跨 run 重建很容易拼出孤儿请求。而且工具结果通常很长，会挤占历史预算。代价是下一轮模型看不到原始工具结果，只能看到最终回答；需要原始数据时得重新调工具。证据留在 `agent_step`，不在对话记忆里。

**Q27：为什么 `tool_call` 事件不是「模型一开始决定调工具」就发？**

OpenAI 兼容协议的流式响应里，工具名和参数是分片到达的，只有 `onCompleteResponse` 才拿到完整 `toolExecutionRequests`；`onPartialResponse` 只有文本。所以事件在该轮响应结束后才发。要更早提示，得用 `onPartialToolCall`，本项目没用。

**Q28：客户端断开或用户点停止，工具循环会停吗？**

断开连接不会停：循环继续跑，只是推流被跳过。用户点停止（或发新消息）会写 Redis 中断标志，循环在两个安全点检查后挂起；流式回调里也会在 200ms 节流检查后抑制 delta，让用户看到字立刻停。工具执行本身不可中断：要么没开始，要么执行完。

### 8.4 工程与边界（Q29–Q33）

**Q29：多实例部署有什么问题？**

状态在 MySQL、中断标志在 Redis，跨实例可用；但 `AgentStreamHub` 是进程内 Map，SSE 必须粘到跑循环的实例，否则重连只能读库补发事件，收不到后续 delta。要真正多实例，需要 Redis Pub/Sub 或 MQ 广播事件。当前是单实例，已知限制。

**Q30：加一个新工具的完整步骤？**

实现 `AgentToolPack` + `@Tool`（写清何时调用）+ `@ToolMeta`（displayName、sideEffect、idempotentBackend、requireApproval、source）；参数用 `@P` 显式命名，运行态信息用 `@ToolMemoryId RunContext` 注入；启动时会做重名、元信息、副作用安全声明的校验；补单测（schema、执行、错误路径）；前端通过 `GET /tools/list` 自动展示。副作用工具要么后端幂等，要么必须审批，否则启动失败。

**Q31：你怎么评测「模型该不该调工具」？**

需要单独的行为评估集：按「该调/不该调/调哪个/参数是什么」标注，测调用率、工具选择准确率、参数准确率、平均轮次、撞顶比例、任务成功率和多次运行方差。M1.5 只测检索本身，测不到工具决策，这是明确缺口。改进时用同一套集子做描述/提示词的 A/B。

**Q32：这套设计最大的风险是什么？**

按影响排序：① 模型漏调检索导致无 RAG，且没有行为评测；② 跨轮重复调用和 8 轮撞顶的语义问题；③ 工具结果注入；④ 没有工具超时和 run 总时长/token 上限；⑤ 单实例线程池并发能力弱。前两个直接影响正确性，后三个影响生产稳定性。

**Q33：为什么把检索从自动改成工具？**

省 token（无关问题不检索）、过程可解释（`tool_call` 可见）、工具与检索统一，且符合项目一开始的架构。代价是召回依赖模型判断：自动检索是「必召回」，工具是「择机召回」。这个行为变化必须用 Agent 行为评测来验证，必要时加强提示或对特定知识库强制检索。
