# 工具调用

> 状态：**M7「只读工具调用的内存内循环」已实现（2026-10-14）**。循环里的**中断、状态落库、副作用工具、人工确认均未做**（属 M8/M9/M10）。
> 前端契约见 [frontend/60-tools](../frontend/60-tools-工具.md)；事件契约见 [frontend/02-SSE协议规范](../frontend/02-SSE协议规范.md)。

## ① 这个模块治的是哪类病（通用问题定义）

大模型只能**生成文本**，不能真的「做事」——它读不了数据库、发不了工单、查不了实时信息。要让它「动手」，需要一套协议：**模型用一段结构化输出表达「我想调用某个能力、参数是什么」→ 宿主解析它、真正执行 → 把结果作为新消息回填给模型 → 模型据此继续**。

所以这个模块要解决的本质问题是：

> **怎么把后端的一批能力「暴露」给模型，让它自己判断该不该调、怎么填参数；并在一轮轮「模型 → 工具 → 模型」之间把控制流接起来，同时挡住模型乱调、反复调、把整轮拖垮。**

它在整条链路里的**位置**：上游是「对话循环 / Agent 编排」（决定何时发起调用），下游是「具体后端能力」（真正干活的那些方法）。它管「**暴露能力 + 执行被点名的工具 + 收口模型的乱来**」，不管「运行状态、中断、续跑」（那是 [12-中断与恢复的状态机](12-中断与恢复的状态机.md)），也不管「调用过程怎么传给前端」（那是 [31-流式输出SSE](31-流式输出SSE.md)）。

### 它的边界

| 归它管 | 不归它管 |
|---|---|
| 工具契约（怎么标注、schema 怎么来）与注册 | 模型怎么决定调用（那是模型能力，不是我们能设计的） |
| 一次工具调用的执行、结果、错误收口 | 运行状态持久化 / 中断 / 续跑（[12](12-中断与恢复的状态机.md)） |
| 循环的收敛约束（轮次护栏、结果截断） | 调用过程怎么推给前端（[31](31-流式输出SSE.md)） |
| 副作用分级（只读 / 有副作用）的**声明** | 副作用工具的执行保证（人工确认、幂等）——那是 M10，见 [12](12-中断与恢复的状态机.md) |

### 四类典型失败模式

| # | 失败模式 | 后果 | 本模块的对策 |
|---|---|---|---|
| 1 | **模型点名了不存在的工具**（幻觉工具名） | 反射找不到方法 → 抛异常 → 整轮崩 | 回一条可读错误（含可用工具清单）给模型，让它改口 |
| 2 | **模型不调该调的工具**（如该检索却不检索） | 答非所问、凭空编造 | 工具的 `description` 写清楚「什么时候该调」；但**无法保证**，见 ⑤ 坑 7 |
| 3 | **循环不收敛**（反复调工具，永不收尾） | 成本与延迟失控 | `maxRounds` 护栏，到顶即停 |
| 4 | **参数错 / 工具自身抛异常** | 拖垮整轮运行 | 不只读工具的错误不影响循环：把错误当**工具结果**回给模型 |

## ② LangChain4j 官方怎么做

官方文档：<https://docs.langchain4j.dev/tutorials/tools/>（本项目用的是 **`langchain4j-core 1.20.0` + `langchain4j 1.20.0`**）

**核心类**（`dev.langchain4j.agent.tool` / `dev.langchain4j.service.tool`）：

| 类 / 注解 | 模块 | 作用 |
|---|---|---|
| `@Tool` | core | 标注方法为工具。`name()` 默认取方法名，`value()` 是给模型的描述 |
| `@P` | core | 标注参数：`name` / `description` / `required` / `defaultValue` |
| `@ToolMemoryId` | core | 标注的参数**不进 schema**，由框架把运行态的 `memoryId` 注入进去 |
| `ToolSpecifications.toolSpecificationsFrom(Object)` / `toolSpecificationFrom(Method)` | core | 反射生成 `ToolSpecification`（JSON schema） |
| `ToolExecutionRequest`（`id`/`name`/`arguments`） / `ToolExecutionResultMessage` | core | 工具调用的「请求」与「结果」消息 |
| `DefaultToolExecutor` | `langchain4j` | 把 `arguments` 的 JSON 绑定到方法入参并反射调用，返回 `ToolExecutionResult`（`isError` / `resultText`） |
| `AiServices` + `maxToolCallingRoundTrips` | `langchain4j` | 把上面这些**串成一个自动循环**，并带轮次护栏 |

**官方给什么**：协议转换、schema 生成、JSON→POJO 绑定、厂商适配，以及一个**开箱即用的自动循环**（`AiServices`）。

**官方不给什么**：把「模型点了哪个工具、结果是什么」变成**事件**推给前端；把**运行状态**落库以支持中断/续跑；副作用的**分级与确认**。这些它要么不管，要么按它自己的模型管（`AiServices` 的循环在内存里跑完就返回）。

> 「官方不给事件、不给可恢复的执行」这句只对 1.20.0 成立。官方另有 `langchain4j-agentic`（1.20.0-beta30）支持挂起/恢复，本项目**评估后未采用**，理由见 [12](12-中断与恢复的状态机.md) ②。升级时要复核。

## ③ 本项目为什么这么落地

### 3.1 用官方的「零件」，自研「循环」

和 [12](12-中断与恢复的状态机.md) 的立场一致：**`@Tool` 的 schema 生成、`DefaultToolExecutor` 的 JSON→POJO 绑定与调用，直接用官方**（这部分框架做得比自写好，见 [01](01-总体架构与路线图.md) 的取舍表）；**「模型 → 工具 → 模型」的循环自研**。

**为什么不用 `AiServices` 的自动循环**：它是内存里跑完就返回的黑盒，中间**没有钩子**让我们在「每次工具调用前后」发事件（`tool_call` / `tool_result`），将来也没有地方插入「落库意图行」「检查中断标志」。而这些恰恰是本项目后续（M8/M9）的核心。所以：**借它的零件，不用它的循环。**

**为什么用 `DefaultToolExecutor(bean, method)`（方法级）而不是 `ToolService`**：`ToolService` 是 LC4j 的 `@Internal` 类（可能随版本变），不直接用。方法级构造器还有个好处：它**按方法引用**调用，所以 `@Tool(name="自定义名")` 与 Java 方法名**可以不一致**（见 ⑤ 坑 1）。

**落地位置**：
- 契约与注册：`agent/AgentToolPack`（标记接口）、`agent/AgentToolRegistry`（扫描 + 建映射 + 执行）
- 循环：`agent/AgentLoop`（阻塞式 ReAct 主循环 + 护栏）
- 事件出口：`agent/AgentEventSink`（循环与传输解耦）
- 工具：`agent/tool/SystemTimeTool`、`agent/tool/KnowledgeTool`
- 接线与 SSE：`service/impl/ChatStreamServiceImpl`
- 配置 / 线程池：`config/AgentProperties`（`ai.agent.*`）、`config/AgentExecutorConfig`
- 清单接口：`controller/ToolController`（`GET /tools/list`）

### 3.2 工具集（M7）

| 工具 | 只读 | 说明 |
|---|---|---|
| `getCurrentTime` | 是 | 补充模型「不知道现在几点」的缺失；最容易复现的演示 |
| `searchKnowledge` | 是 | **RAG 的入口**（见 3.3） |

`createTicket` 等**有副作用**的工具属 M10（需人工确认），M7 不做。

### 3.3 ⚠️ 决策记录：检索从「自动」改为「工具」（2026-10-14）

- **原设计**（M6 起）：每次对话**自动**检索并把命中片段拼进 system prompt（见 [31](31-流式输出SSE.md) 较早的版本）。
- **新设计**（M7 起）：检索改由模型**按需调用** `searchKnowledge` 工具；流式对话里的**自动检索已移除**。
- **为什么改**：整套文档（[01](01-总体架构与路线图.md) 的分层图、[12](12-中断与恢复的状态机.md) 的示例运行）从一开始就把 `searchKnowledge` 当作**工具**，`frontend/60` 也这么定义。自动检索是 M6 阶段的**权宜之计**——那时还没有工具循环，要在对话里用上知识库只能硬塞。M7 有了循环，就该回到「工具」这个正统形态：省 token（无关问题不检索）、可解释（检索过程是可见的 `tool_call`），且和后续「工具 == 检索 == 其它能力」统一。
- **代价（必须承认）**：**模型不调就不召回**。自动检索是「必检索」，改工具后变成「择机检索」，RAG 的召回**取决于模型判断**。这不一定是坏事，但**是个行为变化，需要用评测集验证**是否可接受（见 [60-离线评测](60-离线评测.md)）。若评测证明模型不调，退路是给系统提示词加更强的「涉及已知资料时先检索」引导，或对特定 kbIds 恢复强制检索。

### 3.4 护栏与收口（循环的自研部分）

- **`maxRounds` 护栏**：默认 8 轮（`ai.agent.max-rounds`）。到顶即停，返回最后一轮文本或一条兜底提示。这是 LC4j `maxToolCallingRoundTrips` 的等价物。
- **工具结果截断**：单个结果超过 `ai.agent.max-tool-result-chars`（默认 4000 字符）就截断——结果要进 prompt，不截会顶穿预算。事件里用 `truncated=true` 告知前端。
- **错误一律回文本**：工具执行失败 / 未知工具名，都转成一条「结果文本」回给模型（而不是抛异常），让模型自行纠正或改口（`AgentToolRegistry#execute` 保证不向上抛）。
- **启动即校验**：工具重名、缺 `@ToolMeta`、`@ToolMemoryId` 参数类型不是 `RunContext`，都在**注册时**抛异常（模块 11 的失败快原则，见 [02](02-模块清单与依赖关系.md)）。

### 3.5 运行态怎么进工具：`RunContext` + `@ToolMemoryId`

`searchKnowledge` 要知道「查哪些库、属于谁」。这些是**运行态信息**，不能进模型可见的参数表（否则模型得猜，还可能编）。做法是把它们放进 `agent/RunContext`（`userId` / `conversationId` / `kbIds`），作为 `@ToolMemoryId` 参数注入——LC4j 会把它从 schema 里剔除，只做运行时注入。

### 3.6 线程模型：循环阻塞在专用线程池上

LC4j 的流式是**回调式**的（`StreamingChatModel#chat` 注册 handler 后立即返回）。要把它写成直白的顺序循环，`AgentLoop` 用 `CompletableFuture` 把「一次调用」**桥接成阻塞等待**（回调里推 delta、结束时完成 future）。

因此循环**必须跑在独立线程池**（`agentExecutor`），不能占请求线程：控制器返回 `SseEmitter` 后请求线程要立刻释放，连接由别的线程喂事件。代价是**一次运行占一个线程**——当前池子开得小（core 2 / max 4）。这是 M7 的简化，M8 引入「挂起释放线程」后要重新评估（见 ⑤ 坑 6）。

## ④ 数据结构与流程时序

### 一次带工具调用的对话（M7）

```
请求线程                                    agentExecutor 线程            SSE
  │
  ├─ 校验 / 会话归属 / 取流式模型（缺则 50001，且不写数据）
  ├─ 事务#1 落用户消息
  ├─ 建 RunContext（userId / conversationId / 生效 kbIds）
  ├─ MemoryBuilder.build(convId, SYSTEM_PROMPT) 重建 prompt（不再含检索块）
  ├─ 建 SseEmitter(300s)，send run_start ──────────────────────────────► run_start
  └─ agentExecutor.execute(循环) ──►  ┌ round=1：
                                      │   ChatRequest{ messages, toolSpecifications } → 流式调模型
                                      │     onPartialResponse ──────────────────► message_delta
                                      │   onCompleteResponse：aiMessage.hasToolExecutionRequests()?
                                      │     ├─ 是：对每个 request：
                                      │     │     sink.onToolCall ──────────────► tool_call
                                      │     │     执行工具（RunContext 注入）
                                      │     │     sink.onToolResult ────────────► tool_result
                                      │     │     messages += ToolExecutionResultMessage
                                      │     │     → 下一轮
                                      │     └─ 否：终极回答，退出循环
                                      └ 循环线程：事务#2 落助手消息 → send run_end ──► run_end → complete()
```

**不变量**：① 用具名（这里是 `agentExecutor`）线程池，模型调用不在事务里；② 助手消息只在循环正常结束时落库（客户端断开则不落）；③ 事件的 `stepId` 是**每 run 内存自增**，`toolCallId` 用模型给的 id（没有则回退 `step-N`）。

### 事件形状（见 [frontend/02](../frontend/02-SSE协议规范.md)）

| `event` | `data` |
|---|---|
| `tool_call` | `{stepId, toolCallId, toolName, arguments, sideEffect}`（`arguments` 是解析后的对象） |
| `tool_result` | `{stepId, toolCallId, success, elapsedMs, result, truncated}`（`result` 是解析后的对象；非 JSON 文本包成 `{"text": ...}`） |

> ⚠️ 全局 JSON 把 `Long` 输出成字符串（见 [frontend/01](../frontend/01-通用约定.md)）。`elapsedMs` 特意按 `int` 给，让它是**数字**；`stepId`/`toolCallId` 本就是字符串。

### 主循环伪代码

```
messages = prompt                               # 系统 + 预算内历史
for round in 1..maxRounds:
    resp = stream(model, ChatRequest{messages, toolSpecifications})   # 阻塞，delta 走回调
    ai = resp.aiMessage; messages += ai
    if ai 没有工具请求:
        return 终极回答 = ai.text
    对每个工具请求 req:
        sink.onToolCall(req)                    # 先发事件
        r = registry.execute(req, ctx)          # 抛错也不向上，转成结果文本
        sink.onToolResult(r)
        messages += ToolExecutionResultMessage.from(req, truncate(r.text))
return 兜底(lastText 或 MAX_ROUNDS_MESSAGE)     # 撞护栏
```

### 涉及的表

**M7 不落任何表**。工具调用过程只存在于内存（`stepId` 内存自增、`runId` 占位 UUID）。`agent_step` / `agent_event` 属 M8（见 [10-数据模型总览](10-数据模型总览.md)、[12](12-中断与恢复的状态机.md)）。

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- **不落库**：没有 `agent_run` / `agent_step` / `agent_event`；进程一挂，这次运行就没了。
- **无中断 / 续跑 / 重连**：循环中途无法停、无法续（M8/M9）。
- **无副作用工具、无人工确认**：`ToolMeta.requireApproval` 已声明但**未被消费**（M10）。
- **无 `todo_update`（计划）、无 `ping` 心跳。**
- **客户端断开后循环仍会跑完**：sink 只是停止推流，循环不感知「没人看了」（见坑 6）。
- **非流式 `POST /chat/message` 不接工具**：仍是简化路径（无检索、无 run）。
- `GET /tools/logs`（调用记录）**未实现**——依赖落库，属 M8。

### 坑 1：`@Tool` 的名字与方法名

- **现象/是否踩到**：LC4j 的 `DefaultToolExecutor(bean, ToolExecutionRequest)` 会**按 `request.name()` 反射找同名方法**，所以用请求级构造器时，`@Tool(name="x")` 必须等于 Java 方法名，否则运行期报「找不到方法」。
- **本项目的规避**：用**方法级**构造器 `new DefaultToolExecutor(bean, method)`（见 3.1），按方法引用调用，与名字解耦。因此本项目**没有**这个限制——写文档记下来，是提醒将来若改用请求级构造器会重新踩到。

### 坑 2：参数名依赖 `-parameters` 编译选项

- **背景**：`@P` 不写 `name` 时，LC4j 用**反射拿到的参数名**当 JSON schema 的键。若编译未开 `-parameters`，拿到的是 `arg0`/`arg1`，模型看到的参数名就丢了语义。
- **本项目**：Spring Boot 的父 POM 默认开启 `-parameters`，所以「不写 name 也行」。但 `KnowledgeTool.searchKnowledge` **仍显式写了** `@P(name="query", ...)`——把关键契约钉死，不赌编译选项。

### 坑 3：流式下，工具调用请求在**结束回调**里，不是 delta

- **现象**：想要「模型一开始决定调工具就发 `tool_call`」，但 `onPartialResponse` 只给文本，拿不到工具请求。
- **原因**：OpenAI 兼容协议里，工具调用的参数是**分片拼装**的，只有到响应结束才成型。LC4j 把它放在 `onCompleteResponse(ChatResponse)` 的 `aiMessage().toolExecutionRequests()` 里（还有 `onPartialToolCall` 等更细的回调，本项目**未用**）。
- **结果**：本项目的 `tool_call` 事件在**该轮模型响应结束后**才发（不是「边生成边发」）。对只读工具够用；将来若要「工具调用刚开始就提示用户」，得用 `onPartialToolCall`。

### 坑 4：无参工具的 `ToolSpecification.parameters()` 是 `null`，不是空 schema

- **现象**：`/tools/list` 或单测里对无参工具取 `spec.parameters().properties()` → NPE。
- **原因**：LC4j 对「没有参数」的工具**省略**整个 parameters schema。
- **规避**：`AgentToolRegistry.paramsOf` 对 `null` 返回空列表；单测断言用 `assertNull`。

### 坑 5：工具错误有两条路径，要都兜住

- **现象**：有的工具失败会被 `DefaultToolExecutor` 转成 `isError=true` 的结果，有的会**直接抛**。
- **原因**：方法**调用期**异常（`InvocationTargetException`）被框架转成 `isError` 结果；而**参数绑定期**异常（如必填原始类型缺失、JSON 解析失败）会向上抛。
- **规避**：`AgentToolRegistry#execute` 用 `try/catch` 把两条路径统一成 `ToolRunResult`，**绝不向上抛**——错误永远以「结果文本」回给模型。

### 坑 6：一运行一线程；不做取消（M7 的简化，M8 要重估）

- **现状**：一次运行在 `agentExecutor` 上**阻塞占一个线程**直到结束。客户端断开后，sink 只是停止推流，**循环仍会把剩余轮次跑完**（只读工具无害，但白烧 token）。
- **为什么先这样**：M7 不落状态、不做中断，最直白的实现就是「一个方法跑到底」。硬塞取消逻辑会让循环和传输耦合。
- **什么时候必须改**：M8 引入「挂起释放线程」（[12](12-中断与恢复的状态机.md) 的 `SUSPENDED` / `WAITING_APPROVAL`）时——那时「一个运行长期占一个线程」不可接受，且要在安全点检查中断标志。届时 `AgentEventSink` 的**实现**（而不是循环本身）需要能向循环反馈「客户端已断 / 请停」。

### 坑 7（重要，未验证）：检索改成工具后，召回依赖模型

- 见 3.3 的决策记录。**这是 M7 引入的行为变化，且尚未用数据验证**：自动检索时「必召回」，改工具后「择机召回」。真实性待 [60-离线评测](60-离线评测.md) 给出结论。
